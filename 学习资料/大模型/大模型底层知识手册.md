## Part 1 Transformer 全景（🔴 先立骨架）

**Transformer = 编码器(Encoder) + 解码器(Decoder) 两族**，主流 LLM（GPT/Claude/LLaMA）是**解码器-only**：

```
输入 tokens
   ↓ Embedding（查表成向量 + 位置编码）
   ↓ 多个 Decoder Block（N 层，每层两个子层）
   ↓  ① 自注意力（Attention）——建模 token 间关系
   ↓  ② 前馈网络（FFN/MLP）——逐 token 独立变换
   ↓ （残差连接 + LayerNorm 包裹两个子层）
   ↓ 最后的线性层 + Softmax → 预测下一个 token 的概率分布
下一个 token = 按概率采样（top-p / temperature）
```

**两张图必会**：
- 一张"token 流"图（上面这个）。
- 一张"**每个 token 只看它前面的 token**"图（因果注意力，因为它是自回归生成）。

**为什么叫"注意力机制"代替 RNN**：
- RNN 只能一步一步**串行**、还忘东西（梯度消失）；Attention**并行**看全序列 + 长距离直接关联（一步抓到远距离依赖）。
- **代价**：显存 O(n²)（后面 Part 8/9 都在治这个）。

## Part 2 自注意力（🔴 第一重点，能默写公式直觉）

### 2.1 直觉一句话

> **自注意力 = 让每个 token 最终向量 = 加权求和"其他（前面）token 的值（Value）"，权重由"这个 token 与它们有多相关（Query×Key）"决定。**

### 2.2 公式（🌟 直觉版必会，能**解释**每个符号）

```
Q = X·W_Q    Query：每个 token 想问什么
K = X·W_K    Key  ：每个 token 提供什么"索引"
V = X·W_V    Value：每个 token 提供什么"内容"
分数 = Q · Kᵀ  (query 问 key，得到两两相关度)
scale:  除以 √d_k（防止点积太大导致 softmax 梯度饱和）
weight: softmax( Q·Kᵀ / √d_k )
输出:   weight · V        （按注意力权重加权取 V）
```

**能答清的三个动作**：
1. **Q 问 K**：得到"我和谁相关"的分数。
2. **归一化成权重**：softmax 把分数变成"加起来=1 的注意力权重"。
3. **按权重取 V**：输出 = 相关 token 的内容按相关度加权混合。

### 2.3 为什么除以 √d_k（高频追问）
分数是 d_k 维向量点积，维度越大点积方差越大 → softmax 会走向极端（一个趋近 1 其余趋近 0）→ 梯度极小、学不动 → **除以 √d_k 把方差拉回 1 附近，梯度稳定。**

### 2.4 因果注意力（解码器必须的"只看过去"）
生成时输出只看已经出现的 token：mask 掉"未来的位置"。**这就是为什么预训练和推理都是"只拿前面的 token 预测下一个"。**

### 2.5 ★ 你的 nanoGPT 钩子（强烈建议讲）
> "我从零复现过 nanoGPT——手写了一个很小的 GPT，理解到注意力机制落地就是三件事：**X 过三个线性层变 Q/K/V → 和 Q·Kᵀ 除 √d → softmax 后乘 V 再投影**；还亲手调过**除以 √d_k 的必要性**（不除的话训练很容易崩/变慢），也看过显存随序列长度**二次方涨**。"

## Part 3 MHA / MQA / GQA（🟡 直觉档）

- **MHA（Multi-Head Attention）**：把 Q/K/V 切 h 个"头"，每头独立学不同关系子空间（语法关系/指代/实体关系），输出拼接。
- **MQA（Multi-Query）**：**所有头共享同一份 K、V**，只有 Q 多头 → KV Cache 大幅缩小（显存省），质量略降。
- **GQA（Grouped-Query）**：折中——**把头分组，组内共享 K/V**（如 8 个 Q 头共享 2 组 KV）→ 质量接近 MHA、显存接近 MQA。**主流新模型多用 GQA。**
- **一句话**："**显存吃紧 → MQA/GQA（少存 KV）**；质量优先 → MHA。GQA 是性价比最优的中间态。"

## Part 4 FlashAttention（🟡 直觉档，会讲故事）

- **误解纠正（必说）**：**FlashAttention 快在"省显存搬运"，不是"省计算量"（FLOPs 没变）。**
- **传统 attention 的毛病**：把 N×N 的注意力分数矩阵**先算出来放显存**（O(n²) 显存）再读回来做 softmax → **往返 HBM（高带宽内存）太多次，是最慢的环节**（算力快、搬运慢，瓶颈在 IO）。**长序列时 O(n²) 显存直接爆。**
- **FlashAttention 怎么做**：**分块（tiling）**：把大矩阵拆块，在**片上 SRAM 里算一块就出结果一块**，并**在线 softmax**（fusão：softmax 归一化可以滚动态算）→ **不落盘中间大矩阵 → 显存从 O(n²) 降到 O(n)、搬运量大减 → 又快又能跑长序列**。
- **一句话**："**长序列慢/爆显存是'搬运'和'占地'问题，FlashAttention 用分块 + 在片上算，把显存从 O(n²) 降到 O(n)。**"

## Part 5 位置编码与 RoPE（🟡 直觉档）

- **为什么需要**：Attention 本身**不讲顺序**（Q·K 只关心"像不像"，不关心"谁在前"）→ 不加位置信息，{A B C} 和 {C B A} 对模型一样。
- **方案演进**：绝对位置（加一个位置向量）→ **RoPE（旋转位置编码）**（主流）。
- **RoPE 直觉**：**把 Q/K 向量按位置"旋转"一个角度**（位置 i 的向量旋转 i·θ）→ 这样**两 token 的相对位置**就体现在"它们的点积相位差"上 → **相对位置天然建模 + 外推性好**。
- **一句话**："RoPE 就是给每个位置的 Q/K 加一个和位置绑定的'旋转'，让注意力自然感知到'相隔多远'——主流模型都靠它给 token 排座次。"

## Part 6 Token 化与词表（🟢 知道即可）

- **Tokenizer**：把文本切成子词（BPE），不是按字/词。"I love" → 可能 [I][love] 或更细。
- **为何子词**：平衡"字"（语义碎、序列长）和"词"（词表爆炸、没见过的词）→ 子词是折中。
- **词表与训练**：Vocab 决定 embedding 维度；**"token 数"和"字符数"不是一回事**——所以 cost 按 token 算。
- **你有体感**：Claude 讲"这段文本大概多少 token"，也体现在你看到的 token 消耗/费用里。

## Part 7 推理两阶段：Prefill / Decode（🔴 必懂，贯穿全书）

- **Prefill（预填充）**：传入整套输入（prompt），**一次性**把所有 token 的 K、V 算出来、缓存。→ **算力密集（compute-bound）**，并行度高，像"大矩阵乘"。
- **Decode（解码）**：**逐个**生成下一个 token：只算新 token 的 Q，与缓存的 K、V 做注意力 → 出 token 继续。→ **内存/带宽密集（memory-bound）**：瓶颈是"读出全部 KV cache"，不是算。
- **直观对比**：Prefill 像"编译整个项目"；Decode 像"每打一个字都要重新读一遍整本书"。
- **为什么"第一个 token 快、后面慢"**：Decode 每步都要读完越来越长的 KV Cache，读的越多越慢 → 这就是**长上下文下"首 token 快、末 token 近于线性变慢"的根因**。

> **一句话记忆**："**Prefill 是算力瓶颈，Decode 是显存带宽瓶颈**——所以推理优化（FlashAttention/KV 量化/投机解码）本质都在打 Decode 的'读 KV 太慢'，而不是打算力。"

## Part 8 KV Cache（🔴 直觉 + 为什么吃显存）

### 8.1 直觉一句话
> **KV Cache = 把"前面已算过的 K、V"缓存起来，生成下一个 token 时不用回头重算整个序列，只算新 token 的 Q 再和缓存做注意力。**

- **不缓存会怎样**：每个新 token 都要从开头重算全部 K/V → 计算量 O(n³)（二次方重复）。
- **缓存后**：每步只算新 K、V → 新增量 O(1) 步；显存却**累积 O(n²)**（序列越长存越多）。

### 8.2 为什么 KV Cache 吃显存（🔴 必背公式直觉）
每 token 存的 KV 大小：
```
2 (K 和 V) × n_layers × n_kv_heads × head_dim × dtype_bytes
```
- 序列 n 个 token → 总占 = n × 上式（**线性于 n，乘上"层数×头数×维度"就很大**）。
- **举例直觉**：8B/32 层模型、几千 token 的 KV Cache 就能上 GB 级 → **哪怕模型权重不大，长上下文也把显存占满**。

### 8.3 与你的上下文直觉对应
- 你观察到"Claude Code 跑到一定长度要 auto-compact"——**根源就是 KV Cache 撑爆/decoding 越来越慢。**
- **这也是"长上下文 ≠ 免费"的技术底层**（Part 12 会再论证）。

## Part 9 PagedAttention 与推理引擎（🟡 直觉档）

- **问题**：KV Cache **先不知道会多长**（新 token 一直来）→ 按"最大可能"预留 → **内部碎片 + 显存浪费**；多请求各自预留 → 挤爆。
- **PagedAttention 直觉（一句话）**：**把 KV Cache 切成固定大小的小块（页），像操作系统的分页一样按需分配、还能共享** → 减少碎片、利用率高 → 显存装下更多请求/更长序列。
- **比喻**（必会）：**"PagedAttention 借鉴 OS 虚拟内存分页：把连续的 KV 逻辑上连续、物理上分块管理，缺了就申请一页，还能多请求共享同一页（前缀共享）。"**
- **vLLM**：最早把 PagedAttention 工业化的推理引擎（高吞吐、KV 管理、连续批处理）。
- **顺口衔接**：你的 OS 分页知识（OS 册 4.2）正好引到它——**"分页"思想在 OS 和推理里是同一个隐喻。**（这是跨册串联高光点。）

## Part 10 推理加速与量化（🟢 有余力再看）

- **量化（Quantization）**：权重/激活从 fp16/int8/int4 → **省显存 + 快（读得少）**，代价是精度略降。（**你观察 Claude 各模型有大小档，就是量化/规模取舍的体现。**）
- **投机解码（Speculative Decoding）**：**用一个小草稿模型快速猜多个 token → 大模型一次验证** → 并行验证省"读 KV" → 加速 Decode。
- **连续批处理（Continuous Batching）**：不等一个请求结束就插入新请求，是 vLLM 高吞吐的原因。
- **缓存前缀共享**：共享系统提示的前缀 KV，多个请求复用（**这就是你每天看到的模型服务端 Prompt Cache 的实现底层之一**，和 Agent 册 4.4 呼应）。

## Part 11 训练三阶段：预训练 / SFT / RLHF / DPO（🔴 高频）

### 11.1 三阶段全景（🌟 直觉版必会）
```
① 预训练（Pre-training）
   目标：下一个词预测（next-token prediction），海量文本
   结果：基础模型（base）——会续写，但不会"听话/对话"
   成本：最大最贵（几十 TB 文本、万卡级）
   ↓
② 指令微调（SFT, Supervised Fine-Tuning）
   用"指令→优质回答"对子训练，学"按指令办事、回答格式/语气"
   结果：助手模型——会聊天，但可能不主动拒绝、编造
   成本：中大（几十万~百万高质量样本）
   ↓
③ 对齐（RLHF / DPO）
   目标：让模型的行为**符合人类偏好**（有用/无害/诚实），学会不能被 SFT 教会的"不编/拒绝"
```

### 11.2 RLHF（🟡 直觉档）
- **三步**：① 标人类偏好（两个回答哪个好）→ 训一个**奖励模型 Reward Model**；② 用 RL（PPO）把策略模型调成"奖励打分越高越好"；③ 同时加入 KL 约束/红队，防止模型为了"高分"走上邪路。
- **直觉一句话**："RLHF = 先用人类偏好训练'裁判'（奖励模型），再让大模型在裁判打分下做强化学习改进行为；难点是 RL 难训、不稳定。"

### 11.3 DPO（🟡 直觉档，常考性价比）
- **一句话**："**DPO 跳过强化学习循环**：直接用延迟偏好数据（哪条回答好）构造目标，逼模型让'被偏好的回答'概率更高——**不训奖励模型、不跑 RL，更稳更省，效果常逼近 RLHF。**"
- **对比记忆**：RLHF = 学"打分"再优化；DPO = 直接学"偏好"。

### 11.4 为什么 SFT 不够、还要对齐（高频追问）
- SFT 教的是"回复长这样"，但**学不会"不该编的别编、该拒绝的拒绝"**这类高风险行为（标注质量也难控）。
- 对齐（RLHF/DPO）是**在行为层面做偏好优化**，把"编造/有害/不合规"压下去；同时还要**红队测试**验证（你的测试思维完全适用）。

## Part 12 上下文窗口与长上下文（🔴 Kimi 场景必背）

### 12.1 长上下文的代价是什么（🔴 必答三层）
1. **成本**：每 token 都进 attention，token 数线性涨钱（输入也计费）。
2. **延迟**：**prefill 是算力瓶颈、decode 每步读的 KV 越来越长** → 长上下文 = 末 token 慢。
3. **质量**：**注意力衰减（Attention 噪声）**——"大海捞针"测试：信息埋在长上下文中间，模型会**漏掉该看到的关键信息**（长上下文 ≠ 模型真能利用全部内容）。

### 12.2 ★ Kimi / Moonshot 专项（背下这个论证）
> "Kimi 主打的**长上下文**（K2 曾到 256K，主打 Agentic Coding）技术上是真本事，但**长上下文 ≠ 免费 ≠ 全能**：显存（KV Cache）、延迟（Decode 读 KV）、注意力衰减（信息淹没）三个代价都在。所以我的判断是：**长上下文解决了'放得下'的问题，没解决'用得动、看得准'的问题——检索型 Context Engineering（只喂需要的片段 + 提示缓存）依然不可替代**。两者是互补：长上下文兜底大输入，检索压缩兜底成本与质量。"

> **（这就是 v3 清单里 Kimi 专项的核心论证，用 12.1 的技术依据讲出来会非常扎实。**）

## Part 14 面试题库与直觉卡

### 直觉卡（🌟 面试前必须全部能一句话讲清）
| 点 | 一句话直觉 |
|---|---|
| Attention 在算什么 | 每个 token 按"与其它 token 的相关度"加权融合各 token 的内容 |
| 为什么除 √d_k | 防止点积方差大导致 softmax 饱和、梯度消失 |
| MHA/MQA/GQA | Q 多头各学各的；KV 共享多少份 = 显存 vs 质量折中 |
| FlashAttention | 快在省显存/搬运（分块+SRAM+在线 softmax），不是省 FLOPs |
| RoPE | 给 Q/K 按位置旋转，相对位置自然建模 |
| Prefill vs Decode | 前者算力密集、一次性；后者带宽密集、逐 token 读全 KV，所以逐 token 慢 |
| KV Cache 为什么吃显存 | 2×层×头×维度×token 数，序列越长越大 |
| PagedAttention | 像 OS 分页一样把 KV 分块管理，减碎片、可共享 |
| 训练三阶段 | 预训练学续写→SFT 学对话→RLHF/DPO 学偏好与安全 |
| RLHF vs DPO | RLHF 训奖励模型+RL 优化；DPO 跳过 RL 直接用偏好，更稳更省 |
| 长上下文代价 | 成本↑、Decode↓、注意力衰减(大海捞针)——所以≠免费 |

### 必会口语题（每题能用 1-2 句回答）
1. 请讲一下 Transformer 是怎么算的？→ Part 1 + 2 两张图和公式直觉。
2. FlashAttention 为什么快？→ 省显存搬运，分块在片上算，显存 O(n²)→O(n)。
3. 为什么 Decode 比 Prefill 慢？→ Decode 每步读完整 KV Cache，带宽瓶颈。
4. KV Cache 是什么？为什么占显存？→ 缓存已算 K/V；公式 2×层×头×维×token。
5. PagedAttention 是什么？→ OS 分页思想管理 KV，减碎片、支持共享（vLLM）。
6. RLHF 和 DPO 区别？→ RL 循环 vs 直接偏好优化。
7. 长上下文一定好吗？→ 不好说：成本/延迟/注意力衰减，检索仍必要。
8. 你训练过模型吗？→ nanoGPT 从零训过（Part 2.5 话术）。
