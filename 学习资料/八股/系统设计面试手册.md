## Part 1 系统设计面试怎么答（万能框架）

遇到"设计一个 XX 系统"，别急着画图。按这个顺序讲，**显得有条理、覆盖加分点**：

1. **需求澄清**（先问，别假设）：功能？规模 QPS/日活/数据量？读多写少？强一致还是最终一致？有没有实时要求？（**"你打算支持多大并发"是面试官最爱的第一个问题。**）
2. **容量估算**（展示工程感）：QPS × 每天 → 存储量；单机能扛多少 → 要几台。（不用精确，量级对即可。）
3. **接口设计**：核心 API/数据模型。
4. **存储选型**：关系型/缓存/KV/对象存储/搜索/向量（见数据库册 Part 10）。
5. **核心链路**：画数据流图（读写路径、缓存层、异步化）。
6. **难点攻坚**：一致性、高可用、容错、扩展（这是拿高分的地方）。
7. **监控与降级**：怎么发现、怎么兜。

> **面试官真正在看**：你有没有**权衡（trade-off）意识**和**把问题拆层**的能力，而不是标准答案。**每给一个方案就说出它的代价**（"用 Redis 快，但要处理缓存一致性/雪崩"）会显著加分。

## Part 2 缓存

### 2.1 缓存穿透/击穿/雪崩（🔴 必考三连）
- **穿透 Penetrating**：查**不存在的 key**，每次都打到 DB（缓存和 DB 都没这个值）。→ **解法**：缓存空值（设短 TTL）或布隆过滤器/参数校验。
- **击穿 Breakdown**：**某个热点 key 突然过期**，大量请求同时打到 DB。→ **解法**：**互斥锁**（只让一个线程回源重建）/ 逻辑过期不真删 / 热点 key 永不过期。
- **雪崩 Avalanche**：**大量 key 同时过期** 或 缓存宕机，DB 被打垮。→ **解法**：**过期时间加随机抖动** / 多级缓存 / 限流兜底 / 集群高可用。

**记忆**：穿透=查没有的（挡不存在）、击穿=一个热点过期（挡单点）、雪崩=大面积过期（挡整体）。

### 2.2 缓存一致性（🔴 核心：Cache Aside + 延迟双删）
- **Cache Aside（旁路缓存）**：读时先查缓存→miss 查 DB→写缓存；写时**先更新 DB，再删除缓存（del）**（不是更新缓存）。
- **为什么"删缓存"而不是"改缓存"？** → 并发写时"改缓存"可能因时序写旧值；"删缓存"下次读会从 DB 重建，简单可靠。
- **为什么"先写 DB 再删缓存"？** → 反过来（先删后写）可能在两步之间被并发读回填了旧缓存。
- **经典"脏数据"时序**：写 DB 成功 → 删缓存前，一个读请求读到旧 DB 值并回填缓存 → 缓存变旧。解法：**延迟双删**（更新 DB → 删缓存 → 延迟再删一次）或用**消息队列异步重试删**。
- **强一致场景**：不用缓存旁路，直接读写主库 + 分布式锁，或用**缓存与 DB 同事务**（少见）。
- **你的挂钩**：
  - **Prompt Caching**（Claude/Kimi）本质就是"把固定前缀的结果缓存起来"——**这就是 Cache Aside 的思想应用到 LLM**。**面试可把"我理解 Prompt Caching 就是一种旁路缓存/前缀缓存"讲出来，是把传统八股迁移到 AI 的漂亮串联。**
  - 你的 Claude 对话归档、飞书快照的"每日更新 + 读时检索"= 缓存 + 持久化。

### 2.3 缓存算法（🔴 面试会考 LRU/LFU）
- **LRU（Least Recently Used）**：淘汰最久未用的。**O(1)** 用**双向链表 + HashMap**。
- **LFU（Least Frequently Used）**：淘汰使用次数最少的。
- **你的挂钩**："设计 context 缓存"常被包装成 LRU 题（刷题清单已列）→ 你可以把 **LRU 双向链表**手写出来，并说"我理解它和 KV Cache 淘汰同构"。**（呼应大模型底层册的 KV Cache。）**
- **分布式缓存一致性**：Redis 主从/集群下，**多副本更新不同步 → 读旧值**。用**缓存与 DB 双写/订阅 binlog**（Canal）等方案，或"以 DB 为准，缓存做尽力而为"。

## Part 3 消息队列

### 3.1 MQ 的三大作用（🔴 必背）
1. **解耦**：生产者和消费者互不依赖（加一个新消费者不用改生产者）。
2. **削峰/缓冲**：流量高峰先进 MQ 排队，消费者按能力慢慢处理。
3. **异步**：主流程不阻塞，非关键路径后置。

### 3.2 MQ 的可靠性问题（🔴 深挖重点）
- **消息丢失三个环节**：
  1. 生产端：消息没发出去（ack 机制/事务消息）。
  2. Broker 端：收到没持久化（持久化 + 多副本）。
  3. 消费端：收到没处理完就 ack（**手动 ack，处理完再确认**）。
- **重复消费（at-least-once）**：网络/重启导致同一条消息被消费两次 → **消费端必须幂等**（见 Part 4）。
- **顺序性**：MQ 一般不保证全局顺序（并发消费就乱序）；要顺序就**分区/单队列 + 单线程消费**。
- **积压（堆积）**：消费不过来 → 报警 + 扩容消费者 + 批量/快速消费。

**你的挂钩**：
- **每日总结机器人**把"生成 + 发飞书"异步化（不阻塞调度）。
- **EtherCAT 多轴联动**用"状态/指令消息队列驱动 FSM"→ **天然保序、避免共享变量竞态**（这本质上就是"用队列解耦+串行消费"思想）。**这是"用 MQ 思想做嵌入式/实时"的高级类比，讲出来很亮眼。**

## Part 4 幂等、重试与去重（🔴 分布式第一基本功）

### 4.1 什么是幂等（🔴 必背定义）
**同一个操作执行一次和执行多次，对系统状态的影响相同。**

- **为什么必须幂等**：网络重试、MQ 重复投递、用户重复点击、**Agent 重试工具调用**——只要有重试，就必须幂等。

### 4.2 实现幂等的常见手段（🔴 会列就行）
1. **唯一约束/幂等键**：请求带唯一 ID，DB 插主键冲突则忽略（最常用）。
2. **去重表/去重集合**：记录已处理请求 ID。
3. **乐观锁**：version/状态机 CAS（只有从"待处理"→"处理中"成功的那个生效）。
4. **Token/序号**：服务端下发一次性 token。
5. **条件更新**：`UPDATE ... SET status=? WHERE id=? AND status='待处理'`（靠影响行数判断谁成功）。

### 4.3 重试的三个坑
- **重试要有退避（backoff）+ 上限**（不能无限重试打死下游）→ **这也是 Agent 工具调用必须有的"最大重试次数/退避"。**
- **重试放大**：下游 100% 失败时，N 个调用方各重试 M 次 → 流量放大 N×M → 需**熔断**（见 Part 5）。
- **非幂等操作不能盲重试**（转账/写库）→ 要么幂等化，要么重试要幂等。

> **★ 你的天然优势**：你做**测试**，最清楚"重试/网络抖动导致重复请求"这类问题。**面试讲"我的职业训练让我系统性地想幂等和重试"是真实且有说服力的**：
> "作为测试工程师，我习惯性地从'失败和重复'角度想问题——网络会重试导致重复消费、进程会重启导致消息重投。所以我做 Agent 工具调用时，会给每个工具设计幂等键、设置重试上限和退避，避免一次工具失败把整个 Agent 拖进重复副作用。"

## Part 5 限流、降级、熔断、兜底

- **限流**：限制请求速率，保护系统。
  - 常用算法：**令牌桶**（桶里按速率放令牌，取到才能过，突发可多取）、漏桶、滑动窗口、固定窗口计数器。
  - 维度：QPS、并发数、用户/IP、单用户配额（**Agent 的 token 配额就是维度之一**）。
- **熔断（Circuit Breaker）**：下游错误率超阈值 → **直接快速失败**不再打下游（保护自己也保护下游），一段时间后半开试探恢复。状态：**Closed（正常）→ Open（熔断）→ Half-Open（试探）**。
- **降级**：关掉次要功能/返回兜底数据，保证核心可用（如推荐挂了返回默认列表）。**"优雅降级"**。
- **兜底/超时**：任何外部调用都要有超时 + 兜底（Agent 工具尤其）。
> **你的挂钩**：Agent 的**死循环熔断**（最大步数）、**工具超时**、**token 超预算就降级**、**模型故障切备用小模型（模型路由）**——**这套就是"限流+熔断+降级"在 Agent 里的翻版。**面试时明确点出这个对应关系，极加分。

## Part 6 负载均衡与网关

- **四层（LVS/云 LB）**：TCP 层转发，性能高，不理解应用协议。
- **七层（Nginx/API 网关）**：理解 HTTP，按域名/路径路由，可做缓存/限流/鉴权/灰度。
- **算法**：轮询、带权轮询、最少连接、一致性哈希（**节点变动时只影响相邻 key，缓存场景友好**）。
- **健康检查 + 摘除**：定时探活，失败自动摘除、恢复加入（**你的 systemd/Drone CI 也有健康/重启逻辑，同思想**）。
- **会话保持**：有状态（Agent 对话）需要 sticky 或把状态外置（Redis）。

## Part 7 读写分离、分库分表、一致性

- **读写分离**：主库写、从库读；**主从延迟**问题（刚写完立刻读可能读到旧值 → 强一致读走主库、或延迟窗口内等从库追上）。
- **分库分表**：水平拆（分片，按分片键如 user_id hash 路由）/ 垂直拆（按字段/服务拆）。**难点**：跨片查询、跨片事务、分片键选不好导致热点。
- **一致性（CAP/BASE）**：
  - **CAP**：一致性 C / 可用性 A / 分区容错 P 三选二；P 无法放弃（网络一定分区），所以是 **CP（ZK/etcd，强一致）** 还是 **AP（Eureka，容忍不一致）**。
  - **BASE**：基本可用/软状态/最终一致（NoSQL 常用）；实现手段=**异步化 + 重试 + 幂等 + 对账**。

## Part 8 分布式锁

- **为什么需要**：多实例下"只让一个执行"（去重、定时任务不重复、防止并发超卖）。单机的 `mutex` 在多进程/多机不管用。
- **实现（Redis）**：`SET key val NX EX seconds` 原子加锁 → 释放时**用 Lua 脚本校验持有者再删**（防误删别人的锁）。**必须设过期时间防死锁**；要考虑**续期**（长任务）与**可重入**。
- **更可靠**：ZooKeeper/etcd（临时顺序节点 + Watch，有 ZAB/Raft 强一致保障）。
- **经典问题**：锁超时但业务没执行完 → **续期/watchdog**；网络分区下误删锁 → 校验持有者。
> **你的挂钩**：Agent 并发跑多个任务时，需要"同一份知识库同一时刻只被一个进程写"（防 SQLite 并发写损坏）→ **文件锁（`flock`）或进程内锁**——**这也是分布式锁的简化版思想**。**（你的四库每日更新脚本就能用 flock 讲这个。）**

## Part 9 可观测性：日志/监控/指标/追踪

- **三支柱**：
  - **日志（Log）**：离散事件，定位细节（你的 `box_aligner_node.*.log`、`journalctl`）。
  - **指标（Metric）**：可聚合数值（QPS、延迟 P99、内存、错误率），看趋势/告警。
  - **追踪（Trace）**：一次请求跨服务的完整链路（TraceId 串联），定位"慢在哪一跳"。
- **关键指标（后端必背）**：**QPS、响应延迟（P50/P95/P99）、错误率、可用性（几个 9）**。**为什么要看 P99 而不是平均值**：平均值被大量快请求拉低、掩盖长尾，而用户感知的是慢请求。
- **告警与 SLO**：定可用性目标（如 99.9%），用监控告警兜。
> **★ 你的天然优势（务必点出）**：你做**测试/压测/稳定性**出身，对"长稳、压测、节拍、显存泄露"极熟。面试时**主动把 Agent 系统设计的"评估/可观测性"往你测试经验上靠**：
> "Agent 系统最缺的就是可观测性，因为它的输出有概率性。我做 Agent 时把测试的思维搬过来：用**任务成功率、工具调用准确率、平均步数、token 成本、失败类型分布**当核心指标，给每次运行打 trace，失败可回放——本质就是给 LLM 加了测试体系的观测网。"

**（这段把"Agent 评测"和"传统系统可观测性"缝合，是极高分的回答，务必练熟。）**

## Part 10 ★ 把 Agent 系统当分布式系统设计（你的高分区）

> **本节是你的核心武器。** 传统系统设计题问"设计一个高并发 IM"，你可以说"我更熟 Agent 系统"，然后**用分布式系统的语言把 Agent 的可靠性问题讲透**——这既避开了你不熟的领域，又展示了你独有的 Agent 工程深度。**背下这套映射。**

### 10.1 概念映射表（🔴 核心，直接记这张表）
| Agent 里的问题 | 对应分布式系统概念 | 解决手段（从八股借来） |
|---|---|---|
| **上下文窗口有限，要压缩** | **缓存/分层存储**（热数据内存、冷数据磁盘） | Context 压缩/摘要+检索按需加载（= Cache Aside） |
| **Prompt Caching** | **旁路缓存 Cache Aside** | 固定前缀缓存命中，避免重复算力 |
| **工具调用失败要重试** | **重试 + 退避 + 幂等** | 幂等键、重试上限、指数退避 |
| **死循环（反复调同一工具）** | **熔断 + 循环检测** | 最大步数、重复调用检测、循环就熔断 |
| **token 成本爆炸** | **限流（配额/令牌桶）** | token 预算、单任务配额、模型路由（大小模型） |
| **工具超时/不可用** | **超时 + 降级 + 熔断** | 工具超时、失败切备用工具/小模型 |
| **Agent 任务异步（长任务）** | **消息队列 / 任务队列** | 任务入队异步执行，结果持久化，按 ID 查 |
| **重连后丢上下文** | **会话状态外置 + 幂等恢复** | 状态存外部（DB/文件），按 session_id 恢复 |
| **多用户并发对话** | **无状态化 + 负载均衡** | 会话状态外置、有状态→粘性/共享存储 |
| **Agent 表现不稳定（概率性）** | **可观测性 + 评测体系** | 成功率/步数/token 指标 + 失败 trace 回放 |
| **上下文中残留旧/脏信息** | **缓存一致性 / 数据污染** | 上下文来源可信、过滤注入、定期重置 |

### 10.2 用这套语言设计一个"多用户 Coding Agent 服务"（完整答法示例）

> "如果让我设计一个多用户 Coding Agent 服务，我会这样分层（**先说需求：并发多少、任务多久、要不要多轮有状态**）：
>
> **1. 接入层**：API 网关做鉴权（JWT/Token）、限流（令牌桶，防单用户刷爆 token 配额）。
>
> **2. 任务调度层**：Agent 任务是**长耗时、异步**的——用**任务队列**（MQ）解耦，把'提交任务'和'执行'分开，前端轮询/SSE 拿结果。**这能扛住并发、也能让失败的单个任务不拖垮整体**（相当于削峰+异步）。
>
> **3. 执行层（单任务内部，就是一个带工具的循环）**：
>   - 每步调模型（流式），**上下文按需检索+压缩**（不能每步都塞全量，否则 token 成本 O(n²) 爆炸——这是 Cache Aside + 容量规划思想）。
>   - 工具调用要**幂等 + 重试退避 + 超时 + 熔断**（比如某个工具连续失败就跳过/换路径，别死循环）。
>   - **循环保护**：最大步数、检测重复同一调用则熔断。
>
> **4. 状态与一致性**：会话/任务状态**外置**（DB/文件），按 session_id 恢复，**不要把状态只放在单实例内存**（否则重启/负载均衡就丢）。上下文来源要过滤（如防外部文档里的注入）。
>
> **5. 成本与降级**：token 预算封顶；主模型故障/超预算降级到小模型或返回部分结果（模型路由）；不可用工具快速失败并告知用户。
>
> **6. 可观测性（我最想强调）**：因为输出有概率性，我把**测试的思维**搬过来——给每次运行打 trace，记录**任务成功率、工具调用准确率、平均步数、token 成本、失败类型分布**；失败可回放复现。这套指标就是 Agent 的'监控看板'，没有它，Agent 就是黑盒。
>
> **（收尾 trade-off）**：这里我做了很多取舍——用队列换解耦但多一跳延迟；用幂等换可靠性但要设计幂等键；用熔断换稳定性但可能误伤。总的原则是**宁可少给功能，也不要给一个会死循环、爆 token、不可观测的 Agent**。"

**（这段是把"传统系统设计八股"和"你的 Agent 工程"缝合的满分答法。它：用了 Part 2 缓存、Part 4 幂等重试、Part 5 熔断降级、Part 9 可观测性的全部八股词汇，又全部挂在 Agent 上，还突出了你测试背景的差异化。强烈建议一字一句背熟，面试时按岗位侧重取舍展开。）**

### 10.3 追问准备
- "Agent 的死循环怎么彻底解决？"→ 不止"最大步数"：① 最大步数/预算硬上限；② 重复调用检测（同工具同参数）→ 熔断；③ 环境反馈（无进展检测）；④ 超时。**再讲"这本质是分布式系统的熔断+循环检测"。**
- "怎么保证重试不产生重复副作用？"→ **幂等键**（Agent 每次工具调用生成幂等键，工具端去重）。
- "怎么控制成本？"→ token 预算 + 动态加载 + 提示缓存 + 模型路由 + 提前终止（简单任务小模型）。**每条都能回落到八股。**
- "Agent 和传统服务最大的可靠性差别？"→ **输出概率性**（同输入可能不同结果）→ 所以不能只做"接口监控"，要做**效果评测 + 抽样人工复核**（测试思维）。**（这是你独有的洞察，别人讲不出来。）**

## Part 11 经典系统设计题（购物车/秒杀/IM）

> **只求有套路，不求背。** 面试官更愿意看你**主动澄清需求 + 画数据流 + 讲难点**。下面给最短答题骨架。

- **秒杀/超卖**（最常考，考一致性+防刷）：
  - 答：前端限流+按钮防抖 → 网关限流 → **库存扣减用原子操作**（Redis `DECR`/DB `UPDATE stock=stock-n WHERE stock>=n`，防超卖）→ MQ 异步下单 → 削峰。
  - 亮点词：幂等、原子扣减、削峰、限流、防刷。
- **IM/聊天**（考 WebSocket、长连接、消息有序）：
  - 答：WebSocket 长连接 + 网关路由 → 在线连接管理（谁在哪台）→ 消息存储（MQ 异步落库）→ 离线推送 → 有序（单会话单队列）。
- **短链/海量计数**（考存储选型）：
  - 答：自增 ID/哈希映射（内存 KV）→ 存储分层 → 缓存热点 → 扩容一致性哈希。
- **文件/大文件上传下载**（考分片、断点续传）：分片上传 + 合并校验 + CDN 分发。

> **你如果面到不熟的题，通用救场句**："这块我实战接触不多，但我的思路是：先确认规模需求，再从**存储选型→核心链路→一致性/高可用→可观测性**四步推。如果落到我熟的部分（比如 Agent 任务编排、工具可靠性、评测），我可以展开讲。"（**诚实 + 展示方法论 + 引导到自己主场，优于硬编。**）

## Part 13 面试题库

### 13.1 高频必答
1. 缓存穿透/击穿/雪崩？分别怎么解？→ 空值/布隆；互斥锁/逻辑过期；随机TTL/多级/限流。
2. 缓存和 DB 怎么保证一致？为什么"删缓存"不"改缓存"？→ Cache Aside，先写 DB 再删缓存，删更简单且并发下更安全；延迟双删兜时序。
3. 什么是幂等？为什么要幂等？怎么实现？→ 一次和多次效果同；重试/MQ 重投；唯一键/去重表/乐观锁。
4. 重试有什么坑？→ 无退避打死下游、重试放大、非幂等不能盲重试 → 退避+上限+熔断+幂等。
5. 什么是熔断？和限流、降级的区别？→ 熔断切失败保下游，限流控速率，降级关次要保核心。
6. MQ 怎么保证不丢消息/不重复？→ 生产 ack/事务、Broker 持久化多副本、消费手动 ack；重复靠消费端幂等。
7. 什么是 CAP？P 能放弃吗？→ 三选二，CAP 的 P（分区）不能放弃，故实为 CP 或 AP；BASE=最终一致。
8. 分布式锁怎么实现？注意什么？→ Redis SET NX EX + Lua 校验释放；要续期、可重入、防误删。
9. 后端核心指标有哪些？为什么看 P99？→ QPS/延迟/错误率/可用性；P99 看长尾，avg 掩盖慢请求。
10. 什么是负载均衡？算法有哪些？→ 轮询/带权/最少连接/一致性哈希；会话保持。

### 13.2 深挖
- 缓存一致性"先删后写"行不行？→ 行（概率更低），但要防"删后被并发读回填旧值"→ 双删/订阅 binlog。
- 令牌桶和漏桶区别？→ 令牌桶允许突发（桶有存量），漏桶匀速。
- 熔断怎么"半开"？→ 定时放少量请求试探，成功则全开、失败继续熔断。
- CAP 里"一致性"是强一致还是？→ CAP 的 C 指线性一致性/强一致；最终一致属于另一套（PACELC）。
- 为什么"能重试"必须"幂等"？→ 重试就是重复执行，不幂等会产生重复副作用（转账/下单）。

### 13.3 ★ 结合项目（Part 10 是你的主战场）
- "怎么保证 Agent 工具调用的可靠性？"→ 幂等键+重试退避+超时+熔断+死循环检测。
- "怎么控制 Agent 成本？"→ token 预算+提示缓存+动态加载+模型路由+提前终止。
- "Agent 系统怎么做可观测/评测？"→ 测试思维：trace + 成功率/步数/token/失败分布 + 失败回放。
- "设计一个多用户 Coding Agent 服务。"→ 讲 Part 10.2 那段完整答法。
