## Part 1 关系模型与 SQL 基础

- **表/行/列/主键/外键/约束**。
- **范式**（1NF/2NF/3NF/BCNF）：解决数据冗余与更新异常（插入/删除/更新异常）；**反范式**：用冗余换查询性能。
- **SQL 执行顺序**（高频纠错点）：`FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`。**注意：WHERE 作用于行、HAVING 作用于分组后。**
- **JOIN 类型**（高频）：`INNER`（匹配才留）、`LEFT`（左全留，右补 NULL）、`RIGHT`、`FULL`；性能上尽量用 INNER/小表驱动。

## Part 2 存储引擎

- **InnoDB**（MySQL 默认）：**支持事务、行级锁、外键、聚簇索引**。
- **MyISAM**：表级锁、不支持事务、读取快（早期）。
- **SQLite**（★你的四库用的）：**单文件嵌入式数据库**，**无独立服务进程**、库就是文件；**ACID 靠 WAL/锁**；**B-tree 索引**；**FTS5 全文检索扩展**。**"嵌入式 vs 服务式"**：SQLite/MySQL 客户端-服务器、零运维、单写者；适合本地/边缘/单用户，读并发受限（写锁全局）。
- **面试话术**：
> "我的四套知识库用 SQLite + FTS5，选它的逻辑是**嵌入式、零运维、单文件可备份、够用**——四库是单用户/低并发的个人检索场景，不需要 MySQL 那种独立服务。但我也清楚它的边界：写并发受限（单写锁），所以只适合我这个量级；一旦要多用户高并发写，就得换 PG/MySQL。**选型不是选最强的，是选'够用且运维成本最低'的。**"

**（"清楚工具的边界"这句话是资深信号，一定要说，面试官爱听。）**

## Part 3 索引：B+ 树（🔴 第一重点，必须能默画 + 讲透"为什么选它"）

### 3.1 为什么数据库索引用 B+ 树（🔴 必背，三层递进）
1. **要减少磁盘 IO**：磁盘慢在"寻道"，索引要"少读几次磁盘"。→ 需要**树高尽可能矮**（扇出大）。
2. **B 树/B+ 树是多路平衡树**（不是二叉树）：一个节点能挂很多子指针 → **扇出大 → 树矮 → 查 1000 万行只要 3~4 次 IO**。
3. **进一步优化 → B+ 树**（比 B 树多两点，工程上数据库主用）：
   - **只有叶子存数据 + 叶子间用链表串起来** → 非叶节点只存索引键 → **一个节点能放更多键 → 树更矮 → IO 更少**。
   - **数据/记录都在叶子且有序串联** → 适合**范围查询**（`WHERE id BETWEEN ?`）：定位起点后沿链表顺序扫。
   - 总结：**B+ 树 = 矮 + 范围查询友好**，是"少 IO + 支持范围"的完美折中。

> **必背的推导链**：磁盘 IO 慢 → 减少 IO → 每节点多存（矮树）→ B+树（非叶只存索引，扇出大）→ **查几万行只要 3-4 次 IO**。

### 3.2 聚簇索引（🔴 高频且易混）
- **InnoDB 主键索引 = 聚簇索引**：叶子节点直接存**整行数据**，所以**必须有主键**（无主键则 InnoDB 挑一个唯一非空列当主键，都没有则用隐藏行 ID）。
- **优点**：范围查询快、主键查询极快（不用回表）。
- **二级索引 + 回表**：二级索引叶子存**主键值**；用二级索引查非主键列时，需**再拿主键去聚簇索引取整行** = **回表**。**如果二级索引已包含要查的列 = 覆盖索引，不用回表（更快）。**

### 3.3 最左前缀原则（🔴 组合索引必考）
- 复合索引 `(a, b, c)` 的查询能用上的条件需**从最左连续**：查 `a`✓、`a,b`✓、`a,b,c`✓；查 `b`✗、查 `a,c`✗（`c` 断了）→ **`c` 用不上，条件不连续**。
- **原理**：复合索引在 B+ 树里是按 `(a,b,c)` **字典序**排的，只有按字典序前缀才能连续定位。
- **范围查询会截断后续列**：`WHERE a=1 AND b>2 AND c=3` → `c` 无法用于索引（`b` 范围后面断了）。

## Part 4 事务 ACID 与隔离级别（🔴 第二重点）

### 4.1 ACID 四性（🔴 必背 + 各自实现手段）
| 特性 | 含义 | 实现手段 |
|---|---|---|
| **原子性 A** | 事务要么全做要么全不做 | **undo log**（回滚） |
| **一致性 C** | 事务前后数据满足约束 | 由 AID + 业务约束保证 |
| **隔离性 I** | 并发事务互不干扰 | **锁 + MVCC** |
| **持久性 D** | 提交后永久生效 | **redo log**（写前日志 WAL，fsync） |

- **WAL（Write-Ahead Logging）**：**先写日志再改数据**。崩溃恢复时：redo log 重放已提交、undo log 回滚未提交。**这是持久性+原子性的核心**。**SQLite 也用 WAL 模式**（你的知识库就靠它保证每日增量写入不丢/不半截）。

### 4.2 四种隔离级别（🔴 必背，脏读例子要能默写）
| 级别 | 脏读 | 不可重复读 | 幻读 | 备注 |
|---|---|---|---|---|
| **读未提交 RU** | ✅ | ✅ | ✅ | 几乎不用 |
| **读已提交 RC** | ❌ | ✅ | ✅ | Oracle/PG 默认；**每条语句重新读最新快照** |
| **可重复读 RR** | ❌ | ❌ | ⚠️标准有/实际 MySQL 基本无 | **MySQL InnoDB 默认**（靠 MVCC+间隙锁） |
| **串行化 S** | ❌ | ❌ | ❌ | 最高隔离，最低并发 |

- **脏读**：读到别的事务**还没提交**的修改（可能回滚）。
- **不可重复读**：同一事务内两次读**同一行**结果不同（别人改了这行并提交）。
- **幻读**：同一事务内两次读**同一条件的结果集**行数变了（别人插入了匹配的新行）。
- **记忆口诀**：隔离级别从低到高，读到的"别人未提交数据"越少、并发越差。

### 4.3 追问
- "MySQL 默认可重复读，那幻读真的没有吗？"→ 靠 **MVCC + 间隙锁/Next-Key Lock** 基本消除快照读幻读；但当前读（`SELECT ... FOR UPDATE`）仍靠锁。（**这是拉开档次的问题，能答出"快照读/当前读 + 间隙锁"就很扎实。**）
- "读已提交每条语句新快照，那同一事务内可能读到不同数据？"→ 是的，RC 允许不可重复读。
- "为什么需要 RC 和 RR 都存在？"→ RR 间隙锁影响并发（锁范围大），很多业务用 RC + 唯一索引/乐观锁替代。

## Part 5 MVCC（🔴 第三重点，多版本并发控制）

- **核心思想**：**读不加锁**，每个事务读一个"快照"；写生成新版本，旧版本保留（undo log 链）；读按可见性规则取合适版本 → **读写不互相阻塞**。
- **可见性**：事务读当前"最新已提交版本 + 自己改的版本"，不读其他未提交事务的版本（这正是解决脏读/不可重复读的关键）。
- **实现要素**：`事务 ID` + `undo log 版本链` + `ReadView`（记录活跃事务快照，判断哪个版本可见）。
- **RC vs RR 的 MVCC 差异**：**RC 每次快照读都生成新 ReadView**（所以能读到别人新提交）；**RR 只在第一次快照读生成 ReadView 并复用**（所以可重复读）。
- **当前读 vs 快照读**：
  - **快照读**（普通 SELECT）：读 MVCC 版本，不加锁。
  - **当前读**（`SELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE / INSERT`）：读最新已提交并**加锁**。
- **追问钩子**：
  - "MVCC 怎么解决幻读？"→ 快照读靠 ReadView 看不到新插入；当前读靠间隙锁/Next-Key Lock 锁住间隙阻止插入。
  - "undo log 什么时候能清理？"→ 当没有活跃事务需要旧版本（ReadView 都不再引用）时才能 purge。**（考察 MVCC 理解深度。**）
  - **你的类比**："MVCC 就是给数据行维护多个版本，读操作去挑一个自己看得见的版本，这样读写互不阻塞。"**这个"多版本"直觉讲出来就够了，Agent 的'上下文多版本/快照回滚'同构。**

## Part 6 锁

- **按粒度**：表锁 / 行锁 / 间隙锁 / Next-Key Lock（行+间隙）。
- **按共享性**：**共享锁 S**（读，多个可共存） / **排他锁 X**（写，独占）。
- **意向锁**：表级标记，快速判断"能否加表锁"。
- **乐观锁 vs 悲观锁**：
  - 悲观锁：`SELECT ... FOR UPDATE` 先锁住再改（防并发写，但影响并发）。
  - 乐观锁：`version` 字段 `UPDATE ... SET v=v+1 WHERE id=? AND v=?` 靠版本号冲突检测（无锁，冲突时重试）。
- **死锁与 DB 锁**：多个事务按不同顺序加锁会死锁（见 OS 册）→ **DB 约定按主键/索引顺序加锁避免**；DB 有死锁检测，会回滚代价小的一方让一方重试。

## Part 7 索引失效场景（🔴 实操高频，背这张表）

让索引"用不上"的常见原因（能列 5-6 条就够）：
1. **对索引列做函数/运算**：`WHERE YEAR(create_time)=2026` → 应改**范围**`>= '2026-01-01' AND < '2027-01-01'`。
2. **隐式类型转换**：字符串列 `phone` 用数字查 `WHERE phone=138...` → 索引失效（类型不一致）。
3. **前导模糊匹配**：`LIKE '%abc'`（前有 `%`）→ 索引失效；`LIKE 'abc%'` 才行（**B+ 树字典序前缀可定位**）。
4. **不满足最左前缀**：复合索引跳列。
5. **`OR` 连接非索引列**：`a=1 OR b=2`（b 无索引）→ 可能全表。
6. **`!=` / `NOT IN`**：优化器判断全表扫更快 → 弃索引。
7. **数据分布太散/占比太小**：优化器判断走索引回表不如全表 → 弃索引。
> **原理一句话**：索引失效本质是**B+ 树无法按字典序定位**（函数/类型转换/前模糊改变了比较的对象），或**优化器估算走索引不划算**。

**你的挂钩**：这七条不用死记，但"**为什么 LIKE '%x' 用不上索引？因为 B+ 树只能按前缀字典序定位**"这条原理讲出来，其余都能推。

## Part 8 慢查询与执行计划

- **`EXPLAIN`（执行计划）**：重点看 `type`（访问类型：`ALL` 全表扫最差 → `index/const/ref/range` 越好）、`key`（用了哪个索引）、`rows`（扫多少行）、`Extra`（`Using filesort` / `Using temporary` 提示额外开销）。
- **优化手段**：
  - 加对索引（最常用）。
  - **覆盖索引**（避免回表）。
  - **减少 SELECT \* / 大字段拆分**。
  - **深分页改用"覆盖索引 + 延迟关联"**（`LIMIT 1000000,10` 很慢 → 先用覆盖索引拿主键再回表）。
  - **批量写入**分批提交（省 redo log 刷盘）。
  - **读写分离**（读多场景）。

## Part 9 ★ 全文检索 vs 向量检索（你的杀手锏，一路串到 RAG）

> **这是本册对你最有价值的一节。** 面试官问数据库时，你能从"我会用 SQLite"升级到"**我在全文检索和向量检索之间做过选型**"——这是更高一层的视角，也是 RAG 那一册的地基。

### 9.1 两种检索范式（🔴 核心对比）
| 维度 | **关键词检索（倒排/全文）** | **向量检索（Embedding/ANN）** |
|---|---|---|
| 原理 | 分词 → 建**倒排索引**（词→文档列表）；查时**匹配词** | 文本→**稠密向量**；查时算**余弦/内积相似度**取 TopK |
| 擅长 | **精确词、专有名词、编号、错误码**（"Kinco 0xff3f"） | **语义相似、同义/换词**（"堵转"≈"卡住不动"） |
| 弱项 | **同义/换词召不回** | **精确词、罕见词容易失真**（向量对精确码不敏感） |
| 你的实现 | ★**SQLite FTS5**（倒排+分词） | ★CRG 知识库/向量检索（Embedding） |
| 例子 | 查 "0xff3f"、查 "E42"、查型号 "450/620/770" | 问"纸箱塞不进去怎么办"能召回"负缝隙不可行" |

### 9.2 ★ 你的真实选型故事（面试直接讲，含金量极高）
> "我的四套本地知识库检索，最初用 **SQLite FTS5 全文索引**——因为我的数据里有大量**精确关键词**需求：Kinco/Moons 的**故障码**（`0xff3f`、`0x7320`、`0xff38`）、从站状态、**型号与配置项名**、SKU、箱型尺寸编号（450/620/770 理料台）、人名。这类东西用向量检索反而**失真**（'0xff3f' 这种 token 向量化后没有区分度），用倒排精确匹配又快又准。
>
> 但纯 FTS5 解决不了**语义检索**——我搜'电机卡住不动'，倒排匹配不到原文里的'堵转'。所以后来把**向量检索补进来做语义召回，FTS5 继续负责关键词/精确项**，**两条路混合（hybrid search）**。这也让我理解了 RAG 里为什么要 **Rerank**（粗排召回可能不准，用一个更精细的模型重排），以及为什么'关键词检索和向量检索各有不可替代'。"

**这段话的价值**：它同时证明了你 ① 懂倒排/全文 ② 懂向量/语义 ③ **理解两者 trade-off 并做过混合架构决策**。绝大多数候选人只会说"我用过向量库"。**背下来。**

### 9.3 向量索引与传统索引的关系（🟡 面试可能追问）
- **B+ 树索引**：适合**精确匹配/范围**，是**有序**的（查得准、快，但要精确值）。
- **向量索引（ANN，如 HNSW/IVF）**：**放弃全量精确、放弃顺序**，用**近似最近邻**（分层图/聚类分桶）换**大规模下的速度**。**是"精确+快" vs "近似+更快"在大规模下的 trade-off**。
- **一句话**："B+ 树在有序维度上做精确查找；向量索引放弃了'精确'换'在亿级向量里毫秒级召回 topK'。**关键词检索本质上也是'精确查找'家族的一员，所以它和 B+ 树是近亲，而不是和向量检索对立。**"**（这个串联很聪明，能显著加分。**记下来。**）
- **距离度量**：余弦相似度（看方向，最常用）、内积、欧氏距离（L2）。Embedding 选型/维度/归一化 → 详见 RAG 册。

### 9.4 追问
- "为什么 FTS5 用倒排，向量库用图索引？"→ 倒排是"词→列表"的精确查表；向量是"球面里找最近"，图索引（分层图）能快速剪枝。**一个是"字典查词"，一个是"空间近邻"，索引结构由查询方式决定。**
- "FTS5 的中文分词怎么办？"→ 需用 trigram/自定义分词器或 `unicode61`；中文分词不准是全文检索的经典痛点（这也是为什么工业界常"关键词+向量"混合）。
- "混合检索怎么融合两路结果？"→ **RRF（Reciprocal Rank Fusion）**（按排名倒数加权）或加权分数融合、去重。

## Part 10 连接池与数据库选型

- **连接池（Connection Pool）**：DB 建立连接开销大（TCP+认证），用池复用连接。**必考**：为什么不能每次请求都新建连接（太慢/DB 扛不住）；池大小、连接泄漏排查。**Python 侧 `sqlite3`/SQLAlchemy pool**。
- **数据库选型思路**（面试开放题）：
  - 关系型（MySQL/PG/SQLite）：结构化、事务、强一致。
  - KV（Redis）：缓存、计数器、分布式锁、高频读。
  - 文档（MongoDB）：半结构化、schema 灵活。
  - **向量库（Milvus/Qdrant/PGVector）**：RAG 语义检索。
  - 图数据库（Neo4j）：关系密集分析（**呼应你的 CRG 代码结构图**）。
  - **你的选型**："本地知识库选 SQLite（嵌入式、零运维、够用）；热数据/缓存/任务状态用 Redis 或文件；要语义检索再引向量库——**按需引入，不预先上重型组件**。"

## Part 11 分布式数据库（🟢 P2，知道即可）

## Part 13 面试题库

### 13.1 高频必答
1. 为什么索引用 B+ 树？→ 少磁盘 IO + 扇出大(树矮) + 非叶只存索引 + 叶子链表支持范围。
2. 什么是聚簇索引？二级索引回表？→ 主键索引存整行；二级索引存主键，取非主键列需回表；覆盖索引免回表。
3. 什么是事务 ACID？→ 原子(undo)/一致/隔离(锁+MVCC)/持久(redo+WAL)。
4. 四种隔离级别？脏读/不可重复读/幻读分别是什么？→ 见 Part 4.2 表；MySQL 默认可重复读。
5. MVCC 原理？RC vs RR 差别？→ 多版本+ReadView；RC 每次新 ReadView，RR 复用。
6. 索引失效有哪些场景？→ 函数/运算/隐式转换/前模糊/不最左/OR/!=/分布太散。
7. 什么是覆盖索引？→ 二级索引已含查询列，免回表。
8. SQL 优化怎么做？→ EXPLAIN(type/key/rows)+覆盖索引+避免 SELECT*+深分页延迟关联+读写分离。

### 13.2 深挖
- MySQL 可重复读真的没幻读吗？→ 快照读靠 MVCC，当前读靠间隙/Next-Key Lock。
- MVCC 怎么解决幻读？undo log 版本链 + ReadView 不可见新插入；当前读加间隙锁。
- undo log 什么时候能删？→ 无活跃 ReadView 引用该版本。
- 覆盖索引为何更快？→ 在二级索引就定位到所需列，不回聚簇（少随机 IO）。
- 为什么 HTTP 什么都能干但数据库要 ACID？→ 事务是"把多个操作绑成一个可回滚的原子单元"。

### 13.3 结合项目（用 Part 9.2/12 的话术）
- "你数据库怎么选型的？"→ SQLite 嵌入式够用 + 清楚边界（Part 12）。
- "全文检索和向量检索你怎么选？"→ 讲 Part 9.2 的故障码 vs 语义混合故事。
- "你怎么保证四库数据一致/可追溯？"→ 增量同步 + 事务/批次可追溯 + 四源交叉印证。
