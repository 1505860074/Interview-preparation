## Part 1 进程与线程

### 1.1 进程 vs 线程（🔴 最高频，必须能默画地址空间图）

**本质区别不是"轻不轻"，而是"有没有独立的资源分配单位"。**

| 维度 | 进程 | 线程 |
|---|---|---|
| 资源 | **独立**的地址空间（虚拟内存）、文件描述符表、信号处理、cwd | **共享**所属进程的地址空间、fd 表、cwd |
| 私有数据 | 全部私有 | 只有 **栈、寄存器、程序计数器、TLS（线程局部存储）** |
| 创建/切换成本 | 高（建页表、拷贝/共享地址空间） | 低（换一组寄存器 + 栈） |
| 通信 | 需 IPC（管道/共享内存/消息队列/socket） | 直接读写共享内存，**但需同步** |
| 崩溃影响 | 只崩自己 | **默认整个进程崩**（段错误信号是进程级的） |
| 隔离性 | 强（安全边界） | 弱（一处越界全崩） |

**进程地址空间布局（必默画，Linux x86-64，自高地址到低地址）**：
```
高地址 ┌────────────────────┐
       │   栈 (stack)       │  ← 向下增长；局部变量、函数返回地址
       │   ↓                │
       │   (空隙)            │
       │   ↑                │
       │   堆 (heap)        │  ← malloc/new，向上增长
       ├────────────────────┤
       │   BSS (未初始化)    │  ← 全零，静态变量
       │   DATA (已初始化)   │  ← 静态/全局已初始化变量
       │   TEXT (代码)       │  ← 只读 + 可执行
低地址 └────────────────────┘
       [mmap 区：动态链接库、文件映射]  ← 常在高地址或堆附近
```
> 追问钩子：**栈为什么默认只有 8MB、堆却能到几十 G？** → 栈不设 guard page 的惰性分配成本；栈溢出是"越界踩到未映射页"→ SIGSEGV，比递归无终止更早暴露；把栈调大要 ulimit -s，因为栈在 mm 区域，**用 mmap 匿名映射扩展**。

### 1.2 进程状态与切换（🟡 要能讲清"什么时候会切换"）

- **五状态**：新建 → 就绪 → 运行 → 阻塞 → 终止。
- **就绪↔运行**：被 CPU 调度（时间片到、被抢占、优先级更高者就绪）。
- **运行→阻塞**：主动让出（read 卡住、等待锁、sleep、yield）。
- **关键认知**：**阻塞态不能直接到运行态**，必须先回就绪态排队（这是很多"调度"题坑点）。
- **切换代价**：切线程需保存/恢复寄存器上下文 + 刷 TLB（页表基址寄存器）→ 慢。**这是"进程比线程慢"的真实原因，也是无锁/协程优化的出发点。**
- **fork 的写时复制 COW**：fork 时**不真拷贝**父进程内存，只把页标记为只读+共享；任一方写入时才真正复制该页（触发缺页异常）。**这是你答"为什么 fork 后父子互不影响"的标准答案，也是 COW 语义的来源。**

### 1.3 协程：Python/Go 面试必问（🔴 Agent 岗高频）

**一句话**：协程 = **用户态可切换的执行流**，切换不涉及内核态、不刷 TLB，所以比线程切换快。

- **有栈协程**（goroutine、Kotlin）：每个协程有自己的栈（可增长），切换要换栈 → 接近线程但仍在用户态。
- **无栈协程**（C++20 coroutine、Python 生成器）：不切栈，靠编译器/解释器保存状态（状态机），最快但不能像线程那样调任意阻塞 API。
- **Python asyncio**：
  ```python
  async def main():
      r = await asyncio.gather(fetch(url) for url in urls)  # 并发非并行
  asyncio.run(main())
  ```
  - 单线程 event loop，**靠协作式调度**：只在 `await`（IO 完成后）才让出。CPU 密集段不会自动让出 → 要 `run_in_executor` 丢线程池。
  - **类比钩子**：asyncio 单线程 = 你的"单核跑 FSM 状态机"，多个 IO 任务轮流让出；不是真并行。
- **必须诚实说的边界（追问第三层会到）**：协程切换虽快，但**不是零成本**——有栈协程要换栈，无栈的 await 也要构造/保存状态；且协程不能绕开阻塞调用（协程里调 `time.sleep` 会卡死整个 loop）。这也解释了为什么大厂高性能 Python 服务（如 vLLM 后端）会用多线程 + 多进程混合。

### 1.4 面试官最爱的追问链（提前备好）
- "进程 vs 线程？"→ 独立地址空间 vs 共享
- "那 Go 的 goroutine 是线程吗？"→ 不是，是用户态有栈协程，多个 goroutine 复用少量 OS 线程（M:N 调度）。
- "协程一定比线程快吗？"→ **不一定**：协程切换省了"切内核上下文"，但如果协程做的是重 CPU/重系统调用，协程本身也帮不上忙；且有栈协程换栈也有成本。真正快的是"避免不必要的线程 + 异步 IO"。
- "单核上并发和并行有区别吗？"→ 并发=逻辑上同时推进（切换），并行=物理上同时执行；单核只能并发。

## Part 2 进程间通信 IPC

### 2.1 五种经典 IPC（🔴 会问区别与优劣）

| 方式 | 跨进程 | 特点/适用 |
|---|---|---|
| **管道 Pipe** | 只能**父子/亲缘** | 半双工，内核缓冲（64KB），一个方向；`ls \| wc` 用它 |
| **命名管道 FIFO** | 任意亲缘无关进程 | 有文件名，全双工可多写多读 |
| **消息队列 MQ** | 任意 | 内核维护、有优先级、带 ack 语义的独立对象 |
| **共享内存 Shm** | 任意 | **最快**（无拷贝），但**必须自己做同步**（配信号量/锁） |
| **信号量 Semaphore** | — | 同步原语（P/V），配共享内存；也可做计数锁 |
| **信号 Signal** | 任意 | 异步通知，携带信息少，常用于超时/优雅退出 |
| **Socket** | 任意 | 通用，可跨机器；★你的上位机 5051/5052 就是它 |

**优劣一句话**：**要快选共享内存（自己加锁），要简单选管道/socket，要可靠异步选消息队列。**

### 2.2 你的 IPC 实操（★面试可讲的"真活过"细节）
- **匿名管道**：`deploy.sh` 里 `find ... | xargs`；`curl | tar` 等流式处理（避免落临时文件）。
- **信号**：Bash 脚本 `trap cleanup EXIT` 监听退出/信号做清理——**这就是 SIGINT/SIGTERM 的实际应用**（详见 Part 8）。
- **Socket 自研协议**：上位机 `py_box_aligner` 用 TCP 5052 收 48 字节 `BoxAlignerFdbInfo`、5051 监听每帧 8000 字节（20 通道 × 100 点）。**你自己踩过"字节序 + struct packing"**——这正是网络那册的伏笔。
- **进程管理**：`systemd` 管 `DRNile.service`，`journalctl` 跟踪 crash & restart；`SSH` 部署脚本拉起服务——远程进程 + 守护是后端岗高频场景。

## Part 3 死锁（🔴 高频，四个条件必背，你还有工程解法）

### 3.1 死锁四条件（互相独立，同时满足才死锁）
1. **互斥**：资源同时只能被一个进程/线程占用。
2. **占有并等待**：持有资源 A 的同时，等待资源 B。
3. **不可剥夺**：不能强行抢走别人已占的资源。
4. **循环等待**：存在环形等待链（P1 等 P2 持有的、P2 等 P1 持有的）。

**破坏任一条即可预防**（背这四个"破坏法"）：
- 破坏互斥：尽量无锁/原子操作。
- 破坏占有并等待：**一次性申请所有资源**（或申请失败就全部释放）。
- 破坏不可剥夺：申请失败时**主动释放已占资源**。
- 破坏循环等待：**给资源全局定序**（如按地址/ID 从小到大申请）——**这是最常用的工程解法，数据库死锁解决就是按主键/索引顺序加锁。**

### 3.2 真实排查与解法（★你的工程 hook）
- **现场症状**：`DRNile.service` 反复 crash & restart、线程卡住不响应。
- **检测**：`top`/`htop` 看线程是否长期 100% CPU（自旋锁）或 0%（阻塞）；`py-spy`（Python）/`gdb -p <pid> thread apply all bt`（C++）打印所有线程栈，看是否互相等。
- **工程解法对应**：
  - **定序加锁**（破坏循环等待）：你的 EtherCAT 从站访问/多轴运动规划若多锁，**按从站索引顺序申请 PDO 锁**。
  - **一次性申请**（破坏占有并等待）：`std::lock` / `scoped_lock` 一次性拿多把锁，**C++ 推荐 `std::scoped_lock`，它内部用死锁避免算法，不需要你手动定序**。
  - **超时释放**（破坏不可剥夺）：`try_lock_for` 带超时。
  - **消息驱动替代锁**：多轴联动改成"单线程按消息队列消费状态"，天然无锁（**你 FSM 状态机就是消息驱动的思路——这是很高级的答法，能讲出来很加分**）。

### 3.3 追问链
- "死锁 vs 活锁 vs 饥饿？"→ 死锁=都不动；活锁=都在动但都没进展（如互相礼让）；饥饿=某方一直拿不到资源（优先级反转是典型）。
- "怎么排查死锁？"→ 线程栈 dump → 找互相等待的资源 → `pstack`/`gdb`/`py-spy`；生产上先加超时/看门狗。
- "单线程会有死锁吗？"→ 会（自己等自己，如不可重入锁重复加）。

## Part 4 内存管理（🔴 核心，含虚拟内存）

### 4.1 为什么要有虚拟内存（1.1.1.1 四层价值）
1. **进程隔离**：每个进程独立地址空间，一个进程崩/改野不污染别的（安全边界）。
2. **地址空间统一**：每个进程都从 0 开始编址，编译时不用关心实际物理位置。
3. **内存超额分配（overcommit）**：物理内存不够时可换页到磁盘（swap），**逻辑上"内存无限"**。
4. **共享库/共享内存**：多个进程映射同一份物理页（页表指向同一帧）。

### 4.2 分页：虚拟内存的底层（🔴 必懂）
- **页（page）**：虚拟地址空间切成固定大小（Linux 4KB，大内存/大页用 2MB/1GB 的 huge page）。
- **页表**：虚拟页号 → 物理页框号 的映射表，由 MMU 硬件查。
- **TLB**：页表的高频缓存，存最近用过的映射，**避免每次访存都查页表**。
- **缺页异常（Page Fault）**：访问的页不在物理内存（不在 TLB/未映射/被换出）→ CPU 陷入内核，由 OS 载入：命中磁盘 swap 或文件映射，或判定非法访问（→ SIGSEGV）。**"缺页"不一定是错误，很多正常访问也会缺页。**
- **写时复制 COW**：见 Part 1.2 的 fork。
- **大页（huge page）**：减少页表项数量（2MB 页 = 4KB 的 512 倍），减少 TLB miss，**这就是为什么数据库/推理引擎会配 huge page**（呼应你后续看 PagedAttention 时的"页"概念——**OS 分页 vs 推理分页是同一个隐喻，面试可以串起来讲，是很漂亮的串联**）。

### 4.3 物理内存与 OOM
- **物理内存 ↔ 虚拟内存**：虚拟地址不等于占着的物理内存；**只有"被访问过（触碰过）"的页才真正占物理内存**。
- **OOM Killer**：物理内存耗尽时，Linux 按"oom_score"杀最"不必要"的进程。**面试加分点**：线上服务被 OOM 杀掉时，要调 `oom_score_adj`、监控 RSS/容器 limit 触发的 cgroup OOM。
- **swap 的代价**：换页慢（磁盘 IO），所以服务器常关 swap（`vm.swappiness=0`）宁可 OOM 也不要磁盘换页拖死延迟。

### 4.4 C++ 内存（★你主力语言，面试会问）
- **栈**：函数局部变量/返回地址，自动分配释放，**默认 8MB**。
- **堆**：`new`/`malloc` 手动管理，需配对 `delete`/`free`。
- **RAII + 智能指针**：`unique_ptr`（独占）、`shared_ptr`（共享，**带引用计数，注意循环引用泄漏**）、`weak_ptr`（打破循环）。**面试标准答法：优先用 RAII + 智能指针替代裸 `new`。
- **malloc vs new**：new 额外调用**构造函数**、可重载、返回特定类型指针；malloc 返回 `void*` 需强转、只管内存不管构造。
- **内存对齐**：结构体按最大成员对齐（`alignof`），padding 占空间；**你修过 struct packing 错误**（C++/Python socket 通信时结构体对齐不一致导致解析错乱）——**这是"对齐"最好的实战例子，讲这个能立刻区别于背书的人**。

## Part 5 内存泄漏定位（★你的实战区，讲出来最有分量）

### 5.1 三种"内存问题"先分清
- **内存溢出（OOM）**：申请超上限，抛异常/失败——申请量本身太大（逻辑 bug）。
- **内存泄漏（Leak）**：申请了不再释放，随时间累积涨——**你的专项测试就是这类**。
- **内存碎片（Fragmentation）**：总量够但没连续大块可用（申请大小不一导致碎片）——`malloc` arena 机制、glibc 的 jemalloc/tcmalloc 就是治这个。

### 5.2 泄漏检测流程（★直接照你的经历组织，讲成方法论）
你做过"显存泄露专项测试（max 1.13.1pre9）"。面试时这样讲，显专业：
1. **先复现 & 定量**：跑长周期压测（如多轮周度稳定性/节拍压测），周期性采样进程内存（`top`/`ps` 的 RSS/VSZ；你的项目就是"多轮周度压测"看曲线是否单调上升）。
2. **区分泄漏 vs 缓存 vs 正常波动**：内存不涨但稳定→不是泄漏；缓慢单调上升→疑似泄漏；阶梯上升→可能每次处理任务后未释放或未复用池。
3. **定位**：
   - **C++**：编译带 sanitizer（`AddressSanitizer`/`LeakSanitizer`）跑，报出未释放分配点；`valgrind` 慢但准。
   - **Python**：`tracemalloc` 快照对比、`objgraph` 找引用泄漏；GC 只回收**循环引用**，被外部引用的泄漏它救不了（**这是 Python 内存泄漏最常见原因，讲出来很专业**）。
   - **GPU/显存**（你的场景）：`nvidia-smi` 看显存曲线；显存比内存更易泄漏（驱动缓存、显存池不归还 OS），要用专门 profiler。
4. **修复与验证**：改完重跑同压测，确认内存曲线走平。

> **得分点**：不只是"我测过显存泄露"，而是**"我知道怎么定量复现、用什么工具定位、怎么验证修复"**——这是资深测试工程师的思维方式。

### 5.3 常见泄漏原因（背这些，答题有条理）
- 未释放动态分配（`new` 无 `delete` / `malloc` 无 `free`）。
- 容器/集合只增不减（缓存无淘汰 → 内存"泄漏式"增长）。
- **全局/static 对象持有指针**，进程内永不释放（等价于永久泄漏）。
- 引用计数环（C++ `shared_ptr` 循环 / Python 容器互引）。
- 事件/回调未反注册（`signal`/observer 未 remove → 被回调方持有引用无法回收）。
- 文件/socket 未 close（fd 泄漏，不算内存但同类问题）。

## Part 6 IO 模型（🔴 select/poll/epoll 必考，Agent 服务端同理）

### 6.1 五种 IO 模型（能默画表就够）
| 模型 | 谁等 | 是否利用多核 | 编程复杂度 |
|---|---|---|---|
| **阻塞 IO** | 调用线程等 | 单线程浪费多核 | 最低 |
| **非阻塞 IO** | 立即返回，轮询 | 轮询浪费 CPU | 中 |
| **IO 多路复用** | select/poll/epoll 等就绪 | 单线程事件循环 | 中 |
| **信号驱动 IO** | SIGIO 通知 | — | 高 |
| **异步 IO** | 内核全权做，完通知 | 最高效 | 最高 |

### 6.2 select / poll / epoll（🔴 三者对比是必考题）
- **select**：fd 有数量限制（`FD_SETSIZE` 通常 1024）；每次调用要把 fd 集合**从用户态全量拷贝到内核**再全量扫；**O(n)**；跨平台。
- **poll**：链表存储，无 fd 数量限制；但**仍要全量拷贝 + 全量扫**，**O(n)**。
- **epoll**（Linux 专有）：三个系统调用分工——
  - `epoll_create`/`epoll_ctl`：**注册/修改 fd 关注的事件**（只需增删，不用每次传全量）；
  - `epoll_wait`：**内核把就绪的 fd 主动放入就绪链表**，只返回就绪的 → **O(1) 的就绪处理**；就绪链表配合红黑树管 fd。
  - **优点总结**：不重复拷贝全量、只关心就绪的、支持海量连接（C10K/C100K）。**缺点**：Linux 专有；非阻塞 fd 才能真正用其并发优势。
- **水平触发 LT vs 边缘触发 ET**（进阶）：
  - **LT**：只要 fd 就绪就一直通知（可能重复通知同一个 fd）。
  - **ET**：只在状态**变化**时通知一次 → 性能高，但**必须一次读到 EAGAIN 否则可能丢事件**。
- **类比钩子**：epoll 事件循环 = 你"上位机监听 5051 端口收实时数据"的服务端模型；也是 Nginx 单进程扛 C10K 的底层。**你的 5051 监听口收 8000B 实时帧，和 epoll 监听连接读数据同构。**

### 6.3 面试追问
- "epoll 为什么比 select 快？"→ 不全量拷贝+只返就绪+O(1)（三点说清即可）。
- "ET 模式要注意什么？"→ 必须读到 `EAGAIN`，否则剩余数据可能不再通知（丢事件）。
- "协程 + IO 多路复用什么关系？"→ 底层用 epoll 等 IO 就绪，上层用协程简化业务并发（**asyncio 就是 epoll + 协程**）。

## Part 7 文件系统

### 7.1 核心概念（🟡 会问概念）
- **inode**：文件元信息（大小/权限/时间/块位置），**数据与元信息分离**。
- **硬链接 vs 软链接（符号链接）**：
  - 硬链接：多个目录项指向**同一 inode**，删一个不影响另一个；**不能跨文件系统/不能指向目录**。
  - 软链接：一个文件内容是**另一条路径**，可跨盘、可指向目录、目标删了就成"断链"（`ln -s`）。
- **块缓存 / 页缓存（Page Cache）**：读的文件先缓存在内存（你的"只喂最小上下文省 token"之外，OS 层同理：重复读走缓存，**这就是 IO 快的原因**）；`fsync` 才真正落盘（对应数据库"写前日志/持久性"）。
- **脏页与写回**：改了的内存页标脏，后台批量落盘 → 断电可能丢（所以数据库要 WAL）。

### 7.2 你的挂钩
- 配置/固件/日志都是文件：`box_aligner_config.yaml`、`box_aligner_node.*.log`、固件 `.bin`。
- **写时复制、原子替换、备份脚本 `system-backup`** → 讲"文件系统 + 原子操作"时直接挂钩：脚本备份为何先写临时文件再 `mv`（`mv` 同文件系统内是 rename 原子操作，避免半截文件）。
- 磁盘/分区/挂载点概念基础即可，你不需要深入文件系统实现。

## Part 8 信号与 Bash 的 hook 关系

**信号 = 进程间异步通知**（相当于轻量事件）。
- 常见：`SIGINT`(Ctrl-C, 2)、`SIGTERM`(kill 默认, 15)、`SIGKILL`(9, 不可捕获)、`SIGSTOP`/`SIGCONT`。
- **处理**：`signal()`/`sigaction()` 注册处理函数；默认动作（终止/忽略/暂停）。
- **`SIGKILL`/`SIGSTOP` 不可捕获**（内核直杀/暂停）——进程必须能靠这些"必然生效"的信号被收掉。

**★ 你的 Bash 钩子（讲这个把 OS 原理和你的日常串起来）**：
```bash
#!/usr/bin/env bash
set -euo pipefail          # 严格模式：出错即停
tmpdir="$(mktemp -d)"
cleanup() { rm -rf "$tmpdir"; }   # 清理函数
trap cleanup EXIT           # 无论正常退出/报错/被 SIGINT(SIGTERM)，都触发 cleanup
```
- **`trap cleanup EXIT` 就是一个"信号处理器"**：脚本被 Ctrl-C(SIGINT) 或 `kill`(SIGTERM) 时，bash 会执行注册的清理再退出 → **临时文件不残留**。这就是你录屏转换脚本"退出时清理临时 webm"背后的 OS 原理。
- **追问钩子**："为什么脚本要在 trap 里清理，而不依赖正常结束？"→ 因为异常退出/信号中断/管道上游断开都不会走到正常收尾，必须注册退出钩子保证清理（对应 C++ 的 RAII/atexit/析构函数——**同一个思想：把清理绑定到"生命周期结束"这个事件上，而不是绑到"流程走完"**）。这个类比讲出来非常漂亮，**强烈建议练熟**。

## Part 9 线程安全与并发原语

### 9.1 三个典型问题（🔴 会问区别）
- **临界区/竞态条件**：多线程改同一共享数据，结果取决于执行时序。
- **互斥锁 Mutex**：同一时刻只一个进临界区（会切换/阻塞）。
- **自旋锁 Spinlock**：抢不到就自旋等（忙等，适合"临界区极短 + 多核"；**单核上自旋会白烧 CPU，反而不如互斥锁**——这是经典陷阱）。
- **读写锁**：读多写少时，多个读并发、独占写。
- **原子操作 / 无锁（CAS）**：不靠锁，靠 CPU 原子指令（`compare-and-swap`）实现无锁队列。**优点无阻塞，缺点 ABA 问题**（需 CAS 或版本号）。
- **信号量 Semaphore**：计数器，控制同时访问资源的数量（也用于进程间）。

### 9.2 内存可见性与重排序（🟡 进阶，回答"那为什么加锁还出错"）
- **可见性**：一个线程改了内存，另一个线程可能还看着缓存的旧值 → 需**内存屏障/原子操作**保证可见。
- **重排序**：编译器/CPU 可能打乱指令顺序 → `volatile`（防重排序但不保证原子性）、**原子变量/CAS**（既原子又可见）。
- **面试标准句**："锁保证了互斥和（配合实现）内存屏障，光靠程序顺序可能因重排序和缓存可见性出问题。"

### 9.3 你的挂钩
- 多轴伺服控制同时更新实时数据 → 需要线程安全（锁/原子）保证 RT 数据一致。
- 你的 FSM 状态机**单线程消费状态** → 天然避免竞态（用**消息/队列传递**而非共享变量+锁）——**这是很工程化的"用架构规避并发问题"思路，是加分项。**

## Part 10 实时系统（Xenomai 专用加分区）

> 这是你 C++ 控制系统背景的**稀缺优势**。绝大多数候选人没有实时系统背景，讲出来很亮眼。

- **硬实时 vs 软实时**：
  - 硬实时：错过截止期 = 系统失败（工业控制、航空；你的 EtherCAT 伺服）。
  - 软实时：错过只是质量下降（音视频；多 Agent 服务）。
- **实时关键**：
  - **确定性**：worst-case 延迟可界定（不是平均快，是**最坏情况不超时**）。
  - **优先级抢占**：高优先级任务可抢占低优先级（你的理料台运动控制优先级高于 UI）。
  - **抖动（jitter）**：延迟的波动，工业控制要求抖动小。
- **普通 Linux 不适合硬实时的原因**：分时调度 + 不可抢占内核态（IO/内存操作会触发优先级反转/延迟不可控）。
- **Xenomai**：把实时内核跑在 **PREEMPT_RT** Linux 之上（或后来的 **PREEMPT_RT 主线**），用 `rtapi_*` 实时 API（`rt_task`, `rt_sem`），提供可测量的硬实时；非实时部分跑在普通内核（**双内核/分离架构**）。
- **EtherCAT 周期**：实时任务的周期（如 1ms/2ms PDO 周期）与抖动直接决定伺服指令下发准时性——**周期抖动 = 电机跟随误差**。**"EtherCAT PDO 周期与实时性能的关系"是你的实打实的技术点**（见《工作内容分类汇总》1.8）。

**面试话术（把这块讲成"我理解实时与 Agent 的共性"）**：
> "我做过 Xenomai 实时控制，深知**实时系统的核心是确定性而非平均性能**——EtherCAT 周期抖动直接等于伺服跟随误差。这和 Agent 系统的 SLO 是同一种思维：不是'平均多快'，而是'最坏情况能不能兜住'。我做 Agent 工具调用时也因此特别关注超时、降级和 P99 延迟，而不是只看平均耗时。"

**（把最稀缺的经历迁移到最多被问的方向 = 极高性价比的答法，务必练熟。）**
