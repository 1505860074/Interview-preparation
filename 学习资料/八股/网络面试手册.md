## Part 1 TCP 协议与三次握手

### 1.1 三次握手（🔴 必须能默画四步，含 seq/ack）

```
   Client                                Server
     |                                     |
     | ---- SYN, seq=x -------------------> |   ① 客户端请求建立
     |                                     |
     | <--- SYN+ACK, seq=y, ack=x+1 ------ |   ② 服务端确认+反向请求
     |                                     |
     | ---- ACK, ack=y+1 ----------------> |   ③ 客户端最终确认
     |         (连接建立，开始传数据)         |
```
- **为什么必须是三次（不是两次）？** → 核心是**防止已失效的连接请求报文突然又到达服务端**，服务端误以为要建立连接而白等资源（经典的"三次握手是为了双方都确认收发能力 + 避免历史报文误解"）。
- **为什么要 4 个参数（seq/ack）？** → seq=本端这次发送的第一个字节序号，ack=我已收到你到哪个字节。**TCP 是字节流，全靠 seq/ack 定位"到第几个字节"，这是后面理解粘包、丢包重传的基础。**

### 1.2 四次挥手（🔴 必须懂 TIME_WAIT）

```
   Client                                Server
     | ---- FIN -------------------> |   ① 客户端没数据要发，请求关闭
     | <--- ACK ------------------- |   ② 服务端确认，客户端进入 FIN_WAIT_2
     | <--- FIN ------------------- |   ③ 服务端也发完了，请求关闭
     | ---- ACK ------------------- |   ④ 客户端最终确认 → TIME_WAIT
```
- **为什么挥手要 4 次、握手 3 次？** → 因为 **TCP 是全双工**，两边关闭独立。关闭时服务端可能还有数据要发，所以"我这边没数据了(ACK)"和"我也要关了(FIN)"要分开发 → 4 次。握手时服务端能把自己的能力合并进 SYN+ACK（顺带发）→ 3 次。
- **TIME_WAIT 等 2MSL 是干嘛的（高频追问）？** → 两个作用：
  1. **保证最后一个 ACK 能到达服务端**：若 ACK 丢了，服务端会重发 FIN，客户端需还在 TIME_WAIT 才能重发 ACK 回应。
  2. **让本次连接的"迷途报文"在网络中消散**，避免污染新的同四元组连接。
  - `2MSL`=两个最大段生存时间（MSL 约 30s-2min），故 TIME_WAIT 通常 1-4 分钟。**"TIME_WAIT 太多"是后端高频问题** → 后果见下。
- **主动关闭方才有 TIME_WAIT**（没数据要发、先关的那一方）。

### 1.3 TCP 状态机（🟡 至少能说出 11 个状态和主流程）

`CLOSED → SYN_SENT → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED`（客户端主动关闭）
`CLOSED → LISTEN → SYN_RCVD → ESTABLISHED / CLOSE_WAIT → LAST_ACK → CLOSED`（服务端）

**高频排查关键词**：
- **`CLOSE_WAIT` 堆积** = **本端收到对端 FIN 但本端没关** → 本端应用忘记 `close()`（**代码 bug**，后端经典问题）。
- **`TIME_WAIT` 堆积** = 本端是大量短连接的**主动关闭方** → 调 `tcp_tw_reuse`、用**长连接/连接池**（**这直接连到 Agent/后端的"用长连接降延迟"实践**）。
- **`SYN_RCVD` 堆积** = 半连接队列打满 → 可能是 SYN Flood（要 SYN Cookies）或真的连接量大。

> **★ 你的挂钩**：`systemd` 里 SSH 部署、上位机 TCP 长连接保活，抓包分析 EtherCAT 现场从站掉线——**现场"从站偶发无响应"时用 EtherCAT 诊断工具 + 报文分析，就是这套知识在工业现场的直接应用。**

### 1.4 追问链
- "为什么不是四次握手？"→ 服务端把"确认"和"反向请求"合并成 SYN+ACK（3 次）。
- "TIME_WAIT 有什么副作用？"→ 占端口/内存，高并发短连接把它撑爆；解法是长连接+复用。
- "CLOSE_WAIT 多了说明什么？"→ 本端代码没关连接，代码 bug。

## Part 2 可靠传输：滑动窗口与拥塞控制

### 2.1 滑动窗口（🟡 必背原理）
- 发送方不逐个等 ACK，而是维持一个**发送窗口**，窗口内可以连续发多个报文，用 `seq/ack` 标记累积确认。
- **累积 ACK**：收到第 N 字节前所有字节 = 一次 ACK 全部确认（高效）。
- 窗口前移 = 可靠 + 流水线（既不丢又不卡）。

### 2.2 拥塞控制（🔴 经典八股，四个算法要能背）
- **拥塞窗口 cwnd**：发送方根据网络拥塞程度自适应的"还能发多少"（区别于接收窗口 rwnd，取决于对方缓冲）。**实际发送量 = min(cwnd, rwnd)。**
- **四个阶段**：
  1. **慢启动**：cwnd 指数增长（1→2→4→8…），快速探测网络容量。
  2. **拥塞避免**：达到阈值（ssthresh）后线性增长（+1），试探极限。
  3. **快重传**：收到 3 个重复 ACK（说明中间丢了）→ 立即重传，不等超时。
  4. **快恢复**：cwnd 减半（ssthresh），继续线性增长。
- **超时重传 vs 快重传**：超时（RTO）后 cwnd 归 1 重新慢启动（代价大）；快重传（3 重复 ACK）只减半，恢复快。
- **追问**："拥塞控制和时间片是同一概念吗？"→ 都是"不能抢太多资源"，但拥塞控制管网络、报文级；时间片管 CPU、进程级。

## Part 3 粘包/拆包（★你的最强实操，必须讲到能画图）

### 3.1 什么是粘包/拆包（🔴 必背概念）
- **TCP 是字节流**，不保留"消息边界"（不像 UDP 一个报文一个消息）。发送端多次 `send` 的数据，接收端可能一次性收到（**粘包**）；一次 `send` 的数据可能被拆成多次（**拆包**）。
- **根本原因**：TCP 只保证字节序可靠传输，**不保证"send 一次 = recv 一次"**（Nagle 算法、缓冲区、拥塞都会影响）。

### 3.2 三种解决方案（🔴 会问怎么解）
1. **定长报文**：每条消息固定长度（如你 5051 每帧固定 8000B），接收端按长度切。**最简单，但浪费。**
2. **分隔符**：消息结尾加特殊分隔符（如 `\n`/magic byte），读到分隔符才算一条。**简单，有分隔符被误入内容的风险。**
3. **长度字段（最常用/最规范）**：**报文头里带"后续 body 长度"**，先读头拿到长度，再按长度读 body。→ 你的协议就是这个思路。

### 3.3 ★ 你的协议实战（面试直接讲这段，含金量极高）
**上位机通信架构**：
- **TCP 5052 控制口**：发 **5×uint16** 指令，接收 **48 字节** 固定长度反馈结构（`BoxAlignerFdbInfo`）。
- **TCP 5051 监听口**：C++ 固件每帧推 **8000 字节**实时数据（**20 通道 × 100 点** RT 轨迹），对应 `g_traj` 各通道。

**你能讲的点**：
- 固定长度帧（8000B / 48B）+ 帧头含长度/校验 → 天然防粘包（用长度字段+定长）。
- **struct packing / 字节序 / 内存对齐**：C++ 结构体和 Python 解析时，**对齐和大小端必须一致**，否则解析出垃圾数据（你修过这个 bug）。**这是"应用层如何定义自己的报文协议"的教科书级实操，面试极少有人能讲到"我自定义过跨语言二进制协议并处理了对齐/字节序"。**
- RT 数据高频推送 + 控制指令低频 → **一条连接做控制、一条做数据流**，是典型的"读写分离避免相互阻塞"设计。

> **强烈建议准备的话术**：
> "我们的上位机和 C++ 固件之间是自研的 TCP 二进制协议：控制口发 5 个 uint16 指令、收固定 48 字节反馈；另一个监听口每帧推 8000 字节实时轨迹。因为 TCP 是字节流会粘包拆包，我们的协议是定长+帧头带长度+校验，接收端先读头再按长度读 body。另外 C++ 和 Python 两侧结构体的内存对齐/字节序必须严格一致，我踩过 packing 不一致导致解析错位的问题。"

这段话直接把"TCP 粘包 + 字节序 + 内存对齐 + 应用层协议设计"四考点一次串起来，**背下来，面试时按需展开。**

## Part 4 UDP 与 QUIC 的地基

### 4.1 UDP（🟢 知道对比即可）
- 无连接、不可靠、无序、开销小（8 字节头）、**支持一对多/广播**、**无拥塞控制**（UDP 不拥塞控制，靠应用层自己管）。
- 用在哪：DNS、实时音视频、QUIC 的基础、**心跳/Ping（你现场 ping 从站 IP 192.168.4.200）**。

### 4.2 为什么 QUIC 基于 UDP（🟡 面试可能问）
- 若 QUIC 基于 TCP，**TCP 的队头阻塞 + 握手需多次 RTT** 会拖累 HTTPS；基于 UDP 则可在 **UDP 之上自实现可靠传输**，把拥塞控制/加密/HTTP 解析放用户态，**内核升级不用改 QUIC**，还能**多路复用**。
- **结论**：QUIC 用 UDP 承载是为了**在用户态掌控传输层，摆脱 TCP 的队头阻塞并实现 1-RTT/0-RTT 握手**。

## Part 5 Socket 编程与字节序（★你有实操，讲实操）

### 5.1 socket 生命周期（🟢 会话流程）
`socket()` → `bind()`（服务端，绑 IP+端口）→ `listen()`（服务端，监听 backlog）→ `accept()`（返回已连接 fd）→ `recv()/send()`（读/写）→ `close()`。
客户端：`socket()` → `connect()` → `send/recv` → `close()`。
- **listen 的 backlog**：半连接/全连接队列长度（Part 1.3 讲过 SYN_RCVD 堆积）。
- **多路/多连接**：单进程 epoll 监听一个端口、accept 多个连接（Agent 服务端模型）。

### 5.2 字节序与对齐（★你的实战，讲这个）
- **网络字节序（大端 network byte order）** 是 TCP/IP 约定；主机内部是小端（x86）。跨平台传输要统一用大端（或显式转换）。
- **结构体对齐**：`#pragma pack` / `__attribute__((packed))` / Python `struct.pack` 要与 C++ 侧一致，否则**内存 padding 差异**导致解析错位。
- **实践**：Python 侧 `struct.pack('5H', ...)` 发指令、`struct.unpack` 解反馈；C++ 侧用对应布局的结构体 + `memcpy`。
- **面试话术钩子**："跨语言传二进制必须处理**大小端 + 结构体对齐/padding**，我实际调通过 C++ 固件和 Python 上位机的自定义协议。"

## Part 6 HTTP 演进（🔴 高频）

### 6.1 HTTP 各版本差异（能默画表就够）

| 版本 | 关键特性 | 痛点解决 |
|---|---|---|
| **HTTP/1.0** | 一请求一连接，Connection 关闭 | 无（连接复用差） |
| **HTTP/1.1** | **持久连接 Keep-Alive**、Host 头、管状管道(pipelining)、分块传输 | 减少握手；**但有队头阻塞 + 队队阻塞** |
| **HTTP/2** | **二进制分帧**、**多路复用**、**HPACK 头压缩**、**Server Push**、流量控制(TCP级) | 解决 HTTP 层的队头阻塞与重复头开销 |
| **HTTP/3** | 基于 **QUIC over UDP**、**0-RTT/1-RTT 握手**、**每流独立流控**、**QPACK** | 解决 **TCP 队头阻塞**（丢一个包停所有流） |

### 6.2 关键点辨析（高频混淆）
- **HTTP/1.1 的问题**：① **队头阻塞**（一个请求慢，后面排队）；② **多连接/域名散乱**（同一域名可能开多连接）；③ **头膨胀**（每次都传全量头）。pipelining 虽想复用但**响应必须按序返回**→ 治不了队头阻塞 → 于是想出**并发开多连接**（雪上加霜）。
- **HTTP/2 多路复用**：一个 TCP 连接上跑多个 Stream，**流之间独立**，一个流慢不阻塞其他流 → 解决 HTTP 层队头阻塞。**但底层还是 TCP**→ **只要一个包丢了，TCP 要重传，后续所有流都等着（TCP 层队头阻塞）**→ 这就是 HTTP/3 换 QUIC 的动机。
- **HTTP/3（QUIC）**：在 UDP 上自实现可靠传输，**丢包只重传丢失的那个流**、每流独立流控 → 真正解决传输层队头阻塞。**它还能把加密和拥塞控制放用户态、内核不用动。**

> **一句话记忆**：**HTTP/1.1→2 解决"HTTP 层队头阻塞"，HTTP/2→3 解决"传输层(TCP)队头阻塞"。**

### 6.3 ★ 你的挂钩
- **飞书每日总结机器人**用飞书 webhook 推送（**HTTP POST + 重试**）。
- **MCP** 协议跑在 HTTP/SSE（或 Streamable HTTP）之上 → 就是 HTTP/1.1 持久连接 + 长连接流式（见 Part 9）。
- **Claude Code headless 流水线**本质也是 HTTP 请求模型 API。

## Part 7 HTTPS / TLS（🔴 高频）

### 7.1 TLS 握手（🟡 能讲流程）
```
Client                                Server
  | ---- ClientHello（支持的版本/密码套件/随机数）---> |
  | <--- ServerHello + 证书 + 随机数 ---------------- |
  | (验证证书链, 用证书公钥解密/协商出对称密钥)        |
  | ---- ClientKeyExchange + ChangeCipherSpec ------->|
  | <=== 之后用对称密钥加密传输 ===>                 |
```
- **混合加密**：非对称加密（RSA/ECDSA）**只用来安全协商出对称密钥**，之后用**对称加密（AES）**传数据——**既安全又快**（这是必考的核心）。
- **证书链**：服务器证书由 CA 签发，客户端验证证书链确保"对方真是它"、**防中间人**。
- **SNI**：在 ClientHello 里带域名，服务端据此选证书（**一个 IP 多个域名**的关键，考察点）。

### 7.2 HTTP vs HTTPS（🟢 一句话 + 追问）
- HTTPS = HTTP + TLS 加密，**防窃听/篡改/中间人**，代价是握手多几个 RTT + 加密开销。
- **HTTP/2 之前，HTTPS 更贵**（TCP 三次 + TLS 握手）；**HTTP/2+ 可以合并握手/连接**（1-RTT/0-RTT）→ **所以现代站点全用 HTTP/2 over TLS**。
- **追问**："为什么早期 HTTP/2 反而用 h2c（明文）？"→ 因为 HTTP/2 收益主要来自多路复用/头压缩，不是加密；用 TLS 会引入握手开销，浏览器初期用明文，后主流为强制 HTTPS。

## Part 8 HTTP/2 与 HTTP/3（QUIC）（🟡 会话机制）

- **HTTP/2 二进制分帧**：把请求/响应拆成二进制 frame 在一个连接上传输，替代 HTTP/1.1 的文本首部行。
- **HPACK 头压缩**：首部表 + Huffman 编码，重复头可被索引 → 减小头体积。
- **多路复用（Multiplexing）**：一个 TCP 连接承载多个并行 Stream（对应你的"控制口 + 数据口"思想：HTTP/2 把这个做进了标准）。
- **Server Push**：服务端主动推送关联资源（**注意：浏览器已弃用，工程上少提**）。
- **流控**：HTTP/2 每个流 + 整个连接都有窗口；**区别于 TCP 只有连接级流控**。
- **QUIC 特性**：加密在传输层强制（无明文 QUIC）、**0-RTT 恢复会话**、连接 ID 支持连接迁移（换网不断连）。
- **流式传输**：HTTP/1.1 用 **chunked Transfer-Encoding**；HTTP/2 用**帧**；本质都是"响应还没完，先把已生成的部分推给客户端"——**这就是大模型流式输出的传输基础**（Part 9）。

## Part 9 长连接 / 轮询 / SSE / WebSocket（★Agent 流式必考）

### 9.1 四种通信方式辨析（🔴 Agent 岗高频，因为流式输出）

| 方式 | 方向 | 特点 | 典型用 |
|---|---|---|---|
| **短轮询** | C→S 反复问 | 服务端不推送，客户端定时问；延迟=轮询间隔、空耗多 | 简单通知 |
| **长轮询** | 服务端挂起直到有数据 | 一次请求等一个响应，有数据才回；连接占用 | 中等实时 |
| **SSE**（Server-Sent Events） | **服务端→客户端单向** | 基于 HTTP，`text/event-stream`，**服务端持续 push**；**自动重连** | **大模型逐 token 输出**（主流） |
| **WebSocket** | 全双工双向 | 独立协议（HTTP Upgrade 握手），**可客户端→服务端**持续推 | 实时协同/IM/双向对话 |

- **SSE vs WebSocket（Agent 场景）**：**大模型流式输出（模型→用户）单向为主 → SSE 够用且轻**（走 HTTP、生态成熟、自动重连）；需要**用户中途打断/双向高频**（如语音实时对话）才用 WebSocket。**Claude / OpenAI 官方流式 API 就是 SSE 风格。**

### 9.2 ★ 与你的 Agent 项目直接挂钩
- **headless Claude Code 每日总结流水线**：本质是**发起一次生成 + 流式接收 token + 落库/发飞书**。
- **MCP 协议**的传输层：早期是 **SSE**、现在是 **Streamable HTTP**（POST + 可选 SSE 响应流）→ **MCP 就是"长连接 + 流式"的协议化体现**（Part 10 的话术里会呼应）。
- **面试话术**：
> "我的每日总结 Agent 走的是流式链路：请求模型时用 SSE 逐 token 接收，边生成边判断，避免等全部生成完再解析；同时把最终结构化结果通过 HTTP POST 推飞书 webhook。长连接上做流式，比轮询延迟低、比等全量响应体验好——这和我理解的 Agent 的工程本质一致：**用流式 + 长连接把'等待模型'的延迟隐藏掉**。"

### 9.3 追问
- "SSE 断了怎么办？"→ 浏览器**自动重连**（`Last-Event-ID` 续传）；但**服务端生成任务不该因连接断而丢** → **任务异步化 + 结果持久化**，靠任务 ID 补拉（**这正是 Agent 任务队列化/幂等的思想**，见系统设计册）。
- "keep-alive 和长连接是一回事吗？"→ 语义相近：keep-alive 指 TCP/HTTP 连接不立刻关以便复用；长连接指客户端-服务端保持一个连接做多次通信。

## Part 10 DNS / CDN / 负载均衡

### 10.1 DNS（🟡 会流程 + 缓存）
- **流程**：客户端 → 递归 DNS 服务器 → 根服务器 → TLD 服务器 → 权威 DNS → 拿到 IP。
- **记录类型**：`A`(IPv4)、`AAAA`(IPv6)、`CNAME`(别名)、`MX`(邮件)、`TXT`(验证/文本)。
- **缓存 + TTL**：各级缓存 + TTL 决定生效时间（**"域名解析慢/改了不生效"= TTL 问题**）。
- **负载均衡**：同一域名多个 A 记录 → DNS 层面轮询/加权/就近（CDN 就近解析）。

### 10.2 CDN（🟢 知道原理）
- 边缘节点缓存静态资源 + 就近访问 → 降低源站压力和延迟。**本质是"把内容放到离用户近的缓存"**（与 Agent 的"就近缓存/上下文缓存"同思想）。
- **追问**："CDN 缓存和浏览器缓存区别？"→ 浏览器=单用户本地；CDN=边缘节点共享缓存。

### 10.3 负载均衡（🟡 会层次，详见系统设计册）
- **四层（LVS/云 LB）**：只到 TCP 转发，性能高，不解析应用协议。
- **七层（Nginx/网关）**：理解 HTTP，按 URL/Header 路由、缓存、限流、负载均衡。
- **长连接场景**：需要**会话保持**（sticky session）或**一致性哈希**，否则重连到不同后端丢状态（**Agent 有状态对话就要这个问题**）。

## Part 11 Cookie / Session / Token / JWT（🟡 会区别，后端高频）

- **Cookie**：浏览器存储 + 每次请求自动带上；受同源/域/路径限制；可设 HttpOnly(防 XSS 读)/Secure/SameSite。
- **Session**：服务端存状态，客户端只拿 SessionID；**有状态、服务器要存**（集群要共享/粘性）。
- **Token/JWT**：服务端无状态，Token 自带信息（JWT = Header.Payload+签名，**签名防篡改但 payload 不加密，别放敏感**）。
- **对比**（高频表）：Session **有状态**、可服务端主动失效；JWT **无状态**、难主动失效（要等过期/黑名单）、体积大（每请求都带）。
- **Agent 场景**："对话是有状态的 → Session 思维；API 调用/高并发 → JWT/Token 思维"。
