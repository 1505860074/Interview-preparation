## 一、Git 基础知识

### 1.1 Git 是什么

#### 先用大白话理解「版本控制」

想象你在玩一款单机游戏。打大 Boss 之前，你会先「存个档」；万一打输了，就读回刚才那个存档重来，而不是从头再玩一遍。**版本控制（Version Control）就是给你写的代码、文档做「存档」这件事**——每存一次档，就记录下「此时此刻所有文件长什么样」，以后随时能翻回任意一个存档点。

它其实还是一台「时光机」：不仅能回到过去某个时间点，还能清楚地告诉你「从上个存档到这个存档之间，我到底改了哪几行、加了什么、删了什么、是谁改的、为什么改」。

一句严谨的定义：**版本控制是一套用于记录一个或多个文件内容变化，以便将来查阅特定版本、比较差异、恢复到旧版本的系统。** 而 **Git 就是当今世界上使用最广泛的版本控制系统（VCS，Version Control System）**。

#### 没有版本控制会有多惨

初学者最常见的「土法版本控制」是这样的：

```text
毕业论文_最终版.docx
毕业论文_最终版2.docx
毕业论文_最终版_真的是最后一版.docx
毕业论文_最终版_打死不改了.docx
```

问题一大堆：
- 文件名爆炸，根本分不清哪个是最新的；
- 不知道两个版本之间到底差在哪；
- 多个人一起改一份文件，互相覆盖，改动直接丢失；
- 想回到「三天前那个能跑的版本」，但你根本没存那个档。

Git 就是来系统性解决这些痛点的。

#### 集中式（SVN）vs 分布式（Git）

版本控制系统分两大流派，理解它们的区别，是理解 Git 为什么这么强的关键。

**集中式（以 SVN、CVS 为代表）**：所有的「历史存档」只存在一台中央服务器上。你电脑上只有「当前这一个版本」的文件。你想看历史、想提交，都必须连上中央服务器。

打个比方：集中式就像**公司只有一本纸质账本，锁在总部保险柜里**。你要记一笔账、要查上个月的账，都得亲自跑到总部去。总部一旦着火（服务器挂了），账本没了备份，全公司的历史就全没了。

**分布式（以 Git 为代表）**：每个人 `clone`（克隆）一份仓库到自己电脑后，**本地就有了完整的历史记录**，包括从项目诞生至今的每一次提交。你在本地就能查历史、能提交、能对比，完全不需要联网。只有当你要和别人「同步」时，才需要联网。

对应的比方：分布式就像**每个员工手上都有一本完整账本的副本**。你在自己座位上就能记账、查账；哪天总部账本烧了，随便找个员工的副本就能恢复出完整历史。

用表格总结二者区别：

| 对比维度 | 集中式（SVN） | 分布式（Git） |
|---|---|---|
| 完整历史存在哪 | 只在中央服务器 | 每个人本地都有一份完整副本 |
| 提交/查历史是否需要联网 | 需要联网连服务器 | 本地即可，离线也能干活 |
| 提交速度 | 慢（走网络） | 快（本地操作） |
| 服务器挂了 | 历史可能全丢，风险大 | 任意一个本地副本都能恢复 |
| 分支操作 | 笨重、慢 | 极其轻量、快速（Git 的杀手锏） |

> 面试小贴士：如果被问「Git 和 SVN 最本质的区别是什么」，最核心的答案就是一句——**Git 是分布式的，每个客户端都保存了完整的版本历史；SVN 是集中式的，完整历史只在中央服务器上。** 由此才衍生出「Git 可离线工作、分支廉价、速度快、不怕单点故障」这些优点。

#### Git 为什么这么流行

- **速度快**：绝大多数操作都在本地完成，不走网络。
- **分支极其廉价**：创建、切换分支几乎是瞬间完成，鼓励大家大胆用分支开发新功能（这是后续板块的重点）。
- **数据安全可靠**：Git 用内容校验（SHA 值）保证历史不被悄悄篡改。
- **强大的生态**：GitHub、GitLab、Gitee 等平台都建立在 Git 之上，成了全球开发者协作的事实标准。
- **DevOps 的基石**：现代的 CI/CD（持续集成/持续部署）流水线几乎都以「代码推送到 Git 仓库」作为触发起点。**这也是为什么面运维/DevOps 岗位，Git 是必考的基本功。**

### 1.2 安装与初次配置

#### 各平台如何安装

**Windows**：去官网 [git-scm.com](https://git-scm.com) 下载安装包，一路「下一步」即可。装完后会附带一个叫 **Git Bash** 的终端，它能让你在 Windows 上使用类 Linux 的命令行环境，强烈建议用它来练习 Git。

**macOS**：最简单的方式是先装 Homebrew（macOS 的包管理器），再执行：

```bash
brew install git
```

或者直接在终端输入 `git --version`，如果没装，系统会弹窗提示你安装命令行工具。

**Linux**（以 Debian/Ubuntu 系为例，运维方向最常用）：

```bash
# apt 是 Ubuntu/Debian 的包管理器，update 先刷新软件源列表
sudo apt update
# 然后安装 git 这个软件包，-y 表示自动对所有确认提问回答 yes
sudo apt install -y git
```

CentOS/RHEL 系则用 `yum` 或 `dnf`：

```bash
sudo yum install -y git
```

装完后，**验证是否安装成功**，看看版本号：

```bash
git --version
# 输出类似：git version 2.39.2
```

> 名词解释：`--version` 前面的两个短横线 `--` 是「长选项」的写法（完整单词）；很多命令也支持一个短横线加单字母的「短选项」（如 `-v`）。这是 Linux/Git 命令的通用惯例，后面会反复见到。

#### 初次配置：告诉 Git「你是谁」

装好 Git 后，**第一件必须做的事**就是配置你的用户名和邮箱。因为 Git 每次提交（commit）都会把「作者是谁」记进历史里，如果不配置，提交时会报错或留下空白作者。

```bash
# 配置全局用户名（--global 表示这台电脑上所有仓库都用这个名字）
git config --global user.name "Yao Jinmeng"

# 配置全局邮箱
git config --global user.email "jinmeng.yao@example.com"
```

这里的 `user.name` 和 `user.email` **不是登录账号密码**，只是用来在提交历史里标记「这次改动是谁做的」，可以随便填，但建议填成和你 GitHub/GitLab 账号一致的信息，方便平台正确统计你的贡献。

#### 理解三个配置级别：`--system` / `--global` / `--local`

Git 的配置分三层，优先级从低到高，**范围小的会覆盖范围大的**。这是一个高频考点，务必理解清楚。

| 级别 | 命令参数 | 作用范围 | 配置文件位置 | 优先级 |
|---|---|---|---|---|
| 系统级 | `--system` | 这台机器上的所有用户、所有仓库 | 一般在 `/etc/gitconfig` | 最低 |
| 全局/用户级 | `--global` | 当前登录用户的所有仓库 | 用户主目录下 `~/.gitconfig` | 中 |
| 仓库/本地级 | `--local`（默认） | 只对当前这一个仓库生效 | 该仓库内 `.git/config` | 最高 |

打个比方：这就像穿衣服的「三层规则」。系统级是「全公司统一发的工服」，全局级是「你个人衣柜里默认穿的那套」，本地级是「今天这个特定场合专门换的那身」。哪层离你最近（最具体），就听哪层的。

**实际用途举例**：你平时用公司邮箱提交（配在 `--global`），但某个开源项目想用个人邮箱，就进那个项目目录，单独执行不带 `--global`（即 `--local`）的配置：

```bash
# 进入某个具体仓库目录后执行，只改这一个仓库的邮箱
git config --local user.email "my-personal@example.com"
# --local 是默认级别，其实可以省略不写：
git config user.email "my-personal@example.com"
```

> 常见陷阱：如果你发现提交作者信息不对，先检查是不是当前仓库的 `--local` 配置覆盖了你的 `--global` 配置。用下面的命令能看出每条配置来自哪个文件。

#### 查看配置

```bash
# 列出当前生效的所有配置
git config --list

# 更强的版本：每条配置后面标注它来自哪个文件（system/global/local）
git config --list --show-origin

# 只查某一个具体配置项的值
git config user.name
```

#### 配置别名 alias（给长命令起小名）

有些 Git 命令又长又常用，可以用 alias（别名）给它起个简短的「小名」，敲起来省事。

```bash
# 把 "git status" 简化成 "git st"
git config --global alias.st status

# 把 "git checkout" 简化成 "git co"
git config --global alias.co checkout

# 把 "git commit" 简化成 "git ci"
git config --global alias.ci commit

# 一个很实用的复杂别名：漂亮的图形化日志（后面会详解 log）
git config --global alias.lg "log --oneline --graph --all"
```

配置好后，`git st` 就等价于 `git status` 了。原理是：Git 发现你敲的 `st` 不是内置命令，就去配置里查有没有对应的别名，查到了就替换成真正的命令执行。

#### 配置默认编辑器

有些操作（比如写较长的提交说明、交互式操作）Git 会自动打开一个文本编辑器让你输入。默认可能是 Vim，很多初学者被 Vim「困住」不知道怎么退出（顺带一提：Vim 里按 `Esc` 后输入 `:wq` 回车是「保存并退出」）。你可以把它改成自己顺手的编辑器：

```bash
# 改成 VS Code（--wait 表示 Git 会等你关闭编辑器窗口后再继续）
git config --global core.editor "code --wait"

# 改成 nano（比 Vim 对新手友好得多，底部有快捷键提示）
git config --global core.editor "nano"
```

#### 中文乱码与换行符问题（运维/跨平台必知）

**问题一：`git status` 里中文文件名显示成一堆 `\xxx` 数字**

Git 默认会把非 ASCII 字符（比如中文）用八进制转义显示，看起来像乱码。关掉这个行为即可正常显示中文：

```bash
# quotepath 直译「给路径加引号转义」，设为 false 就不转义了，中文正常显示
git config --global core.quotepath false
```

**问题二：换行符 `core.autocrlf`（跨平台协作的经典坑）**

背景知识：不同操作系统表示「换行」的方式不一样。Windows 用 `CRLF`（回车+换行，即 `\r\n`），而 Linux/macOS 用 `LF`（只有换行，即 `\n`）。如果 Windows 和 Linux 的同事一起改一个项目，换行符不统一会导致 Git 误以为「整个文件每一行都被改过」，产生大量无意义的差异。

`core.autocrlf` 就是用来自动处理这个转换的：

```bash
# Windows 用户推荐：提交时把 CRLF 转成 LF，检出时再转回 CRLF
git config --global core.autocrlf true

# Linux/macOS 用户推荐：提交时把 CRLF 统一转成 LF，检出时不转换
git config --global core.autocrlf input

# 完全不做任何转换（团队约定统一用 LF 时可用）
git config --global core.autocrlf false
```

| 平台 | 推荐值 | 含义 |
|---|---|---|
| Windows | `true` | 存进仓库统一为 LF，拿到本地变 CRLF |
| Linux/macOS | `input` | 存进仓库统一为 LF，检出时不改动 |

> 记忆要点：**仓库里永远存 LF，是业界通行的最佳实践。** `autocrlf` 就是帮 Windows 用户在「本地 CRLF」和「仓库 LF」之间自动来回转换的开关。

#### 凭证存储 `credential.helper`（免去每次输密码）

当你用 HTTPS 方式往远程仓库推送代码时，Git 每次都会问你要用户名和密码/令牌，很烦。`credential.helper` 可以把凭证存起来，免得反复输入。

```bash
# 方式一：cache，把凭证在内存里缓存一段时间（默认 15 分钟）
git config --global credential.helper cache
# 可以指定缓存时长（单位秒），这里设为 1 小时
git config --global credential.helper 'cache --timeout=3600'

# 方式二：store，把凭证以明文保存到磁盘文件（~/.git-credentials），永久免输入
git config --global credential.helper store
```

> 安全陷阱：`store` 会把密码/令牌**明文**存在磁盘文件里，方便但不安全，个人电脑上可用，公共或服务器环境慎用。Windows 上更推荐系统自带的 `manager`（凭据管理器，加密存储）。另外，现在 GitHub 等平台已不允许用账号密码推送，需要用 **PAT（Personal Access Token，个人访问令牌）** 来代替密码，这个令牌就当密码填进去即可。

### 1.3 核心概念：Git 的几大区域与文件状态

这一节是**整个 Git 的心脏**，务必吃透。理解了这几个「区域」，后面所有命令你才知道它们到底在搬动什么东西。

#### 四大区域（用「写文章投稿」打比方）

想象你在写文章投稿给杂志社，整个流程有四个地方：

1. **工作区（Working Directory）**——你的**书桌**。你正在上面涂涂改改的稿纸，就是你项目文件夹里那些你能直接看到、直接编辑的文件。

2. **暂存区（Staging Area / Index）**——你的**待寄信封**。你觉得某几页改好了，就先把它们放进信封里「预备寄出」，但还没真正投进邮筒。这一步让你能挑选「这次到底要提交哪些改动」，而不是桌上所有东西一股脑全交。

3. **本地仓库（Local Repository / `.git` 目录）**——你家里的**已寄存档柜**。信封投进邮筒（提交）后，这次投稿就正式存档、生成了一个不可更改的历史记录点，永久保存在你本地。

4. **远程仓库（Remote Repository）**——**杂志社总部**。你把本地存档柜里的稿件同步一份到杂志社，别人才能看到、才能和你协作。（GitHub/GitLab 上的仓库就是远程仓库。）

> 关键点：**暂存区（Staging Area）是 Git 相比很多工具最独特、也最容易让新手困惑的设计。** 它的意义是给你一个「缓冲和挑选」的机会——你可以只把一部分改动放进暂存区去提交，把另一部分改动留在工作区继续改。别名 **Index（索引）** 是它的历史叫法，二者指同一个东西。

#### 文件在 Git 眼里的四种状态

Git 会持续追踪你工作区里每个文件的「状态」。理解状态流转，`git status` 的输出你才看得懂。

| 状态 | 英文 | 含义（大白话） |
|---|---|---|
| 未跟踪 | Untracked | 新建的文件，Git 还没管它，「查无此人」 |
| 已修改 | Modified | 被 Git 跟踪的文件，改动过但还没放进暂存区 |
| 已暂存 | Staged | 改动已经放进暂存区（信封里），等待提交 |
| 已提交 | Committed | 改动已经安全存进本地仓库（存档柜） |

#### 用 ASCII 图看清「文件是怎么流动的」

```text
   工作区                暂存区                本地仓库              远程仓库
(Working Dir)        (Staging Area)      (Local Repo/.git)     (Remote Repo)
     │                     │                     │                    │
     │   git add           │                     │                    │
     ├────────────────────>│                     │                    │
     │  (把改动放进信封)     │                     │                    │
     │                     │   git commit        │                    │
     │                     ├────────────────────>│                    │
     │                     │  (投进邮筒/存档)      │                    │
     │                     │                     │   git push         │
     │                     │                     ├───────────────────>│
     │                     │                     │  (同步到杂志社总部)  │
     │                     │                     │                    │
     │                     │                     │   git fetch/pull   │
     │                     │<────────────────────┼────────────────────┤
     │                     │              (把别人的改动拿回本地)         │
```

把三条最核心的命令和这张图对应记牢：
- **`git add`**：工作区 → 暂存区（挑选要提交的改动）
- **`git commit`**：暂存区 → 本地仓库（正式存档一个历史点）
- **`git push`**：本地仓库 → 远程仓库（同步给团队）

一个文件的典型「一生」：

```text
新建 hello.py（Untracked）
      │ git add hello.py
      ▼
放进暂存区（Staged）
      │ git commit -m "新增 hello.py"
      ▼
存进仓库（Committed）
      │ 你又改了 hello.py 的内容
      ▼
已修改（Modified）
      │ git add hello.py  → 再次 Staged
      │ git commit        → 再次 Committed
      ▼
     ...循环往复...
```

### 1.4 创建仓库

有两种方式让一个目录变成 Git 仓库：从零新建，或从别处克隆。

#### `git init`：把现有目录变成 Git 仓库

当你本地已经有一个项目文件夹，想开始用 Git 管理它：

```bash
# 先进入你的项目目录
cd my-project

# 初始化 Git 仓库
git init
```

执行后，Git 会在当前目录下悄悄创建一个名为 `.git` 的**隐藏文件夹**（名字以点开头的在 Linux 下默认隐藏，用 `ls -a` 才看得到）。**这个 `.git` 文件夹就是「本地仓库」本体**，里面装着所有历史记录、配置、暂存区等。你千万别手动删它，删了整个版本历史就没了。

> 小知识：新版 Git 初始化后默认分支名可能是 `master` 或 `main`（取决于版本和配置）。GitHub 等平台现在默认用 `main`。可以这样把你的默认分支名统一设成 `main`：
> ```bash
> git config --global init.defaultBranch main
> ```

#### `git clone`：把远程仓库整个复制到本地

当项目已经存在于 GitHub/GitLab 等远程平台，你想参与，就用 `clone` 把它「克隆」下来：

```bash
# 克隆一个远程仓库到当前目录（会自动新建一个和仓库同名的文件夹）
git clone https://github.com/user/repo.git

# 也可以指定克隆到的本地文件夹名字
git clone https://github.com/user/repo.git my-folder
```

`git clone` 一步到位做了好几件事：把远程仓库的**完整历史**下载到本地、自动创建 `.git`、自动把这个远程仓库记为 `origin`（默认远程名）、并检出最新的代码到工作区。所以克隆完你就能直接干活了。

#### HTTPS vs SSH：克隆地址的两种形式

克隆地址有两种协议，长得不一样，作用相同：

| 方式 | 地址长相 | 特点 |
|---|---|---|
| HTTPS | `https://github.com/user/repo.git` | 简单直接，推送时要输账号/令牌（可配凭证存储免输） |
| SSH | `git@github.com:user/repo.git` | 需提前配置 SSH 密钥，配好后推送免密、更安全，适合长期开发 |

打个比方：**HTTPS 像每次进门都要刷卡输密码；SSH 像提前给了你一把专属钥匙，配一次以后进出自由。** 初学练习用 HTTPS 最省事；长期开发、频繁推送，建议配 SSH 密钥（生成密钥的具体步骤这里从略，后续「远程协作」板块会讲）。

### 1.5 基础工作流命令详解

这一节把你每天都会用到的命令逐个讲透。建议边看边在一个练习仓库里亲手敲一遍。

#### `git status`：查看当前状态（用得最勤的命令）

它回答「我现在处于什么情况」：哪些文件没跟踪、哪些改了没暂存、哪些已暂存待提交、当前在哪个分支。

```bash
git status
```

典型输出解读：

```text
On branch main                        # 当前在 main 分支
Changes to be committed:              # 已暂存、待提交的（绿色）
        new file:   a.txt
Changes not staged for commit:        # 已修改但没暂存的（红色）
        modified:   b.txt
Untracked files:                      # 未跟踪的新文件（红色）
        c.txt
```

嫌输出太啰嗦，可以用简洁模式：

```bash
git status -s      # -s 是 --short，用两列字母紧凑显示状态
```

> 上手建议：**每做一步操作前后都习惯性敲一下 `git status`**，它会明确告诉你「现在什么状态、下一步能做什么」，是新手最好的向导。

#### `git add`：把改动放进暂存区

把工作区的改动挑选进暂存区（信封）。有多种用法：

```bash
# 暂存指定的单个文件
git add hello.py

# 暂存当前目录及子目录下所有改动（最常用）
git add .

# 暂存整个仓库范围的所有改动（含删除，范围最全）
git add -A
```

`git add .` 和 `git add -A` 的区别是初学常见的困惑点：

| 命令 | 作用范围 | 是否包含「文件删除」 |
|---|---|---|
| `git add .` | 当前目录及其子目录 | 新版 Git 中包含 |
| `git add -A` | 整个仓库（不管你当前在哪个子目录） | 包含 |
| `git add -u` | 只针对**已跟踪**文件的修改和删除 | 包含，但不加新文件 |

**交互式暂存 `-p`（进阶但很实用）**：

```bash
git add -p     # -p 是 --patch，一块一块地问你「这段改动要不要暂存」
```

它会把你对某个文件的改动切成一小块一小块（Git 叫 hunk），逐块问你 `y`（要）/`n`（不要）。这在「一个文件里改了好几处，但你只想先提交其中一部分」时特别有用。

#### `git commit`：把暂存区内容正式存档

把信封投进邮筒，生成一个永久的历史记录点。

```bash
# 最标准的写法：-m 后面跟本次提交的说明信息
git commit -m "新增用户登录功能"
```

`-m` 是 message（说明）的意思，**每次提交都必须写说明**，用来记录「这次改了啥、为啥改」。如果不加 `-m`，Git 会弹出编辑器让你写（新手容易卡在这，所以推荐直接用 `-m`）。

**`-a` 的用法（跳过 add）**：

```bash
# -a 表示：自动把所有【已跟踪】文件的改动直接暂存并提交，省去 git add 这一步
git commit -a -m "修复登录按钮样式"
# 可以合写成
git commit -am "修复登录按钮样式"
```

> 陷阱：`-a` **只对已经被 Git 跟踪过的文件生效**，对全新的 `Untracked` 文件无效！新文件还是得先 `git add`。

**`--amend`：修补上一次提交（基础用法）**：

```bash
# 场景1：刚提交完发现提交说明写错了，想改说明
git commit --amend -m "正确的提交说明"

# 场景2：刚提交完发现漏了一个文件，先 add 上，再 amend 合并进上次提交
git add forgot.py
git commit --amend --no-edit    # --no-edit 表示沿用原来的提交说明不改
```

`--amend` 直译「修订」，作用是**用新的内容替换掉「最近一次」提交**，而不是新增一次提交。它常用来「弥补上一次提交的小失误」。

> 重要陷阱：`--amend` 会改变提交的身份（生成一个新的提交 ID 顶替原来的）。**如果这次提交已经 push 到远程、别人可能已经拉取了，就不要随便 amend**，否则会和别人的历史冲突。只在「还没推送出去的本地提交」上用 amend 才安全。

#### `git diff`：查看差异（对比不同区域）

`diff`（difference，差异）用来看「到底改了哪几行」。**关键在于分清它对比的是哪两个区域**，这是高频考点：

```bash
# 1) 工作区 vs 暂存区：看「改了但还没 add」的内容
git diff

# 2) 暂存区 vs 上次提交：看「已经 add、即将 commit」的内容
git diff --staged        # --cached 是它的同义词，效果一样
git diff --cached

# 3) 工作区 vs 上次提交：看「相对上次提交的全部改动」（不管有没有 add）
git diff HEAD

# 4) 两次提交之间的差异
git diff abc123 def456   # 后面两个是提交的 ID（可只写前几位）
```

用一张表彻底理清对比关系（这也是面试爱问的点）：

| 命令 | 对比左边 | 对比右边 | 通俗理解 |
|---|---|---|---|
| `git diff` | 工作区 | 暂存区 | 我改了还没 add 的部分 |
| `git diff --staged` | 暂存区 | 最近一次提交 | 我 add 了即将提交的部分 |
| `git diff HEAD` | 工作区 | 最近一次提交 | 相对上次提交的所有改动 |

> 名词：`HEAD` 是 Git 里一个非常重要的「指针」，你可以先简单理解为「**当前所在分支的最新一次提交**」，也就是「你现在站在哪个存档点上」。后面板块会深入讲它。

#### `git log`：查看提交历史（时光机的目录）

`log` 把历史上所有提交按时间倒序列出来。直接敲 `git log` 输出很长很占屏，所以要掌握常用参数来「瘦身美化」：

```bash
# 最原始的完整历史（信息最全但很长，按 q 键退出查看）
git log

# 每条提交压缩成一行：只显示短 ID + 提交说明（最常用）
git log --oneline

# 用字符画出分支合并的图形，直观看分叉和汇合
git log --graph

# 显示所有分支的历史（不加 --all 默认只看当前分支）
git log --all

# 组合拳：一行式 + 图形 + 全部分支（强烈推荐，可设成前面讲的 alias lg）
git log --oneline --graph --all

# 每条提交连带显示具体改了哪些代码行（-p 是 patch）
git log -p

# 只看最近 3 条
git log -3
```

**按作者、时间、关键词过滤**（运维排查问题常用）：

```bash
# 只看某位作者的提交
git log --author="Yao"

# 只看某个时间之后的提交
git log --since="2026-01-01"
git log --after="2 weeks ago"

# 只看某个时间之前的
git log --until="2026-08-01"

# 按提交说明里的关键词搜索
git log --grep="修复"

# 只看某个文件的历史（-- 后面跟文件名，把它和分支名区分开）
git log --oneline -- src/app.py
```

> 退出提示：`git log` 内容多时会进入一个叫 pager（分页器，通常是 `less`）的浏览界面，用**上下方向键**滚动，按 **`q`** 键退出。新手常被「卡在这个界面出不去」，记住按 `q` 就行。

#### `git show`：查看某一次提交的详情

`log` 是看「历史清单」，`show` 是看「某一条的完整细节」——包括这次提交的作者、时间、说明，以及具体改了哪些代码。

```bash
# 查看最近一次提交（HEAD）的完整内容
git show

# 查看指定提交（用它的 ID，可只写前 7 位左右）
git show abc1234

# 查看某次提交里某个具体文件的改动
git show abc1234:src/app.py
```

### 1.6 基础撤销操作（入门级）

> 本节只讲最简单、最安全的「撤销日常小改动」。至于功能更强、也更容易出事的 `git reset`（三种模式）、`git revert`、`git reflog` 找回等，**属于进阶内容，详见第二板块**。这里点到为止，够你应付日常即可。

初学者最常见的三种「后悔了想撤销」的场景：

#### 场景一：改乱了工作区文件，想丢弃改动、恢复成上次提交的样子

```bash
# 新版 Git 推荐写法（Git 2.23+）
git restore hello.py

# 老版本 / 传统写法（效果相同）
git checkout -- hello.py
```

`restore`（恢复）会把 `hello.py` **还原成暂存区（或上次提交）里的样子，你没保存的改动会永久丢失**。

> 严重陷阱：这个操作**不可撤销**，丢弃的改动找不回来！执行前一定确认这些改动你真的不要了。传统写法 `git checkout -- 文件名` 里那个 `--` 不能省，它的作用是告诉 Git「后面跟的是文件名，不是分支名」，避免歧义。

#### 场景二：`git add` 加错了，想把文件「撤出」暂存区（但保留改动）

```bash
# 新版推荐写法：把文件移出暂存区，改动仍留在工作区
git restore --staged hello.py

# 老版本 / 传统写法（效果相同）
git reset HEAD hello.py
```

注意这一步**只是把文件从「信封」里拿回书桌**，你对文件的改动内容一点都不会丢，只是取消了「待提交」状态。它和场景一正好是相反方向的操作，别搞混：
- `git restore --staged 文件` = 取消暂存（改动还在）
- `git restore 文件` = 丢弃工作区改动（改动没了）

#### 三个撤销命令速查表

| 你想做的事 | 推荐命令（新版） | 传统命令 | 改动是否丢失 |
|---|---|---|---|
| 丢弃工作区的修改 | `git restore <file>` | `git checkout -- <file>` | **会丢失** |
| 把文件撤出暂存区 | `git restore --staged <file>` | `git reset HEAD <file>` | 不丢失 |

> 为什么有「新旧两套写法」：早期 Git 把「撤销修改」和「取消暂存」都塞给了 `git checkout` 和 `git reset`，这俩命令一词多义、极易误用。于是 Git 2.23 版本拆出了语义更清晰的 `git restore`（管文件恢复）和 `git switch`（管切换分支）。**新手建议直接学新写法，语义更明确、更不容易误伤。**

### 1.7 `.gitignore` 详解：让 Git 忽略不该管的文件

#### 为什么需要它

项目里总有些文件你**不想让 Git 跟踪**：编译产生的临时文件、日志、依赖包目录（如 `node_modules`）、含密码的配置文件、编辑器的缓存等。这些东西提交上去既占地方又可能泄密。

`.gitignore` 就是一个特殊的文本文件，你把「不想让 Git 管的文件/目录规则」写进去，Git 就会自动无视它们，`git status` 里也不再提示。

打个比方：`.gitignore` 就是贴在门口的一张「**这些东西别往信封里装**」的清单，Git 每次打包时都会对照这张清单跳过它们。

#### 在哪里创建

在项目根目录下创建一个名字就叫 `.gitignore` 的文件（注意开头有个点）：

```bash
# 在项目根目录创建（这里用 touch 命令新建一个空文件）
touch .gitignore
```

然后用编辑器往里写规则。

#### 规则语法详解

```gitignore
# 以 # 开头的是注释行，会被忽略

# 1) 忽略所有 .log 结尾的文件（* 是通配符，匹配任意多个字符）
*.log

# 2) 忽略名为 temp 的文件或文件夹（不带斜杠，任意层级都匹配）
temp

# 3) 只忽略「目录」，末尾加斜杠 / 明确表示这是文件夹
build/
node_modules/

# 4) 以斜杠 / 开头表示「只匹配根目录下的」，不匹配子目录里的同名文件
/config.local        # 只忽略根目录的 config.local

# 5) ! 开头表示「例外，不要忽略」（反向规则）
*.log                # 先忽略所有 .log
!important.log       # 但 important.log 例外，要保留跟踪

# 6) ? 匹配单个任意字符
file?.txt            # 匹配 file1.txt、fileA.txt，但不匹配 file10.txt

# 7) ** 匹配任意层级的目录
logs/**/*.tmp        # 匹配 logs 下任意深度的 .tmp 文件

# 8) 忽略某目录下所有内容，但保留某个子文件
doc/*                # 忽略 doc 下所有
!doc/README.md       # 但保留这个
```

把最常用的规则符号整理成表：

| 符号 | 含义 | 例子 |
|---|---|---|
| `#` | 注释 | `# 这是说明` |
| `*` | 匹配任意多个字符（不含 `/`） | `*.log` |
| `?` | 匹配单个字符 | `file?.txt` |
| `/`（结尾） | 只匹配目录 | `build/` |
| `/`（开头） | 只匹配根目录下的 | `/config` |
| `!` | 取反，不忽略（例外） | `!keep.log` |
| `**` | 匹配任意层级目录 | `a/**/b` |

#### 常见项目模板参考

不同语言项目常忽略的内容不太一样，这里给几个片段感受一下：

```gitignore
# ===== Python =====
__pycache__/
*.pyc
.venv/
venv/
*.egg-info/

# ===== Node.js / 前端 =====
node_modules/
dist/
.env

# ===== 通用：日志、系统、编辑器 =====
*.log
.DS_Store          # macOS 自动生成的目录缓存文件
.idea/             # JetBrains 系 IDE 的配置
.vscode/           # VS Code 的本地配置
```

> 实用技巧：不用自己从零写，GitHub 官方维护了各种语言的 `.gitignore` 模板仓库（github.com/github/gitignore），或直接在新建仓库时勾选对应语言，平台会帮你生成。

#### 全局 `.gitignore`（一次配置，所有仓库生效）

像 `.DS_Store`、编辑器缓存这类「和具体项目无关、每个仓库都想忽略」的东西，与其在每个项目里都写一遍，不如配一个**全局忽略文件**：

```bash
# 1) 指定一个全局 ignore 文件的位置
git config --global core.excludesfile ~/.gitignore_global

# 2) 然后把通用规则写进 ~/.gitignore_global 这个文件里即可
```

#### 高频陷阱：已经被跟踪的文件，加进 `.gitignore` 却不生效！

这是**面试和实战都极常见**的坑，务必记牢：

**`.gitignore` 只对「还没被 Git 跟踪过的文件」生效。** 如果一个文件在你写规则之前就已经被 `add`/`commit` 跟踪了，那么即使你现在把它写进 `.gitignore`，Git 依然会继续跟踪它、依然会提示它的改动。

解决办法：先把它从「暂存区/仓库的跟踪」里移除，但**保留本地实际文件**，再提交：

```bash
# --cached 表示只从 Git 的跟踪里删除，不删你磁盘上的实际文件
git rm --cached config.local

# 如果是一整个目录，加 -r（递归）
git rm --cached -r logs/

# 然后把它写进 .gitignore，再提交这次改动
git commit -m "停止跟踪 config.local，并加入 .gitignore"
```

> 关键理解：`git rm --cached` 里的 `--cached` 是「只动缓存（暂存区/索引），别动我的真实文件」的意思。**如果不加 `--cached`，`git rm` 会把你磁盘上的文件也一起删掉**，这是很多人误操作丢文件的原因，务必小心。

### 1.8 远程仓库基础

前面讲的都是「本地」操作。要和团队协作、要把代码备份到 GitHub/GitLab，就得和**远程仓库**打交道。这一节讲最基础的远程操作。

#### `git remote`：管理远程仓库地址

「远程仓库」在本地是用一个**简短的别名**来指代的，默认叫 `origin`（起源）。这样你就不用每次都敲又长又难记的完整 URL。

```bash
# 查看当前配置了哪些远程仓库（-v 是 verbose 详细，会显示对应的 URL）
git remote -v
# 输出类似：
# origin  https://github.com/user/repo.git (fetch)
# origin  https://github.com/user/repo.git (push)

# 新增一个远程仓库，取名为 origin，指向某个 URL
git remote add origin https://github.com/user/repo.git

# 给远程仓库改名（把 origin 改成 upstream）
git remote rename origin upstream

# 删除一个远程仓库配置
git remote remove origin

# 查看某个远程仓库的详细信息
git remote show origin
```

> 说明：`origin` 只是一个**约定俗成的默认名字**，不是关键字，你完全可以叫别的名。但业界习惯：自己 fork 来的、自己主要推送的远程叫 `origin`；原项目的官方远程习惯叫 `upstream`（上游）。用 `git clone` 克隆下来的仓库，Git 会自动帮你把它配成 `origin`。

#### `git push`：把本地提交推送到远程

把你本地仓库（存档柜）里的提交，同步一份到远程仓库（杂志社）。

```bash
# 完整写法：把本地 main 分支推送到名为 origin 的远程
git push origin main
```

这条命令拆开理解：`push`（推送）+ `origin`（推到哪个远程）+ `main`（推送哪个本地分支）。

**首次推送与 `-u` 的含义（重点）**：

```bash
# 首次推送某个分支时，加 -u 建立「跟踪关系」
git push -u origin main
```

`-u` 是 `--set-upstream` 的缩写，意思是「把本地 `main` 和远程 `origin/main` **绑定**起来」。绑定之后，Git 就记住了「我这个本地分支对应远程哪个分支」。**好处是：以后在这个分支上，你只需敲 `git push` 或 `git pull`，不用再写 `origin main` 了**，Git 知道推/拉到哪去。

```bash
# 建立跟踪关系后，以后直接：
git push        # 等价于 git push origin main
git pull        # 等价于 git pull origin main
```

> 常见新手错误：第一次推送忘了本地和远程分支名不一致，或远程还有你本地没有的提交，push 会被拒绝（rejected）。此时通常需要先 `pull` 把远程改动拉下来合并，再 push。冲突处理的细节留待后续板块。

#### `git fetch` vs `git pull`：拉取远程更新（最重要的区分点）

这是**面试高频、实战也极其重要**的一对命令。二者都是「从远程获取更新」，但行为不同：

**`git fetch`（取回，但不合并）**：

```bash
git fetch origin
```

它把远程的最新提交**下载到本地**，更新你本地记录的「远程分支状态」（如 `origin/main`），但**不会动你当前正在编辑的工作区和分支**。相当于「先把杂志社的最新稿件取回来放一边，让我先看看有什么变化，我自己决定要不要合并」。**安全、不会打乱你手头的工作。**

看完可以对比差异，确认无误后再手动合并：

```bash
git fetch origin
git diff main origin/main    # 先看看远程比我多了什么
git merge origin/main        # 确认后再合并进来
```

**`git pull`（取回并立即合并）**：

```bash
git pull origin main
```

`git pull` 本质上等于 **`git fetch` + `git merge`** 两步合一：先下载远程更新，然后**立刻自动合并**到你当前分支。相当于「取回稿件后二话不说直接并进我正在写的稿子里」。方便，但如果远程改动和你本地改动有冲突，会当场产生合并冲突需要你处理。

一图看清：

```text
git fetch  = 只下载，不合并       （安全，你自己决定何时合并）
git pull   = git fetch + git merge（下载后立即合并，一步到位）
```

| 对比 | `git fetch` | `git pull` |
|---|---|---|
| 是否下载远程更新 | 是 | 是 |
| 是否自动合并到当前分支 | 否 | 是（自动 merge） |
| 会不会改动你的工作区 | 不会 | 会 |
| 安全性 | 高（可先审查再合并） | 较低（可能突然冒出冲突） |
| 适用场景 | 想先看远程变化再决定 | 确定要直接同步最新代码 |

> 面试标准答案：**`git fetch` 只把远程的更新下载到本地仓库，不会修改你的工作区和当前分支；`git pull` 则是 `git fetch` 加 `git merge`，下载之后会立即把远程改动合并到当前分支。** 更保险的习惯是「先 `fetch` 看清楚再决定要不要 `merge`」，尤其在多人协作、担心冲突时。

#### `git clone` 回顾

前面 1.4 讲过 `git clone`，放在远程这一节再串一下它的地位：`clone` 是你和一个远程仓库打交道的**起点**——它一次性完成「下载完整历史 + 建好 `.git` + 自动配好 `origin` 远程 + 检出最新代码」。克隆之后，你就可以在本地正常 `add`/`commit`，需要同步时用 `fetch`/`pull` 拉、用 `push` 推，形成完整的协作闭环。

#### 本节命令小结

```bash
git remote -v                    # 看有哪些远程
git remote add origin <url>      # 加一个远程
git push -u origin main          # 首次推送并建立跟踪
git push                         # 之后直接推
git fetch origin                 # 只取回，不合并
git pull                         # 取回并合并
git clone <url>                  # 克隆整个远程仓库到本地
```

> 关于分支的创建、切换、合并（merge/rebase）、以及推送时的冲突处理等更复杂的远程协作流程，**将在后续的进阶板块中详细展开**，本板块先掌握上面这套「单人 + 简单同步」的基础闭环即可。

### 2.1 分支管理（branch / switch / checkout）

#### 2.1.1 分支的本质：一个"可移动的指针"

**大白话**：很多初学者以为"建一个分支"是把整个项目文件夹复制了一份，其实完全不是。分支在 Git 里**就是一张贴在某个提交（commit）上的便利贴**，上面写着这个分支叫什么。你在这个分支上每提交一次，这张便利贴就自动往前挪一格，贴到最新的提交上。

**严谨说明**：一个分支（branch）本质上就是一个**指向某个 commit 的、可移动的引用（reference）**。它在物理上只是 `.git/refs/heads/` 目录下的一个小文件，文件内容就是一串 40 位的 commit 哈希值（SHA-1）。所以创建分支几乎是"零成本"的——不复制任何文件，只是新建一个 41 字节的指针文件。

还有一个特殊指针叫 **HEAD**，你可以理解成"**你现在人站在哪儿**"的那个箭头。正常情况下 HEAD 指向某个分支（比如 `main`），而那个分支再指向某个 commit。

```
        C1 ──── C2 ──── C3
                         ↑
                        main   ← 分支指针，指向 C3
                         ↑
                        HEAD   ← 你现在站在 main 上
```

当你在 `main` 上再提交一个 C4 时，`main` 和 `HEAD` 会一起自动往前挪：

```
        C1 ──── C2 ──── C3 ──── C4
                                 ↑
                                main
                                 ↑
                                HEAD
```

> 面试小抄：被问"Git 分支为什么这么轻量、切换这么快？"标准答案就是——**分支只是一个指向 commit 的指针，创建和切换分支只是移动指针，不涉及文件的大规模复制**。

#### 2.1.2 `git branch`：创建、查看、删除、重命名

```bash
# 查看所有本地分支（当前所在分支前面有个 * 号）
git branch

# 查看所有分支，并显示每个分支最新 commit 的信息
git branch -v

# 查看远程分支
git branch -r

# 查看本地 + 远程所有分支
git branch -a

# 创建一个新分支叫 feature，但注意：只创建，不切换过去！
git branch feature

# 删除分支（-d 是 delete，安全删除）
git branch -d feature

# 强制删除分支（-D 等于 --delete --force）
git branch -D feature

# 重命名分支（-m 是 move/rename），把 old 改名成 new
git branch -m old new

# 如果你就在要改名的分支上，可以省略旧名字，直接：
git branch -m new
```

**`-d` 和 `-D` 的关键区别（易错点，面试常问）**：

| 命令 | 全称 | 行为 | 什么时候拦你 |
|---|---|---|---|
| `git branch -d` | `--delete` | **安全删除**：只有当这个分支的提交已经被合并进当前分支（不会丢东西）才允许删 | 分支上有"还没合并进来的提交"时会报错拒绝，防止你误删丢代码 |
| `git branch -D` | `--delete --force` | **强制删除**：不管有没有合并，直接删掉这个指针 | 从不拦你（危险，可能丢掉未合并的工作） |

> 常见陷阱：删分支删的**只是那个指针**，被指向的 commit 不一定马上消失。如果你 `-D` 强删了一个还没合并的分支，那些 commit 会变成"没有任何指针指向的孤儿提交"，一段时间后才会被 Git 垃圾回收。**在被回收之前，用 `git reflog` 还能救回来**（见 2.9 节，这是面试神题）。

#### 2.1.3 `git checkout` vs `git switch`：新旧命令之争

**大白话**：`git checkout` 是个"老前辈"，但它管的事太多太杂——既能切分支，又能恢复文件，还能检出某个提交，功能全塞在一个命令里，新手极容易用混、误操作。于是 Git 2.23 版本（2019 年）把它"拆家"了：切分支这件事交给新命令 `git switch`，恢复文件交给 `git restore`（见 2.7 节），职责更清晰。

| 目的 | 老命令（checkout） | 新命令（推荐） |
|---|---|---|
| 切换到已有分支 | `git checkout main` | `git switch main` |
| 创建并切换到新分支 | `git checkout -b feat` | `git switch -c feat` |
| 恢复工作区文件（丢弃改动） | `git checkout -- file.txt` | `git restore file.txt` |

```bash
# —— 老写法 ——
git checkout main            # 切到 main 分支
git checkout -b feature      # 创建 feature 并立刻切过去（-b = branch）

# —— 新写法（更推荐，语义清晰）——
git switch main              # 切到 main 分支
git switch -c feature        # 创建 feature 并切过去（-c = create）

# 切回"上一个待过的分支"（横杠是简写）
git switch -                 # 等价于 git checkout -
```

> 面试答法：被问"checkout 和 switch 有什么区别？"就说——**`checkout` 是历史遗留的多功能命令，职责过载容易误用；Git 2.23 起把它的功能拆成了专管切分支的 `switch` 和专管恢复文件的 `restore`，语义更清晰、更不容易出错。生产里推荐用新命令。**

> 常见陷阱：`git checkout <文件名>` 会**直接丢弃该文件在工作区的未提交改动，且不可撤销、不进回收站**。历史上无数人手滑用这个命令把没保存的工作删没了。这也是社区把它换成语义更明确的 `git restore` 的重要原因。

#### 2.1.4 追踪分支（tracking / 上游 upstream）

**大白话**：你本地的 `main` 和远程仓库上的 `origin/main` 之间，可以建立一种"结对绑定"的关系——绑定之后，你敲 `git pull` / `git push` 时不用每次都写清楚"从哪个远程的哪个分支拉/推"，Git 自己知道该找谁。这个被绑定的"对家"就叫**上游分支（upstream）**，这种绑定关系叫**追踪（tracking）**。

```bash
# 基于远程分支创建本地分支时，通常会自动建立追踪关系
git switch -c dev origin/dev        # 本地 dev 自动追踪 origin/dev

# 明确指定追踪某个上游（--track）
git branch --track dev origin/dev

# 已经在某分支上，事后给它补设上游：
git branch --set-upstream-to=origin/dev
# 或者第一次 push 时用 -u（--set-upstream）一步到位
git push -u origin dev

# 查看每个本地分支追踪的是哪个上游
git branch -vv
```

> 好处：设好上游后，在该分支上直接 `git pull` / `git push` 即可，不必写 `git push origin dev`。`git status` 也会贴心地告诉你"你比上游领先 2 个提交 / 落后 3 个提交"。

### 2.2 合并 merge：Fast-forward vs 三方合并 vs `--no-ff`

**大白话**：合并（merge）就是把另一条分支上做的改动"汇总"进你当前所在的分支。但根据两条分支的历史关系不同，Git 会用两种完全不同的策略来合，产生的历史形态也不一样。

#### 2.2.1 情形一：Fast-forward（快进合并）

**什么时候发生**：当你要合并进来的那条分支，**是从当前分支的最新提交上直直往前长出来的**（当前分支自这条分支分叉后一个新提交都没有），Git 发现"根本不用真的合并，我把指针往前挪到你那儿就行了"——这就叫快进（fast-forward，简称 ff）。

合并前：
```
        C1 ──── C2            ← main（HEAD 在这）
                 \
                  C3 ──── C4  ← feature
```

`git merge feature` 之后（main 指针直接"快进"滑到 C4）：
```
        C1 ──── C2 ──── C3 ──── C4
                                 ↑
                              main、feature
```

**特点**：不产生新的 merge commit，历史是一条直线，很干净。但缺点是——**从历史上看不出来"这里曾经有过一条 feature 分支"**，因为分叉的痕迹被抹平了。

#### 2.2.2 情形二：三方合并（three-way merge），产生 merge commit

**什么时候发生**：当两条分支**各自都有新提交**（真正分叉了），无法简单快进。Git 会找到两条分支的**共同祖先**（分叉点），加上两条分支各自的最新提交，一共三个 commit 做"三方合并"，然后**自动生成一个特殊的合并提交（merge commit）**，这个提交有**两个父提交**。

合并前（两边都有新提交，真的分叉了）：
```
        C1 ──── C2 ──── C5     ← main（C5 是 main 独有的新提交）
                 \
                  C3 ──── C4   ← feature
```

`git merge feature` 之后：
```
        C1 ──── C2 ──── C5 ──── M   ← main
                 \             /
                  C3 ──── C4 ─╯
              （M 就是 merge commit，它有两个父：C5 和 C4）
```

> "三方合并"名字由来：它需要基于**三个**快照来算——共同祖先 C2、我方 C5、对方 C4，比较这三者才能算出最终结果，故名 three-way merge。

#### 2.2.3 `--no-ff`：强制产生 merge commit

**大白话**：有时候明明可以快进（情形一），但你**故意不让它快进**，非要生成一个 merge commit，为的是在历史上**留下"这里合并过一条功能分支"的明确记录**。这在团队协作里很常见——一眼就能看出每个功能是一次完整合并进来的。

```bash
# 默认行为：能快进就快进
git merge feature

# 强制生成 merge commit，即使本可以快进（no fast-forward）
git merge --no-ff feature

# 反过来：只允许快进，不能快进就直接报错（用于保持历史绝对直线）
git merge --ff-only feature
```

用 `--no-ff` 合并上面的"情形一"，历史会变成：
```
        C1 ──── C2 ─────────── M   ← main
                 \            /
                  C3 ──── C4 ╯     （即使能快进，也硬造一个 M）
```

**三种合并方式对比（面试高频）**：

| 方式 | 触发条件 | 是否产生 merge commit | 历史形态 | 优点 / 缺点 |
|---|---|---|---|---|
| Fast-forward（默认，能快进就快进） | 当前分支无新提交，只是落后 | 否 | 一条直线 | 干净；但抹掉了分支存在过的痕迹 |
| 三方合并（真分叉时自动发生） | 两条分支各有新提交 | 是（自动生成） | 出现分叉再汇合的"菱形" | 真实反映历史；merge commit 多了会显乱 |
| `--no-ff`（手动强制） | 能快进也不快进 | 是（强制生成） | 每次合并都有汇合点 | 保留完整功能合并记录，团队规范常用；历史会多出 merge 节点 |

> 常见陷阱：`git merge` **默认合并到"你当前所在的分支"**。所以合并前一定先确认自己站在目标分支上（比如要把 feature 并进 main，得先 `git switch main` 再 `git merge feature`），别站错了分支。

### 2.3 合并冲突解决全流程（面试高频，讲透）

**大白话**：合并冲突（conflict）不是 bug，也不是你操作错了，而是**两个人（或两条分支）改了同一个文件的同一处地方**，Git 不敢替你瞎猜到底该留谁的，于是它举手投降："这块我搞不定，你自己来决定。"

#### 2.3.1 冲突长什么样：三个标记详解

当 `git merge` 遇到冲突，它会**暂停合并**，并在冲突文件里插入一段"冲突标记"，长这样：

```text
<<<<<<< HEAD
这是你当前分支（HEAD）里这一行的内容
=======
这是要合并进来的那条分支里这一行的内容
>>>>>>> feature
```

三个标记怎么读：

| 标记符号 | 含义 |
|---|---|
| `<<<<<<< HEAD` | 冲突区**开始**。这条线以下、到 `=======` 之间，是**你这边（当前分支 HEAD）**的版本 |
| `=======` | **分隔线**。上半段是你的，下半段是对方的 |
| `>>>>>>> feature` | 冲突区**结束**。`=======` 到这条线之间，是**对方分支（这里叫 feature）**的版本 |

#### 2.3.2 解决步骤（完整六步）

```bash
# 第 1 步：合并，撞上冲突，Git 会告诉你哪些文件冲突了
git merge feature
#   会提示：CONFLICT (content): Merge conflict in app.py
#          Automatic merge failed; fix conflicts and then commit the result.

# 第 2 步：看看到底哪些文件还处于冲突未解决状态
git status
#   Unmerged paths 下面列出的就是冲突文件

# 第 3 步：用编辑器打开冲突文件，找到 <<<<<<< ======= >>>>>>> 三个标记
#          手动决定最终要留什么内容：
#            - 只留你的、只留对方的、两者都留、或者两者融合成新的
#          改完后必须把三个标记行本身也全部删掉！

# 第 4 步：告诉 Git "这个文件我解决好了"——用 git add 把它标记为已解决
git add app.py

# 第 5 步：所有冲突文件都 add 完后，提交，完成这次合并
git commit          # 不用写 -m，Git 会自动填好合并信息，你确认即可

# 第 6 步：git status 确认干净
git status
```

> 关键理解：在冲突解决流程里，**`git add` 的作用不只是"加入暂存区"，更是在向 Git 声明"这个文件的冲突我已经处理完毕"**。只有把所有冲突文件都 `add` 了，才能 `git commit` 收尾。这是 add 在冲突场景下的特殊语义，面试可以答这一点。

#### 2.3.3 反悔：`git merge --abort`

**大白话**：合并合到一半，冲突太多、太乱、想放弃，一键"时光倒流"回到合并之前的干净状态：

```bash
git merge --abort     # 彻底取消这次合并，工作区恢复到 merge 之前的样子
```

> 陷阱：`--abort` 只在"合并进行中、还没 commit"时有效。如果你已经 `git commit` 完成了合并，就得用 `git reset` 或 `git revert` 来回退了（见 2.6 节）。

#### 2.3.4 冲突处理心法与工具

- **心法一：先沟通再动手**。冲突处的两段代码往往是两个人各自的意图，别自己一个人闷头选，搞不清就问对方。
- **心法二：解决完务必测试/编译**。手动拼接代码极易拼出"语法能过但逻辑错"的结果。
- **心法三：善用带上下文的 diff**。用 `git diff` 看合并前后的差异，确认没漏改。
- **可视化工具 mergetool**：命令行看 `<<<<<<<` 眼花时，可以调出图形化三栏对比工具：

```bash
git mergetool         # 调出配置好的可视化合并工具（如 vimdiff、meld、VS Code 等）
```
它会把"我方 / 对方 / 合并结果"三栏并排展示，点几下就能选择保留哪边，比手撕文本直观得多。

> 减少冲突的工程建议：**勤同步主分支**（经常把 main 的最新改动合/变基进自己的功能分支）、**小步提交、功能拆小**。冲突往往是"分支长期不合、越攒越多"攒出来的。

### 2.4 变基 rebase

#### 2.4.1 原理："把提交摘下来，重新播放一遍"

**大白话**：merge 是"把两条路在终点汇合，留个岔路口的疤"；rebase（变基）则是"**假装我这条分支从一开始就是从对方最新的地方长出来的**"——它把你分支上的每一个提交，像撕便利贴一样一张张揭下来，先记在小本本上，然后把你的分支基点（base）挪到目标分支的最新提交上，再把刚才记下的提交**一个个重新贴上去（replay，重新播放）**。结果是历史变成了一条漂亮的直线，看不出分叉。

rebase 前：
```
        C1 ──── C2 ──── C5      ← main
                 \
                  C3 ──── C4    ← feature（HEAD 在这）
```

在 feature 上执行 `git rebase main` 后（C3、C4 被"重放"成了新的 C3'、C4'，接在 C5 后面）：
```
        C1 ──── C2 ──── C5 ──── C3' ──── C4'   ← feature
                         ↑
                        main
```

> **关键理解（面试重点）**：C3' 和 C4' 虽然改动内容和 C3、C4 一样，但它们是**全新的提交、有全新的哈希值**。因为一个 commit 的哈希是由"它的父提交 + 内容 + 时间 + 作者"共同算出来的，父提交变了，哈希必然变。这就是后面"黄金法则"的根源——**rebase 会重写提交历史**。

```bash
# 站在 feature 分支上，把它变基到 main 的最新提交
git switch feature
git rebase main
```

#### 2.4.2 交互式 rebase：`git rebase -i`（整理提交历史的利器）

**大白话**：交互式变基（interactive rebase）是"提交历史的美容院"。它让你在把提交重放之前，**先弹出一个清单，让你逐条决定每个提交怎么处理**——可以改措辞、可以合并、可以删除、可以重新排序。常用来在把功能分支合入主线前，把一堆凌乱的 `fix typo`、`再改一点`、`debug` 提交整理成几个干净、有意义的提交。

```bash
# 对最近 3 个提交做交互式整理（HEAD~3 表示"从倒数第 3 个之后"开始）
git rebase -i HEAD~3
```

执行后会打开一个编辑器，长这样（**注意：最上面是最老的提交，最下面是最新的**）：

```text
pick a1b2c3d 实现登录功能
pick e4f5g6h 修复登录的一个 typo
pick i7j8k9l 又改了一下样式

# 下面是命令说明（Git 自动生成的注释）
```

把每行开头的 `pick` 换成你想要的指令即可：

| 指令 | 简写 | 作用 |
|---|---|---|
| `pick` | `p` | 保留这个提交，原样使用（默认） |
| `reword` | `r` | 保留提交，但**修改它的提交信息（message）** |
| `edit` | `e` | 停在这个提交处，让你**修改提交的内容**（改文件、拆分提交等），改完 `--continue` |
| `squash` | `s` | 把这个提交**合并进上一个提交**，并且**保留两条提交信息让你编辑合并** |
| `fixup` | `f` | 同 squash 合并进上一个，但**丢弃本提交的信息**，只用上一个的（更常用、更干净） |
| `drop` | `d` | **删掉这个提交**（直接删掉这一行也等于 drop） |

举例——把后两个小修补压进第一个提交：
```text
pick   a1b2c3d 实现登录功能
fixup  e4f5g6h 修复登录的一个 typo      ← 压进上面那条，丢弃本条信息
fixup  i7j8k9l 又改了一下样式           ← 压进上面那条
```
保存退出后，三个提交就被"揉成"了一个干净的"实现登录功能"提交。

> 排序：交互界面里**直接上下移动这些行**，就能改变提交的先后顺序（reorder）。

#### 2.4.3 rebase 冲突处理：`--continue` / `--skip` / `--abort`

**大白话**：rebase 是把提交一个个重放，所以冲突也可能**一个提交一个提交地接连出现**。跟 merge 不同，merge 是"一次性把所有冲突摆给你"，rebase 是"重放到哪个提交撞车了就停在哪，你解决完再继续放下一个"。

流程：
```bash
git rebase main
# —— 重放某个提交时撞上冲突，rebase 暂停 ——

# 1. 像解决 merge 冲突一样，编辑冲突文件、删掉冲突标记
# 2. git add 标记已解决
git add <冲突文件>
# 3. 继续重放剩下的提交（注意：这里不是 git commit，而是 --continue）
git rebase --continue

# 如果想跳过当前这个惹麻烦的提交（比如它变成了空提交）：
git rebase --skip

# 如果想彻底放弃整个 rebase，回到变基之前的状态：
git rebase --abort
```

> 陷阱：rebase 冲突解决后是 **`git rebase --continue`**，不是 `git commit`！新手最容易在这里习惯性敲 `git commit` 而搞乱流程。记住：merge 冲突用 `commit` 收尾，rebase 冲突用 `--continue` 续跑。

#### 2.4.4 merge vs rebase 对比 + 适用场景

| 对比项 | `git merge` | `git rebase` |
|---|---|---|
| 历史形态 | 保留分叉，出现 merge commit，历史是"菱形网状" | 拉成一条直线，无 merge commit |
| 是否改写历史 | **否**，原有提交哈希不变 | **是**，被搬动的提交全部变成新哈希 |
| 真实性 | 完整、真实反映"何时分叉、何时合并" | 更整洁，但"美化"了历史，抹掉了真实分叉 |
| 冲突处理 | 一次性集中解决 | 可能逐个提交反复解决 |
| 溯源难度 | merge commit 多时看起来乱，但能追溯 | 线性历史读起来爽，但丢失了分叉信息 |
| 对协作的风险 | 安全 | 对**已推送的公共分支**用会坑队友（见黄金法则） |

**适用场景速记**：
- **想保留真实的合并记录、分支是多人协作的公共分支** → 用 **merge**（尤其 `--no-ff`）。
- **只是自己本地的功能分支，想在合入主线前把历史整理干净、追平主线** → 用 **rebase**。
- 一句话方针：**"私有分支随便 rebase 美化，公共历史一律 merge 保真。"**

#### 2.4.5 rebase 黄金法则：不要对"已推送的公共分支"做 rebase

**黄金法则（The Golden Rule of Rebasing）**：
> **绝不要对已经推送到远程、别人可能已经拉取/基于它工作的分支执行 rebase。**

**为什么？用大白话讲清因果链**：
1. rebase 会把提交**重写成全新哈希**（C3 变 C3'，原来的 C3 被抛弃）。
2. 如果这些提交你**已经 push 出去了**，同事已经把老的 C3、C4 拉到他本地，并基于它们继续开发。
3. 你 rebase 后强推（force push）把远程的 C3、C4 换成了 C3'、C4'。
4. 同事再一 pull，Git 发现"远程的历史和我本地的历史对不上了"——他本地还留着老的 C3、C4，远程却是 C3'、C4'，于是**同一份改动出现了两套提交**，历史严重分叉，冲突和重复提交满天飞，团队一片混乱。

所以：**rebase 只用在"还没推送出去、只有你自己看得见"的本地提交上**。一旦推送到公共分支被别人依赖，就只能用 `merge`（或 `revert`）这种"不改写已有历史"的方式了。

> 面试满分答法：先说 rebase 会重写提交哈希/历史，再说黄金法则是"不对已共享的公共分支 rebase"，最后点出根因——**别人已经基于旧提交工作，你改写历史会导致他们的历史与远程分叉、产生重复提交和混乱**。能把这条因果链讲顺，面试官就知道你是真懂而不是背命令。

### 2.5 git stash：临时"存档"未完成的工作

**大白话**：你正改代码改到一半（活儿没干完，不适合提交），突然要紧急切到别的分支修个 bug。这时工作区一堆改动挡着你切不过去。`git stash`（stash = 藏匿、私房钱）就像游戏里的"**临时存档**"——把当前所有没提交的改动打包塞进一个"暂存抽屉"，让工作区瞬间变回干净的样子，等你忙完再"读档"把它们原样拿回来。

```bash
# 把当前工作区 + 暂存区的改动统统"藏"起来，工作区恢复干净
git stash
# 等价的、可带说明的推荐写法（-m 加一句备注，方便以后辨认）
git stash push -m "登录功能写了一半"

# 查看所有藏起来的存档（每个存档有个编号 stash@{0}、stash@{1}...）
git stash list

# 恢复最近一次藏的改动，并把这条存档从抽屉里删掉
git stash pop

# 恢复最近一次藏的改动，但存档"留底"不删（适合想恢复到多个分支）
git stash apply

# 恢复指定的某个存档（比如第 1 号）
git stash apply stash@{1}

# 删掉某个存档
git stash drop stash@{0}

# 清空所有存档（危险，一次全删）
git stash clear
```

**`pop` vs `apply` 的区别（易错点）**：

| 命令 | 恢复改动 | 恢复后是否删除该存档 | 适用 |
|---|---|---|---|
| `git stash pop` | 是 | **是**（用完即弃） | 只想恢复到一个地方，恢复完就不要了 |
| `git stash apply` | 是 | **否**（存档保留） | 想把同一份改动应用到多个分支，或怕恢复出问题想留个底 |

**其他常用变体**：

```bash
# 默认 stash 不管"未跟踪的新文件"（还没 git add 过的新建文件）！
# 想把未跟踪文件也一起藏，加 -u（--include-untracked）
git stash -u

# 连被 .gitignore 忽略的文件也一起藏，用 -a（--all，慎用）
git stash -a

# 从某个存档直接开一个新分支，并恢复改动到这个新分支上
# （适用于：当初 stash 的基础提交后来变了，pop 会冲突时，用这招最稳）
git stash branch <新分支名> stash@{0}
```

> 常见陷阱一：**`git stash` 默认会漏掉"未跟踪的新文件"**（那些你新建、还没 `git add` 过的文件不会被藏起来，还留在工作区）。要连它们一起藏，必须加 `-u`。这是新手最常踩的坑。
> 常见陷阱二：`stash pop` 恢复时如果和当前工作区有冲突，**存档不会被自动删除**（Git 保护你，怕你没恢复成功就把存档弄丢），需要你手动解决冲突后再 `git stash drop`。

### 2.6 撤销与回退大全（本板块核心，务必讲透）

这一节是 Git 面试的"重灾区"，也是实操中最容易出事的地方。核心是三个命令：`reset`、`revert`、`restore`，外加一个清理命令 `clean`。先把它们的定位分清楚，再逐个讲。

- **`git reset`**：移动分支指针，**改写历史**（把提交"退回去"）。主要用于**本地、还没推送**的提交。
- **`git revert`**：**新增一个"反向提交"**来抵消之前的提交，**不改写历史**。用于**已推送的公共分支**。
- **`git restore`**：恢复**工作区/暂存区的文件**，不碰提交历史。
- **`git clean`**：删除**未跟踪的文件**（清理工作区垃圾）。

#### 2.6.1 `git reset` 的三种模式（`--soft` / `--mixed` / `--hard`）

**大白话**：`git reset` 干的核心事就一件——**把当前分支这个指针，向后（或任意位置）挪到某个提交上**，相当于"假装后面那几个提交没发生过"。区别在于：挪指针的同时，**要不要顺手把你的暂存区、工作区也一起改掉**。这三档"改的程度"就是 `--soft`、`--mixed`、`--hard`。

要理解它们，先记住 Git 里的"三个区域"：
- **HEAD / 提交历史**：已经提交存档的东西。
- **暂存区（Staging / Index）**：`git add` 之后、等待提交的东西。
- **工作区（Working Directory）**：你在编辑器里实际看到、正在改的文件。

三种模式对这三个区域的影响：

| 模式 | 移动 HEAD 指针 | 暂存区（Index） | 工作区（你的文件） | 通俗理解 |
|---|---|---|---|---|
| `--soft` | ✅ 移动 | ❌ 不变（改动仍在暂存区） | ❌ 不变 | "撤销提交，但改动原封不动留着、且已 add 好，随时能重新提交" |
| `--mixed`（**默认**） | ✅ 移动 | ✅ 清空（改动退回工作区，变未暂存） | ❌ 不变 | "撤销提交 + 撤销 add，改动还在文件里，但要重新 add" |
| `--hard` | ✅ 移动 | ✅ 清空 | ✅ **一起重置（改动被彻底丢弃！）** | "撤销提交 + 丢光所有改动，工作区变回那个提交的样子（危险）" |

用图理解，假设现在是：
```
   C1 ── C2 ── C3   ← main / HEAD（C3 是最新提交）
```
执行 `git reset --xxx C2`（把指针退回 C2）后，三种模式的差别只在"C3 那些改动去哪了"：

```
   C1 ── C2   ← main / HEAD    （C3 这个提交都被"甩掉"了）

  --soft ：C3 的改动 → 还乖乖待在【暂存区】，git status 显示"待提交"
  --mixed：C3 的改动 → 退回【工作区】，git status 显示"改动未暂存"
  --hard ：C3 的改动 → 直接【蒸发】，工作区干净得像 C3 从没存在过
```

命令示例：

```bash
# 撤销最近 1 次提交，但改动全保留并已暂存（常用于：提交早了，想重新组织再提交）
git reset --soft HEAD~1

# 撤销最近 1 次提交，改动退回工作区、需重新 add（默认模式，最常用）
git reset HEAD~1            # 不写 --mixed 就是 --mixed
git reset --mixed HEAD~1   # 等价写法

# 撤销最近 1 次提交，并彻底丢弃改动（危险！确定不要了才用）
git reset --hard HEAD~1

# reset 还能用来"取消暂存"某个文件（把 add 撤销，等价于 restore --staged）
git reset HEAD file.txt
```

> `HEAD~1` 什么意思？`HEAD` 是当前提交，`HEAD~1` 是它的上一个提交，`HEAD~2` 是上上个，以此类推。所以 `reset HEAD~1` = "退回到上一个提交"。

> **常见陷阱（血泪教训）**：`git reset --hard` 会**不留痕迹地删掉工作区里所有未提交的改动**，没有回收站、没有二次确认。跑之前务必确认这些改动你真的不要了。**万一手滑用 `--hard` 丢了已提交的东西，还能靠 `git reflog` 找回被甩掉的提交（见 2.9）；但纯工作区里从没提交过的改动，reflog 也救不了。**

> **黄金原则**：`git reset` 会改写历史，**只在本地、还没 push 的提交上使用**。已经推送到公共分支的提交，请改用下面的 `git revert`。

#### 2.6.2 `git revert`：安全撤销"已推送"的提交

**大白话**：`revert`（还原、撤销）不删除历史，而是**新做一个提交，这个提交的内容正好和你要撤销的那个提交"相反"**——你之前加了一行，它就删掉那一行；你之前删了个文件，它就把文件加回来。相当于"用一次新的提交，抵消掉旧提交的效果"，历史记录里两个提交都还在，谁都能看到"这里做过一件事，又被撤销了"。

```
   C1 ── C2 ── C3   ← main（想撤销 C2 的改动）
```
执行 `git revert C2` 后：
```
   C1 ── C2 ── C3 ── C2'   ← main
   （C2' 是新提交，效果与 C2 完全相反，等于把 C2 的改动抵消了）
```

```bash
# 撤销某个提交（会生成一个反向的新提交，弹出编辑器让你确认提交信息）
git revert <commit哈希>

# 撤销最近一次提交
git revert HEAD

# 撤销但先不自动提交，想把多个 revert 攒一起再一次提交
git revert -n <commit哈希>     # -n = --no-commit
```

**`reset` vs `revert` 对比（超高频面试题）**：

| 对比项 | `git reset` | `git revert` |
|---|---|---|
| 做法 | 移动分支指针，**抹掉**后面的提交 | **新增一个反向提交**来抵消 |
| 是否改写历史 | **是**（历史被改写） | **否**（老提交都还在，只是多了个抵消提交） |
| 历史记录 | 被撤销的提交从历史上消失 | 保留完整痕迹（做过 + 撤销过都看得见） |
| 适用场景 | **本地、未推送**的提交 | **已推送的公共分支** |
| 对协作的影响 | 用在公共分支会坑队友（需强推） | 安全，正常 push 即可，不影响别人 |
| 能否撤销中间某个提交 | 不方便（会连带影响后面的） | 方便，可精准撤销历史中任意一个 |

> 一句话记忆：**"私有的、没推的用 reset 抹掉；公共的、推了的用 revert 抵消。"**

#### 2.6.3 `git restore`：新命令，专管恢复文件

**大白话**：前面说过 Git 2.23 把 `checkout` 拆了家，`restore`（恢复、还原）就是接手"恢复文件"这摊活的新命令。它**只管工作区和暂存区里的文件，绝不碰提交历史**，所以比 `reset`/`checkout` 安全、语义清晰。

```bash
# 丢弃某个文件在【工作区】的未提交改动，恢复成最近一次提交的样子
# （相当于旧的 git checkout -- file.txt，但语义更明确）
git restore file.txt

# 取消暂存：把已经 git add 的文件从暂存区撤回（但工作区改动保留）
# （相当于旧的 git reset HEAD file.txt）
git restore --staged file.txt

# 把文件恢复成"某个特定提交"里的版本
git restore --source=HEAD~2 file.txt

# 丢弃工作区所有文件的改动（危险，不可逆）
git restore .
```

`restore` 两个常用姿势对照记忆：

| 需求 | 命令 | 老写法 |
|---|---|---|
| 丢弃工作区某文件的改动 | `git restore file` | `git checkout -- file` |
| 取消某文件的暂存（撤销 add） | `git restore --staged file` | `git reset HEAD file` |

> 陷阱：`git restore file.txt`（不带 `--staged`）会**直接丢弃工作区未提交的改动，不可恢复**。和 `checkout -- ` 一样危险，跑之前想清楚。

#### 2.6.4 `git clean`：清除"未跟踪的文件"

**大白话**：`git clean` 专门用来打扫工作区里那些**"从没被 Git 管过"的文件**——比如编译出来的临时产物、你随手新建还没 `add` 的文件。注意它管的是**未跟踪（untracked）文件**，`reset`/`restore` 那些命令是碰不到未跟踪文件的，得靠它。

```bash
# 【强烈建议先跑这个】-n = --dry-run，只"预览"会删哪些，并不真删！
git clean -n

# -f = --force，真正删除未跟踪的文件（Git 默认要求加 -f 才肯删，防手滑）
git clean -f

# -d：连同未跟踪的空目录一起删
git clean -fd

# -x：连 .gitignore 里忽略的文件也一起删（比如 node_modules、build 产物）
git clean -fdx
```

> **常见陷阱（危险命令）**：`git clean -f` 删掉的文件是**未跟踪的**，Git 从没记录过它们，所以**删了就是彻底没了，reflog 也救不回来**（reflog 只管提交，管不了没进过 Git 的文件）。铁律：**跑 `git clean` 之前，永远先 `git clean -n` 预览一遍**，确认清单没问题再加 `-f`。尤其 `-x` 会把 `node_modules`、构建产物一并清掉，威力巨大。

#### 2.6.5 "我想撤销 XX" 场景速查小表（收藏级）

| 我想…… | 用这个命令 |
|---|---|
| 丢弃某个文件工作区的改动（还没 add） | `git restore file` |
| 取消某个文件的 add（撤销暂存，改动保留） | `git restore --staged file` |
| 撤销上一次提交，但改动留着待重新提交 | `git reset --soft HEAD~1` |
| 撤销上一次提交，改动退回工作区重新整理 | `git reset HEAD~1`（默认 mixed） |
| 撤销上一次提交，且彻底不要那些改动 | `git reset --hard HEAD~1`（危险） |
| 只改上一次提交的信息或补点东西进去 | `git commit --amend`（见 2.10） |
| 撤销一个**已经推送**的公共提交 | `git revert <commit>` |
| 删掉工作区里未跟踪的临时文件 | `git clean -n` 预览 → `git clean -fd` |
| 临时收起没写完的活儿去切分支 | `git stash`（见 2.5） |
| 找回被 `reset --hard` 丢掉的提交 | `git reflog` + `git reset`（见 2.9） |

### 2.7 git cherry-pick：精准"挑拣"某个提交

**大白话**：cherry-pick 直译是"挑樱桃"——从一大串提交里，**单独挑出你想要的那一个（或几个）提交，把它的改动复制一份、应用到你当前所在的分支上**。最典型的用途：一个紧急 bug 修复（hotfix）先在某个分支上改好了，你想把"就这一个修复提交"也搬到其他分支（比如同时打到 main 和正在开发的 release 分支），又不想把整条分支合并过来，就用它。

```
   main:     A ── B ── C
   hotfix:   A ── B ── D   ← D 是那个修复提交
```
在 main 上执行 `git cherry-pick D` 后：
```
   main:     A ── B ── C ── D'   ← D' 是 D 的"复制品"，改动一样，新哈希
```

```bash
# 把某个提交摘到当前分支
git cherry-pick <commit哈希>

# 一次摘多个提交
git cherry-pick <commit1> <commit2> <commit3>

# 摘一段连续的提交（从 A 之后到 B，注意 A 本身不含，是"左开右闭"）
git cherry-pick A..B
# 想连 A 也包含进来，用 A^（A 的父提交）做起点：
git cherry-pick A^..B

# 冲突处理：和 rebase 一样的三件套
git cherry-pick --continue   # 解决冲突并 add 后，继续
git cherry-pick --skip       # 跳过当前这个
git cherry-pick --abort      # 放弃整个 cherry-pick

# -x：在生成的提交信息里自动记一句"(cherry picked from commit 原哈希)"
# 方便日后追溯这个改动是从哪儿摘来的，团队协作强烈建议加
git cherry-pick -x <commit哈希>
```

> 陷阱一：cherry-pick 出来的是**新提交、新哈希**（和 rebase 一个道理），不是同一个提交。所以同一个修复被 cherry-pick 到多个分支后，日后如果这些分支再合并，可能出现"同一改动的两个提交"，偶尔会引起小冲突。
> 陷阱二：如果要挑的提交依赖它前面的某些改动（比如 D 用到了 C 里加的函数），单独 pick D 可能会因为缺上下文而冲突或报错。挑之前想清楚这个提交是不是"自洽独立"的。

### 2.8 标签 tag：给重要提交贴"里程碑标记"

**大白话**：标签（tag）就是给某个提交贴一个**永久的、不会移动的名字牌**，通常用来标记版本发布点，比如 `v1.0.0`、`v2.3.1`。它和分支的最大区别是：**分支会随着新提交不断往前移动，标签一旦贴上就死死钉在那个提交上、永远不动**。运维发版时"这次上线的是哪个版本"，靠的就是 tag。

**两种标签：轻量标签 vs 附注标签**

| 类型 | 轻量标签（lightweight） | 附注标签（annotated） |
|---|---|---|
| 本质 | 只是一个指向 commit 的名字（像便利贴） | 一个完整的 Git 对象，**额外存了打标签的人、日期、说明信息，还能签名** |
| 创建 | `git tag v1.0` | `git tag -a v1.0 -m "正式发布 1.0"` |
| 适用 | 临时/私人用的小标记 | **正式发版**（推荐，信息完整可追溯） |

```bash
# —— 轻量标签 ——
git tag v1.0                       # 给当前提交（HEAD）打个轻量标签

# —— 附注标签（发版推荐）——
git tag -a v1.0 -m "正式发布 1.0 版本"   # -a=annotated，-m 写说明

# 给"历史上某个提交"补打标签（在末尾加上那个提交的哈希）
git tag -a v0.9 -m "补标 0.9" <commit哈希>

# 查看所有标签
git tag
# 按模式筛选标签
git tag -l "v1.*"
# 查看某个标签的详细信息（附注标签会显示打标签人、日期、说明）
git show v1.0

# 删除本地标签
git tag -d v1.0
```

**推送标签到远程（重点，易踩坑）**：

```bash
# 陷阱：git push 默认【不会】推送标签！必须显式推
git push origin v1.0          # 推送单个标签
git push origin --tags        # 一次推送所有本地标签

# 删除远程标签（语法有点反直觉，记一下）
git push origin --delete v1.0
# 或旧写法：git push origin :refs/tags/v1.0
```

**检出标签（会进入 detached HEAD 状态）**：

```bash
git checkout v1.0
# 或新命令：
git switch --detach v1.0
```

> **"分离头指针（detached HEAD）"是什么？** 大白话：正常你站在一个"分支"上，HEAD 指着分支、分支指着提交。但标签不是分支，检出标签时 HEAD 就**直接指向那个提交本身、没有分支托着它**了，这就叫"分离头指针"。此时你**可以看、可以编译，但如果在这儿做了新提交，这些提交不属于任何分支，一旦切走就可能变成"孤儿"被回收丢失**。
> 正确做法：想基于某个标签继续开发，先从它拉一个分支出来再干活：
> ```bash
> git switch -c hotfix-1.0 v1.0    # 基于 v1.0 标签新建分支，在分支上安全地改
> ```

> 面试常见问题："tag 和 branch 有什么区别？"——**branch 是会随提交移动的指针（用于开发线），tag 是钉死不动的标记（用于标注版本/里程碑）**；此外附注标签还携带打标签人、时间、说明等元信息。

### 2.9 找回与排查工具（reflog / bisect / blame）

#### 2.9.1 `git reflog`：后悔药，找回"丢失"的提交（面试神题）

**大白话**：`reflog`（reference log，引用日志）是 Git 偷偷给你记的一本"**流水账**"——**你每一次让 HEAD 移动的操作**（提交、切分支、merge、rebase、`reset --hard`……）它都悄悄记了一笔，包括移动前指向哪。所以哪怕你 `reset --hard` 把提交甩没了、或者误删了分支，只要那些提交还没被垃圾回收，就能**在这本流水账里找到它的哈希，再把指针挪回去，完成"起死回生"**。

```bash
# 查看 HEAD 的移动流水账（最近的操作在最上面）
git reflog
```
输出长这样：
```
a1b2c3d HEAD@{0}: reset: moving to HEAD~1     ← 就是这一步把提交甩掉的
e4f5g6h HEAD@{1}: commit: 我误删的那个重要提交   ← 这就是要找回的！
i7j8k9l HEAD@{2}: commit: 前一个提交
```

**实战：找回被 `reset --hard` 丢掉的提交**
```bash
# 1. 打开 reflog，找到你想回到的那个提交的哈希（比如上面的 e4f5g6h）
git reflog

# 2. 把当前分支硬重置回那个提交，提交就回来了
git reset --hard e4f5g6h
# 或者更稳妥：基于它开个新分支，避免再动到当前分支
git switch -c recovered e4f5g6h
```

**实战：找回误删的分支**
```bash
# 分支被 git branch -D feature 删了，但它最后指向的提交还在 reflog 里
git reflog                      # 找到 feature 被删前指向的那个提交哈希
git switch -c feature <那个哈希>  # 用这个哈希重建分支，改动全回来了
```

> 面试满分点：被问"误用 `git reset --hard` / 误删了分支，代码还能救吗？"标准答案是——**能，用 `git reflog`**。原理是 Git 会记录 HEAD/分支的每一次移动历史，被"甩掉"的提交在被垃圾回收（默认约 30~90 天）之前依然物理存在，reflog 里能查到它的哈希，据此 `reset` 或新建分支即可找回。能答出"reflog + 未被 gc 回收"这两个词就是内行。
> 边界：reflog **只能救"曾经被提交过"的东西**。从没 `commit`、从没进过 Git 的纯工作区改动（比如被 `git clean` 删掉的未跟踪文件），reflog 无能为力。

#### 2.9.2 `git bisect`：二分法定位"哪个提交引入了 bug"

**大白话**：假设你的项目原来好好的，某天发现有个 bug，但中间已经积了几百个提交，不知道是哪次改坏的。一个个试太慢。`bisect`（bisect = 二分、对半分）用**二分查找**帮你快速定位：你告诉它一个"确定是好的"旧提交和一个"确定是坏的"新提交，它自动跳到正中间那个提交让你测试，你回答"这里好还是坏"，它据此再折半……几步就能从几百个提交里精准揪出"第一个变坏的那个提交"。几百个提交，大概测 8~9 次就能定位（log₂）。

```bash
# 1. 开始二分
git bisect start

# 2. 标记当前提交是"坏的"（有 bug）
git bisect bad

# 3. 标记一个你确定"好的"旧提交（比如某个老版本 tag 或哈希）
git bisect good v1.0
#    —— 此时 Git 自动 checkout 到正中间的某个提交，等你测试 ——

# 4. 你去编译/运行/测试当前这个提交，然后如实回答：
git bisect good     # 如果这个提交没问题
git bisect bad      # 如果这个提交有 bug
#    —— Git 根据你的回答继续折半，跳到下一个待测提交，重复第 4 步 ——

# 5. 反复几轮后，Git 会打印："<某哈希> is the first bad commit"，凶手锁定！

# 6. 结束二分，回到你原来的分支
git bisect reset
```

**自动化（进阶，很酷）**：如果你能写一个"测试脚本"（bug 存在时返回非 0，正常时返回 0），可以让 bisect 全自动跑完：
```bash
git bisect start HEAD v1.0        # HEAD 是坏的，v1.0 是好的
git bisect run ./test.sh          # 自动对每个中点跑脚本，直到揪出凶手
git bisect reset
```

> 面试价值：`git bisect` 是体现"排障能力"的加分项。能说清"**用二分查找在 O(log n) 次测试内定位首个引入 bug 的提交，还能配合 `git bisect run` 全自动化**"，会显得很专业。

#### 2.9.3 `git blame`：逐行追溯"这行是谁、哪次提交写的"

**大白话**：`blame`（字面意思"责怪"，但实际是中性的"溯源"）能把一个文件的**每一行**都标注上：这行最后一次是**谁、在哪个提交、什么时候**改的。排查"这段奇怪的代码是谁加的、为什么加"时特别有用——找到那个提交再 `git show` 看它当时的完整改动和提交说明。

```bash
# 查看某文件每一行的最后修改者和提交
git blame app.py

# 只看某文件第 20 到 40 行（-L = line 范围）
git blame -L 20,40 app.py

# 忽略纯空白/缩进改动的干扰（-w），更容易找到"真正改逻辑"的那次提交
git blame -w app.py
```
输出每行大致是：`提交哈希 (作者 日期 行号) 这一行的代码`。找到可疑提交哈希后：
```bash
git show <那个哈希>     # 看这个提交完整改了什么、提交信息写了啥
```

> 小提示：blame 显示的是"每行**最后一次**被改动"的提交，不代表这行第一次是谁写的。要深挖某行的完整变更历史，可以配合 `git log -L :函数名:文件` 追踪某段代码的演化。

### 2.10 修改历史注意事项（amend / force push）

#### 2.10.1 `git commit --amend`：修补"最后一次提交"

**大白话**：`amend`（修正、修订）专治"提交刚发出去就后悔"——比如提交信息打错字了，或者发现漏加了一个文件。它能让你**修改最近的那一次提交**：改提交说明，或把新的改动补进去，而**不会新增一个提交**，看起来就像上次那个提交本来就是这样。

```bash
# 只改最近一次提交的信息（message）——打开编辑器让你改
git commit --amend

# 改信息且不打开编辑器，直接给新信息
git commit --amend -m "修正后的提交信息"

# 漏提交了一个文件？先 add 上，再 amend 补进上一次提交
git add 漏掉的文件.py
git commit --amend --no-edit    # --no-edit 表示信息不变，只把文件补进去
```

> **关键陷阱**：`--amend` 看起来是"修改"，但它实际上是**用一个全新的提交替换掉了原来的最后一次提交**（新提交、新哈希，老提交被抛弃）。这本质上也是**改写历史**！所以——**只对"还没 push 出去"的最后一次提交用 amend**。如果那个提交已经推送到公共分支，amend 后本地和远程就对不上了，push 会被拒绝，只能强推，于是又回到了"改写公共历史坑队友"的老问题。

#### 2.10.2 改写历史后的 force push 风险与 `--force-with-lease`

**大白话**：只要你用了 rebase、amend、`reset` 等**改写了已经推送过的提交**，本地历史就和远程"分叉对不上"了。这时普通 `git push` 会被 Git 拒绝（"你的历史和远程冲突，我不敢推"）。要推上去就得**强推（force push）**，等于用你本地的历史**强行覆盖**远程的历史。

强推有两个层次，安全性天差地别：

| 命令 | 行为 | 风险 |
|---|---|---|
| `git push --force`（或 `-f`） | **无条件**用本地覆盖远程，不管远程这期间有没有别人的新提交 | **危险**：如果你 fetch 之后、push 之前，同事往远程推了新提交，`--force` 会把同事的提交**直接覆盖掉、彻底丢失** |
| `git push --force-with-lease` | 推之前先检查"远程还是不是我上次看到的样子"，**只有远程没被别人动过才覆盖**，否则拒绝 | **相对安全**：如果同事偷偷推了新东西，它会拒绝推送并提醒你，避免误覆盖别人的工作 |

```bash
# 危险：无脑覆盖远程，可能吃掉别人的提交
git push --force

# 推荐：带"租约"检查的安全强推
git push --force-with-lease
```

> `--force-with-lease` 的"lease（租约）"怎么理解？大白话：你上次 fetch 时"租下"了远程当时的状态记在本地，强推前 Git 拿这个"租约状态"和远程现状核对——**只要远程还是你租约里那个样子（没人动过），就允许覆盖；一旦发现远程变了（有人推了新东西），就说明有人在你不知情时改了远程，拒绝推送、保护那个人的工作**。

> **面试满分总结**：能说出这条完整逻辑就很加分——"**rebase / amend / reset 会改写提交历史，推送已改写的历史需要 force push；但 `--force` 会无条件覆盖远程、可能吃掉同事的新提交，所以生产中应改用 `--force-with-lease`，它只在远程未被他人更新时才覆盖，更安全**。"再叠加 2.4.5 的黄金法则——**能不改写公共历史就别改**，非改不可时用 `--force-with-lease` 兜底，就是一套完整、专业的回答。

### 3.1 Git 的本质：一个「内容寻址的文件系统」

#### 大白话先建立直观印象

想象有一个巨大的储物柜，你往里放任何一件东西，它不给你一个「柜子编号」，而是**根据东西的内容算出一串指纹**，用这串指纹当钥匙。以后你只要报出这串指纹，它就能把原封不动的东西还给你。内容一样的东西，指纹永远一样，所以同样的东西不会存两份。

Git 的核心就是这么一个储物柜，学名叫**内容寻址存储（content-addressable storage）**。

- 「寻址」= 找东西的方式。
- 「内容寻址」= **用「内容算出来的哈希」当地址**，而不是用「文件名/路径」当地址。

普通文件系统是「按位置找」：你告诉它 `/home/xyz/a.txt`，它去那个位置取。Git 是「按内容找」：你告诉它 `d670460b...`（内容的指纹），它去取对应内容。文件名只是记在另一张表里的「标签」，不是本质。

#### 关键澄清：Git 存的是「快照」，不是「差异」

这是面试高频、也是初学者最常见的误解。

很多人以为 Git 是这样存的（**这是错的**）：

```
版本1: 完整文件 a.txt
版本2: 只存 a.txt 的第 3 行改成了 "hello"   ← 存差异 diff
版本3: 只存 a.txt 删了第 5 行              ← 存差异 diff
```

上面这种「只存每次改了哪几行」的模型，是 SVN、CVS 等老式版本控制的做法，叫 **delta-based / 差异存储**。

**Git 不是这样。** Git 每次提交，都是给「当前整个项目的文件树」拍一张**完整快照（snapshot）**：这一版里每个文件的完整内容，都作为对象存下来（通过哈希去重）。

```
差异模型（SVN 等）：            快照模型（Git）：
版本1 ── Δ1 ── Δ2 ── Δ3        版本1: 记录 {a.txt→内容A, b.txt→内容B}
        （链式存增量）            版本2: 记录 {a.txt→内容A, b.txt→内容C}
                                版本3: 记录 {a.txt→内容D, b.txt→内容C}
                                      （每次都是一整套「文件→内容」的映射）
```

关键点：**如果某个文件这一版没变，Git 不会重新存它的内容**，而是让新快照里那个文件「指向」上一版已经存在的同一个内容对象（因为内容一样→哈希一样→本来就是同一个对象）。所以「拍完整快照」并不浪费空间，靠的正是「内容寻址天然去重」。

> 面试话术：Git 存的是「一系列文件树的快照」，通过内容哈希在对象层面去重；差异只是**展示**时临时算出来的，不是**存储**方式。

#### 那为什么 `git log`、`git diff` 看起来全是「差异」？

因为「怎么存」和「怎么给你看」是两回事。

`git diff`、`git log -p` 展示的「+/- 若干行」，是 Git 在你运行命令的那一刻，**拿两个快照临时对比、现场算出来的**，算完显示给你看，并不代表它是这样存的。就像你有两张照片，随时可以对比出「这两张哪里不一样」，但你存的是两张完整照片，不是「不一样的地方」。

（补充一句：3.8 会讲到，Git 在**打包压缩**时确实会用 delta 压缩来省空间——但那是存储层的「压缩优化」，和「版本模型是快照」不冲突。逻辑上每个版本仍是完整快照，delta 只是物理存盘时的压缩手段。这两个层次别混。）

### 3.2 `.git` 目录结构详解：仓库的全部家当都在这

你 `git init` 之后，所有版本信息都藏在项目根目录下那个 `.git` 文件夹里。**把 `.git` 删了，仓库就退化成一堆普通文件；把 `.git` 完整拷走，历史就全带走了。** 它就是仓库本体。

看一眼结构：

```bash
ls -F .git
# 预期能看到（不同版本略有差异）：
# HEAD  config  description  hooks/  info/  objects/  refs/
```

随着你开始提交，还会陆续冒出 `index`、`logs/`、`COMMIT_EDITMSG`、`packed-refs` 等。逐个说明：

```
.git/
├── HEAD              ← 【核心】指针，记录"我现在在哪个分支/哪个提交上"
│                        内容通常是一行：ref: refs/heads/master
├── config            ← 本仓库的配置（远程地址、用户名、别名等）
├── description       ← 仓库描述，只有老式 GitWeb 网页界面才用，平时无视
├── index             ← 【核心】暂存区（staging area），二进制文件，见 3.6
├── objects/          ← 【核心】对象数据库，所有 blob/tree/commit/tag 都存这
│   ├── ab/           ← 松散对象：哈希前 2 位当目录名
│   │   └── cdef...   ← 剩下 38 位当文件名，内容是 zlib 压缩后的对象
│   ├── pack/         ← 打包对象：.pack 数据包 + .idx 索引（见 3.8）
│   └── info/         ← 对象库的辅助信息
├── refs/             ← 【核心】各种"引用"，本质是存着某个哈希的小文本文件
│   ├── heads/        ← 本地分支：refs/heads/master 里存 master 指向的 commit 哈希
│   ├── tags/         ← 标签
│   └── remotes/      ← 远程分支的本地镜像，如 refs/remotes/origin/master
├── packed-refs       ← 把大量 refs 打包进一个文件（refs 太多时的优化）
├── logs/             ← 【核心】引用移动的历史日志，reflog 的数据来源（见 3.9）
│   ├── HEAD          ← HEAD 每次移动都记一行
│   └── refs/heads/*  ← 每个分支各自的移动历史
├── hooks/            ← 钩子脚本模板（pre-commit 等），本板块不展开
├── info/exclude      ← 类似 .gitignore，但不纳入版本控制的本地忽略规则
├── COMMIT_EDITMSG    ← 上一次提交信息的暂存文件（编辑器里写的那段）
└── ORIG_HEAD         ← 危险操作（reset/merge/rebase）前 HEAD 的旧位置备份
```

后面几节会把带「核心」标记的这几个（objects、refs、HEAD、index、logs）一个个讲透。你可以随时用 `cat` 去偷看它们：

```bash
cat .git/HEAD
# 预期输出：ref: refs/heads/master   （说明你现在在 master 分支上）
```

看，`HEAD` 就是一个只有一行字的普通文本文件。Git 的「神奇」很多时候就是这么朴素。

### 3.3 四种对象：Git 世界的四种「原子」

Git 对象库（`.git/objects/`）里只存四种东西，理解了它们，就理解了 Git 的一大半。

| 对象类型 | 大白话 | 存了什么 |
|---|---|---|
| **blob** | 一个文件的「内容本身」 | 纯文件内容（不含文件名！） |
| **tree** | 一个「目录」 | 一层目录下有哪些文件/子目录，各自叫什么名、什么权限、指向哪个对象 |
| **commit** | 一次「提交/快照」 | 指向一个 tree（本次快照的根目录）+ 父提交 + 作者 + 时间 + 提交信息 |
| **tag** | 一个「附注标签」 | 指向某个对象（通常是 commit）+ 标签名 + 打标签的人 + 说明 |

关键工具（一定要记住这三条）：

- `git hash-object`：把内容算成哈希（加 `-w` 顺便写进对象库）。
- `git cat-file -t <哈希>`：看这个对象是**什么类型**（type）。
- `git cat-file -p <哈希>`：**漂亮地打印**这个对象的内容（pretty print）。

#### 3.3.1 blob：文件内容

blob = binary large object，可以理解成「一坨文件内容」。注意：**blob 里只有内容，不含文件名**。文件名是记在 tree 里的（下一节讲）。

亲手造一个 blob：

```bash
echo 'test content' | git hash-object -w --stdin
# 预期输出：d670460b4b4aece5915caf5c68d12f560a9fe3e4
```

这一串 40 位十六进制就是这段内容的「指纹」（SHA-1 哈希）。`-w` 让它真的写进 `.git/objects/`，`--stdin` 表示内容从标准输入读。

验证它确实存进去了、类型是 blob、内容能读回来：

```bash
git cat-file -t d670460b4b4aece5915caf5c68d12f560a9fe3e4
# 预期输出：blob

git cat-file -p d670460b4b4aece5915caf5c68d12f560a9fe3e4
# 预期输出：test content
```

再去磁盘上找到它本人：

```bash
ls .git/objects/d6/
# 预期输出：70460b4b4aece5915caf5c68d12f560a9fe3e4
# （前 2 位 d6 当目录名，后 38 位当文件名，拼起来正好是完整哈希）
```

这个文件的内容是 zlib 压缩过的二进制，直接 `cat` 是乱码，必须用 `git cat-file` 解读——这就是「松散对象」的样子（3.8 细讲）。

#### 3.3.2 tree：目录结构

tree = 「一层目录」的清单。它把「文件名 → blob」、「子目录名 → 子 tree」的对应关系记下来，还带上每个条目的权限模式。**没有 tree，blob 就是一堆没名字的内容，谁也不知道哪坨是 `a.txt`。**

我们用暂存区来快速造一个 tree（`git add` 会把文件写成 blob 并登记进 index，`git write-tree` 再把 index 定型成一个 tree 对象——这里先照做，3.6 再讲原理）：

```bash
echo 'hello'  > a.txt
echo 'world'  > b.txt
git add a.txt b.txt
git write-tree
# 预期输出（一个 tree 的哈希，例如）：
# 88e38705fdbd3608cddbe904b67c731f3234c45b
```

打印这个 tree 看看它长什么样：

```bash
git cat-file -p 88e38705fdbd3608cddbe904b67c731f3234c45b
# 预期输出（每行一个条目）：
# 100644 blob ce013625030ba8dba906f756967f9e9ca394464a    a.txt
# 100644 blob cc628ccd10742baea8241c5924df992b5c019f71    b.txt
```

逐列看懂这张表：

```
100644        blob        ce013625...          a.txt
└─权限模式    └─条目类型   └─指向的对象哈希      └─在这一层里叫什么名
  (普通文件)  (blob=文件)   (a.txt 的内容 blob)   (文件名记在这里！)
```

权限模式常见值：`100644` 普通文件、`100755` 可执行文件、`120000` 符号链接、`040000` 子目录（此时条目类型是 tree，不是 blob）。

也可以用专门的命令看 tree，更直观：

```bash
git ls-tree 88e38705fdbd3608cddbe904b67c731f3234c45b
# 输出同上
```

**tree 可以嵌套**：如果目录里有子目录，条目里就会出现一个 `040000 tree <哈希> 子目录名`，那个子哈希又是另一个 tree。于是整个项目目录树，就被表示成「tree 套 tree 套 blob」的层级结构。

#### 3.3.3 commit：一次快照 + 元数据 + 父指针

有了 tree（某一刻整个项目根目录的样子），再包一层「谁、什么时候、为什么、上一版是谁」的信息，就成了 commit。

先真正提交一次：

```bash
git commit -m "first commit"
# 预期输出：[master (root-commit) 1a2b3c4] first commit ...
```

看最新提交对应的 commit 对象内容（`HEAD` 指向它，可以直接用 `HEAD` 代替哈希）：

```bash
git cat-file -p HEAD
# 预期输出（大致如下）：
# tree 88e38705fdbd3608cddbe904b67c731f3234c45b
# author  姚金盟 <jinmeng.yao@xyzrobotics.com> 1756339200 +0800
# committer 姚金盟 <jinmeng.yao@xyzrobotics.com> 1756339200 +0800
#
# first commit
```

一个 commit 对象里就这么几样东西：

- `tree`：指向本次快照的**根目录 tree**。这是「这次提交时，整个项目长什么样」的入口。
- `parent`：指向**父提交**（上一个 commit）。第一个提交没有父，所以上面没有 parent 行；第二个提交起会有一行 `parent <哈希>`；合并提交（merge）会有**两行 parent**（3.11 讲）。
- `author` / `committer`：作者、提交者、时间戳。
- 空行之后：**提交信息**（你 `-m` 写的那句话）。

注意：**commit 里没有直接存文件内容，只存了一个 tree 哈希**。文件内容藏在 tree 指向的 blob 里。这正是「快照」的实现方式——commit 只是「指向某棵完整文件树的一个带元数据的把手」。

#### 3.3.4 tag：附注标签对象

标签有两种：

- **轻量标签（lightweight）**：本质就是 `refs/tags/` 下一个存着 commit 哈希的小文件，**不产生新对象**，跟分支类似只是不会移动。
- **附注标签（annotated）**：会创建一个**真正的 tag 对象**，里面记录「指向哪个对象、标签名、打标签的人、时间、说明」，还能被 GPG 签名。发布版本一般用这种。

造一个附注标签看看：

```bash
git tag -a v1.0 -m "release 1.0"
git cat-file -t v1.0
# 预期输出：tag        ← 说明它是一个真正的 tag 对象

git cat-file -p v1.0
# 预期输出：
# object 1a2b3c4...        ← 指向的对象（这里是那个 commit）
# type commit
# tag v1.0
# tagger 姚金盟 <...> 1756339200 +0800
#
# release 1.0
```

#### 3.3.5 把四种对象连成图：commit → tree → blob

现在把上面造的东西串起来。假设项目里有 `a.txt`、`b.txt`，还有个子目录 `src/main.c`，整张对象图长这样：

```
        ┌───────────────────────────────┐
 tag ──▶│ commit  1a2b3c4                │
(v1.0)  │  tree   → 88e3870             │──┐
        │  parent → (上一个 commit 或无) │  │
        │  author / message ...          │  │
        └───────────────────────────────┘  │
                                            ▼
                              ┌───────────────────────────┐
                              │ tree  88e3870 (根目录)      │
                              │  100644 blob ce01362  a.txt│──────┐
                              │  100644 blob cc628cc  b.txt│───┐  │
                              │  040000 tree f00dbab  src/ │─┐ │  │
                              └───────────────────────────┘ │ │  │
                                                            ▼ │  │
                                    ┌──────────────────────┐ │  │
                                    │ tree f00dbab (src/)   │ │  │
                                    │ 100644 blob 9a8b main.c│─┼──┼──┐
                                    └──────────────────────┘ │  │  │
                                                              ▼  ▼  ▼
                                              ┌───────┐ ┌───────┐ ┌───────┐
                                              │ blob  │ │ blob  │ │ blob  │
                                              │cc628cc│ │ce01362│ │ 9a8b… │
                                              │"world"│ │"hello"│ │main.c │
                                              └───────┘ └───────┘ │ 内容  │
                                                                  └───────┘
```

一句话记住这张图的方向：**commit 指向一棵 tree，tree 指向 blob 和子 tree，blob 是内容的叶子；tag 指向 commit；commit 之间用 parent 串成历史链。** 整个 Git 仓库，就是这样一张由哈希连起来的对象图（有向无环图 DAG）。

### 3.4 哈希与内容寻址：40 位指纹是怎么来的

#### 大白话

前面那些 `d670460b...` 是怎么算出来的？不是随机编号，而是**对「对象内容」做一次哈希运算**得到的指纹。同样的输入，永远得到同样的指纹；输入差一个字节，指纹面目全非。

#### 计算规则：不是只哈希内容，还要加个「小帽子」

Git 算对象哈希时，用的公式是：

```
对象存储格式 =  "<类型> <内容字节数>\0"  +  <内容本身>
                └──────── 头部 header ────┘
哈希 = SHA-1( 上面这一整串 )
```

其中 `\0` 是一个 ASCII 值为 0 的空字节，用来分隔头部和内容。

我们手动验证 blob `d670460b...` 到底是不是这么算的。前面 `echo 'test content'` 因为 echo 会自动加个换行，实际内容是 `test content\n`，共 **13** 个字节，所以头部是 `blob 13\0`：

```bash
printf 'blob 13\0test content\n' | sha1sum
# 预期输出：d670460b4b4aece5915caf5c68d12f560a9fe3e4  -
```

看，和 3.3.1 里 `git hash-object` 给的哈希**一模一样**。这说明：Git 的哈希没有任何黑魔法，就是「类型 + 长度 + \0 + 内容」做 SHA-1。你完全可以脱离 Git 自己算出来。

（tree、commit 的头部分别是 `tree <长度>\0...`、`commit <长度>\0...`，规则相同，只是内容的组织格式不同。）

#### 相同内容 → 相同哈希 → 天然去重

因为哈希只由内容决定，所以：

- 两个不同文件如果内容完全一样，它们的 blob 哈希相同，**在对象库里只存一份**。
- 某个文件在 100 次提交里都没改过，这 100 个快照里它都指向**同一个 blob**，不会存 100 份。
- 甚至两个毫不相干的仓库，只要有一段内容一样，算出来的哈希也一样。

这就是 3.1 说的「拍完整快照却不浪费空间」的底层保证——**内容寻址自带去重**。

顺带一提：这也是 Git 数据**完整性**的来源。哈希由内容算出，任何一个字节被悄悄改动，哈希都对不上，Git 立刻能发现数据损坏。Git 里「用哈希指来指去」的结构，本质是一棵 Merkle 树（默克尔树），和区块链是同一类思想。

#### 为什么要迁移到 SHA-256

Git 诞生时用的是 **SHA-1**，产出 40 位十六进制（160 bit）。但 SHA-1 在密码学上已被证明**可以人为构造碰撞**（2017 年 Google 的 SHAttered 攻击，真的造出了两个 SHA-1 相同但内容不同的 PDF）。虽然要攻击一个真实 Git 仓库门槛仍然很高（Git 后来还加了碰撞检测），但「用一个已被攻破的哈希做完整性根基」终究不理想。

于是 Git 引入了 **SHA-256** 支持（产出 64 位十六进制 / 256 bit）。可以显式用它初始化仓库：

```bash
git init --object-format=sha256 repo-sha256
```

现状（了解即可，面试提一句是加分项）：SHA-256 仓库已经能用，但生态（各大托管平台、老工具的互操作）还在过渡，SHA-1 目前仍是绝大多数仓库的默认。所以你日常看到的还是 40 位哈希，知道「Git 正在往 SHA-256 迁移、原因是 SHA-1 被攻破」就够了。

### 3.5 引用 refs：给冷冰冰的哈希起个好记的名字

#### 大白话

commit 哈希那么长，谁记得住？**ref（引用）就是给某个 commit 哈希起的一个人类友好的别名**，比如 `master`、`dev`、`v1.0`。它们物理上就是 `.git/refs/` 下的小文本文件，文件里存着一个 40 位哈希。分支之所以「轻量、切换快」，就是因为它不过是「一个存着哈希的文件」而已。

#### 分支引用：`refs/heads/xxx`

直接看 master 分支这个「文件」：

```bash
cat .git/refs/heads/master
# 预期输出：1a2b3c4d5e6f...   （就是最新那个 commit 的完整哈希）
```

**一个分支 = 一个存着某 commit 哈希的文件，仅此而已。** 所以：

- 「创建分支」= 新建一个这样的小文件（几乎零成本，和分支多大无关）。
- 「提交」= 生成新 commit，然后把这个文件里的哈希改成新 commit（3.7 会演示）。
- 「分支移动」= 改这个文件里的那行哈希。

理解这一点，很多分支操作就都不神秘了。

#### `HEAD`：指向「当前分支」的符号引用

`HEAD` 回答一个问题：**「我现在在哪儿？」** 正常情况下它不直接存 commit 哈希，而是存「我在哪个分支上」——这叫**符号引用（symbolic ref）**：

```bash
cat .git/HEAD
# 预期输出：ref: refs/heads/master
```

`ref: refs/heads/master` 意思是「HEAD 指向 master 分支」。于是链条是：

```
HEAD ──▶ refs/heads/master ──▶ commit 1a2b3c4 ──▶ tree ──▶ blob...
（我在哪个分支）   （分支指向哪个提交）    （提交是哪个快照）
```

你切换分支（`git switch dev`）时，Git 干的事就是把 `.git/HEAD` 的内容改成 `ref: refs/heads/dev`。就这么简单。

有个专门的命令读写 HEAD，别再去手动改文件：

```bash
git symbolic-ref HEAD
# 预期输出：refs/heads/master   （告诉你 HEAD 当前符号性地指向哪个分支）
```

#### detached HEAD（分离头指针）：HEAD 直接指向 commit

正常情况 HEAD → 分支 → commit。但 HEAD 也可以**跳过分支，直接指向某个 commit 哈希**，这种状态叫 **detached HEAD（分离头指针）**。

复现一下（直接检出某个具体提交，而不是分支名）：

```bash
git checkout 1a2b3c4          # 用某个 commit 哈希，而不是分支名
# 预期提示：You are in 'detached HEAD' state. ...

cat .git/HEAD
# 预期输出：1a2b3c4d5e6f...   ← 注意！这次是一个哈希，不再是 "ref: refs/heads/..."
```

看出区别了吗：正常时 `HEAD` 文件里是 `ref: refs/heads/master`；分离时里面直接是一个 commit 哈希。

**什么时候会遇到它？**
- 你 `git checkout <某个历史提交哈希>` 想看看旧代码。
- `git checkout <tag>`（检出一个标签）。
- 变基、二分查找（`git bisect`）过程中，Git 会临时让你处于分离状态。

**风险在哪？** 分离状态下你**照样能提交**，会生成新的 commit，HEAD 会跟着往前挪——但**没有任何分支指向这些新 commit**。一旦你 `git switch master` 切走，这些新提交就成了「没有引用指向的孤儿」，在界面上「消失」了，将来还可能被垃圾回收删掉（见 3.10）。

**怎么救？** 在切走之前，给它安个分支名把它「拴住」：

```bash
git switch -c my-work   # 以当前(分离的)提交为起点新建分支 my-work，HEAD 重新指向这个分支
```

只要建了分支，那些提交就有了引用、不再是孤儿。就算你已经切走了才想起来，也能用 3.9 的 reflog 找回来。

#### 远程引用：`refs/remotes/`

当你 `git clone` 或 `git fetch`，Git 会把远程仓库各分支的最新位置，记在本地的 `refs/remotes/<远程名>/<分支名>` 下，比如：

```bash
cat .git/refs/remotes/origin/master
# 预期输出：远程 master 分支在你上次 fetch 时所处的那个 commit 哈希
```

`origin/master` 是**远程分支在本地的只读镜像**，代表「我上次和远程同步时，远程的 master 停在哪」。它不会自动实时更新，只有 `fetch`/`pull` 时才刷新。你本地的 `master` 和 `origin/master` 是两个独立的 ref，这也是为什么会出现「你的分支领先/落后 origin/master 几个提交」的提示。

#### 标签引用：`refs/tags/`

`refs/tags/v1.0` 也是个存哈希的文件。区别是：分支会随提交移动，标签**钉死不动**。轻量标签直接存 commit 哈希；附注标签（3.3.4）存的是那个 tag 对象的哈希，tag 对象再指向 commit。

#### 小结这一节的世界观

```
       refs/tags/v1.0 ─────────────┐
                                    ▼
HEAD ─▶ refs/heads/master ─────▶ commit ─▶ commit ─▶ commit (历史链)
        refs/heads/dev ─────────────────────▶ commit
        refs/remotes/origin/master ─▶ commit
```

**所有 ref 都只是「一个名字 → 一个哈希」的映射文件；HEAD 是那个特殊的、告诉你「你现在站在哪」的指针。** Git 里大量操作，本质都是在挪这些指针。

### 3.6 暂存区 / 索引（index）的本质

#### 大白话

暂存区（staging area），也叫索引（index），物理上就是 `.git/index` 这一个二进制文件。你可以把它想成一张「**下一次提交的购物清单草稿**」：它记着「等下提交时，每个文件应该是什么内容（哪个 blob）、叫什么名、什么权限」。`git add` 就是往这张清单上填/改条目，`git commit` 就是照这张清单结账、定型成一次快照。

它的位置很关键——**它夹在「工作区」和「对象库」中间，是三者的连接点**：

```
工作区(working tree)          index(暂存区)              对象库(objects)
你实际编辑的文件         ──┐   一张"文件名→blob哈希"    ──┐   真正存内容的
a.txt(你刚改的)            │   的清单快照                 │   blob/tree/commit
                          │                             │
        git add a.txt ────┘  ①算出内容的blob写进对象库   │
                             ②把 a.txt→新blob哈希 记进index
                                                         │
        git commit ─────────────────────────────────────┘
                    ③照 index 生成 tree+commit，移动分支
```

#### `git add` 到底写了什么

很多初学者以为 `git add` 只是「做个标记」。不是。**`git add` 会真的把文件内容算成 blob、写进 `.git/objects/`，同时在 index 里登记「这个路径 → 这个 blob 哈希」**。

实测看 index 里有什么：

```bash
git ls-files --stage
# 预期输出（每行一个已暂存的文件）：
# 100644 ce013625030ba8dba906f756967f9e9ca394464a 0	a.txt
# 100644 cc628ccd10742baea8241c5924df992b5c019f71 0	b.txt
# └权限   └该文件当前暂存的 blob 哈希              └暂存槽  └路径
```

它记录的核心是「**路径 ↔ blob 哈希**」的对应，外加权限和一些文件状态信息（stat：修改时间、大小等，用来快速判断工作区文件是否变过）。

再实测「add 会写对象」：

```bash
echo 'new stuff' > c.txt
git add c.txt
# 现在去对象库里，一定能找到 'new stuff\n' 对应的那个新 blob
git cat-file -p $(git hash-object c.txt)
# 预期输出：new stuff   ← 内容已经在对象库里了，还没 commit 就已入库
```

这就解释了一个常见困惑：**为什么 `git add` 之后再改文件，提交的还是 add 那一刻的版本？** 因为 add 时内容就已经被固化成 blob 并登记进 index 了；你之后改工作区文件，index 里记的还是旧 blob，除非你再 add 一次覆盖它。

> 面试点：index 是「工作区」和「仓库」之间的缓冲层，它让你能精确控制「这次提交到底带哪些改动、甚至同一文件只带部分改动（`git add -p`）」。它记的是 blob 哈希，不是文件本身。

### 3.7 快照模型串起来：一次 `git commit` 到底发生了什么

把前面所有零件拼起来。当你 `git add` 若干文件再 `git commit`，Git 内部按顺序做了这么几步：

```
第①步  git add：
        对每个被 add 的文件，算出内容的 SHA-1，把内容作为 blob 写进 .git/objects/，
        并在 index 里登记 "路径 → blob 哈希"。
                                    │
                                    ▼
第②步  git commit（其一）：把 index 定型成 tree。
        读取当前 index 的全部条目，按目录层级组织，生成一个（或多个嵌套的）
        tree 对象写进对象库。—— 这一步等价于底层的 git write-tree。
                                    │
                                    ▼
第③步  git commit（其二）：生成 commit 对象。
        新建一个 commit 对象：tree 指向第②步的根 tree；parent 指向"当前 HEAD
        所指的那个 commit"（即上一次提交）；填入 author/committer/时间/提交信息。
        算出这个 commit 的哈希，写进对象库。
                                    │
                                    ▼
第④步  移动分支指针。
        把当前分支文件（如 .git/refs/heads/master）里的哈希，改成第③步新 commit
        的哈希。因为 HEAD → master，所以 HEAD 也就自然跟着指向了新提交。
```

用底层命令「手工造一次提交」，能把这个过程看得清清楚楚（进阶，感兴趣可跟着敲）：

```bash
# ① 把内容写成 blob
echo 'manual commit demo' > d.txt
git add d.txt

# ② 把 index 定型成 tree，拿到根 tree 哈希
TREE=$(git write-tree)

# ③ 基于这个 tree 和当前 HEAD(作为父)造一个 commit，拿到新 commit 哈希
COMMIT=$(echo "manual commit" | git commit-tree $TREE -p HEAD)

# ④ 手动把 master 指针挪到新 commit 上
git update-ref refs/heads/master $COMMIT

git log --oneline -1
# 预期：能看到 "manual commit" 出现在历史里
```

你会发现，`git commit` 这条高层命令，不过是把 ②③④（`write-tree` + `commit-tree` + `update-ref`）打包成一步。这就是「从底层理解 commit」。

一图收尾——一次提交后的对象关系：

```
提交前:  HEAD ─▶ master ─▶ C1(tree0)

git commit 之后:

         HEAD ─▶ master ─▶ C2 ──parent──▶ C1
                            │              │
                          tree1          tree0
                          /  \           /  \
                       blob  blob     blob  blob
                       (变了的重新存；没变的 C2 直接复用 C1 里的同一个 blob)
```

### 3.8 对象存储与压缩：松散对象 vs 打包文件

前面造的对象，都是**松散对象（loose object）**：一个对象一个文件，单独用 zlib 压缩后，存成 `.git/objects/前2位/后38位`。

```bash
# 每个松散对象本体都是被 zlib 压缩过的，直接看是乱码：
xxd .git/objects/d6/70460b4b4aece5915caf5c68d12f560a9fe3e4 | head
# 预期：一堆二进制（开头能看到 zlib 魔数 78），不可读——必须用 git cat-file 解
```

松散对象的问题：文件一多（一个大项目几十万个对象），既占 inode、又浪费空间——因为**每个版本的相似文件各存一份完整（压缩）内容，版本间的重复没有被跨对象利用**。

于是 Git 会把大量对象**打包（pack）**成一个 `.pack` 文件，配一个 `.idx` 索引，放在 `.git/objects/pack/` 下。打包时用了两层省空间手段：

- **zlib 压缩**：每个对象内容照旧压缩。
- **delta 压缩（增量压缩）**：在 packfile 内部，Git 会挑出「内容高度相似」的对象，只完整存其中一个（基对象），其余的存成「相对基对象的差异」。**注意这里才第一次出现「差异」，而且是纯粹的存储层压缩优化，和 3.1 的「版本模型是快照」是两个层面，别混。** 逻辑上每个版本仍是完整快照；物理落盘时 Git 偷偷用 delta 省了空间。

什么时候会打包？`git push`/`fetch` 传输时会临时打包；本地对象攒多了、或你手动触发时也会打包。相关命令：

```bash
git gc
# garbage collect：垃圾回收 + 优化。它会把松散对象打包成 packfile、
# 合并已有 pack、顺便清理过期的不可达对象（见 3.10）。

git repack -d
# 只做"重新打包"这件事：把对象重打成 pack，-d 删掉打包后多余的旧 pack。

git count-objects -vH
# 看看当前有多少松散对象、多少已打包、各占多大空间（体检用）
```

你平时几乎不用手动 `gc`，Git 会在合适时机（比如某些命令后松散对象超阈值）自动触发 `git gc --auto`。知道「松散→打包、gc 会做压缩和清理」即可。

### 3.9 reflog 原理：为什么「丢失」的提交还能找回

#### 大白话

`reflog`（reference log，引用日志）是 Git 给你记的一本**私人流水账**：「HEAD 和各分支，每一次挪动，从哪个哈希挪到了哪个哈希」。因为这本账把「旧位置」也记下来了，所以即使你把分支指针挪走、看起来提交「没了」，账本里还留着它的哈希——顺着哈希就能把它捞回来。

#### 数据存在哪

就是 3.2 提到的 `.git/logs/`：

```bash
cat .git/logs/HEAD
# 预期输出（每行一次移动，字段：旧哈希 新哈希 操作者 时间  操作说明）：
# 0000...000 1a2b3c4 姚金盟 <...> 1756... commit (initial): first commit
# 1a2b3c4    5f6e7d8 姚金盟 <...> 1756... commit: manual commit
# 5f6e7d8    1a2b3c4 姚金盟 <...> 1756... checkout: moving from master to 1a2b3c4
```

每个分支还有自己的 `.git/logs/refs/heads/<分支名>`。用命令看更友好：

```bash
git reflog
# 预期输出（HEAD 的移动史，带 HEAD@{n} 序号）：
# 5f6e7d8 HEAD@{0}: commit: manual commit
# 1a2b3c4 HEAD@{1}: commit (initial): first commit
```

`HEAD@{0}` 是「现在」，`HEAD@{1}` 是「上一步 HEAD 在哪」，以此类推。**只要你能在 reflog 里找到那个哈希，就能把那一刻的状态找回来**，比如 `git switch -c 救回来 5f6e7d8` 或 `git reset --hard HEAD@{1}`。

#### 关键点：reflog 是本地的、有有效期

- reflog **只存在于你本地**，不会被 push 到远程，别人看不到你的 reflog。
- reflog 条目有过期时间：可达的默认 90 天、不可达的默认 30 天（`gc.reflogExpire` 配置）。过期后这些「找回入口」才会被清掉。
- 正因为 reflog 里还引用着那些哈希，**它也算一种「可达性」的来源**——只要 reflog 还记着某个 commit，垃圾回收就不会删它（见下一节）。这就是为什么「刚 reset 掉的提交」总能救回来。

### 3.10 可达性与垃圾回收：谁会被删、谁不会

#### 大白话

Git 判断一个对象「有没有用」，靠的是**可达性（reachability）**：从「根」（各个 ref：分支、标签、HEAD，外加 reflog、index）出发，顺着 commit→parent、commit→tree→blob 这些指针一路走，**能走到的对象就是「活的」（可达）**；一个都走不到的，就是「悬空 / 不可达对象（dangling / unreachable object）」——像一个没有任何绳子拴着的气球，飘在对象库里没人引用。

```
根(refs / HEAD / reflog / index)
   │ 顺着指针能走到的 → 可达(活对象)，永远不删
   ▼
  C3 ─▶ C2 ─▶ C1 ─▶ tree ─▶ blob ...

  C_x  (某次 reset 后没有任何 ref 指向它，reflog 也过期了)
   └─ 没有任何绳子拴着 → dangling，将来会被 gc 删掉
```

#### 检查悬空对象：`git fsck`

```bash
git fsck --full
# 预期可能输出：
# dangling commit 9f8e7d6...     ← 悬空提交（比如被 reset 掉、无 ref 指向的）
# dangling blob   3c2b1a0...     ← 悬空 blob
```

`fsck` = file system check，用来检查对象库完整性，同时会把「悬空对象」列出来。如果你手滑弄丢了什么，`git fsck --lost-found` 能帮你把悬空提交找出来。

#### GC 何时真正删除对象

**不可达 ≠ 立刻删除。** Git 很谨慎，给了「宽限期」，防止误删你可能还想找回的东西：

- 只有在跑 `git gc`（或自动 `gc --auto`）时才会真正清理不可达对象。
- 而且默认只删「不可达**且**已经超过宽限期」的对象，宽限期由 `gc.pruneExpire` 控制，**默认 2 周（two weeks ago）**。
- 前提还得是这个对象**连 reflog 都不再引用**（reflog 也有它自己的过期时间，见 3.9）。

把这几条串起来，就解释了那个经典问题——

> **「我 `git reset --hard` 把提交丢了，为什么还能救回来？」**
> 因为：reset 只是把分支指针挪回旧位置，被甩掉的那个 commit 变成不可达，但①它还被 **reflog** 引用着（reflog 记了 reset 前的位置），②就算不算 reflog，它也没超过 gc 的宽限期。所以对象根本还在对象库里。你只要用 `git reflog` 找到它的哈希，`git reset --hard <哈希>` 或建个分支指过去，就完好无损地回来了。真正让它「永远消失」，要等 reflog 过期 + gc 宽限期过 + 跑了 gc，这三件事都发生之后。

### 3.11 从底层理解常见命令：一切都是「指针移动 + 造新对象」

有了前面的世界观，这些命令就不用死记「会不会丢代码」，而是能从「它到底动了哪个指针、造了什么对象」推出来。核心记住三条主线的作用范围：**HEAD 在哪、分支指针在哪、index 和工作区是否被改**。

#### `checkout` / `switch`：移动 HEAD（切换你「站」的位置）

- `git switch dev` / `git checkout dev`：把 `HEAD` 改成指向 `dev` 分支，并把工作区、index 更新成 dev 最新提交的样子。**本质是移动 HEAD + 刷新工作区**，不产生新 commit、不动历史。
- `git checkout <commit哈希>`：HEAD 直接指向那个 commit → 进入 detached HEAD（3.5）。
- 新版把「切分支」和「改文件」拆成了 `git switch`（切分支）和 `git restore`（改文件/撤销工作区改动），语义更清晰，`checkout` 是它俩的老版合体。

#### `reset`：移动**当前分支指针**（可选带上 index、工作区）

`reset` 的核心是「把当前分支指针挪到某个 commit」，三种模式区别只在于「顺不顺便重置 index 和工作区」：

```
                       动分支指针?   动 index?   动工作区?
git reset --soft  C     ✔            ✗           ✗        ← 只挪指针，改动都留在暂存区
git reset --mixed C     ✔            ✔            ✗        ← 默认；挪指针+清空暂存，改动留工作区
git reset --hard  C     ✔            ✔            ✔        ← 全部重置，工作区也变（会真丢未提交改动）
```

- `--soft`：只移动分支指针，index 和工作区都不动 → 常用于「把最近几次提交揉回暂存区，重新组织成一次提交」。
- `--mixed`（默认）：移动指针 + 重置 index，工作区保留 → 「撤销 add / 撤销提交但保留改动」。
- `--hard`：移动指针 + 重置 index + 重置工作区 → **唯一可能真丢未提交改动的模式**，慎用（但已提交过的东西仍可靠 reflog 找回，见 3.10）。

关键：reset **一般不造新对象**，只是挪指针（外加改 index/工作区）。被甩在后面的旧提交并没被删，只是当前分支不再指向它们。

#### `merge`：造一个「有两个父」的新 commit

合并 dev 到 master 时，如果不是快进（fast-forward），Git 会新建一个**合并提交（merge commit）**，它的特别之处是有**两个 parent**：

```
        C1 ─▶ C2 ─▶ C3 (master)
               \          \
                \          ▶ M  (新的 merge commit：parent = C3 和 C5)
                 ▶ C4 ─▶ C5 (dev)
```

```bash
git cat-file -p HEAD   # 合并后看合并提交
# 会看到两行 parent：
# parent C3哈希
# parent C5哈希
```

merge 的本质就是「造一个新 commit 把两条历史线在此汇合」，历史里从此有了「分叉→汇合」的形状。而**快进合并（fast-forward）**是特例：如果 master 落后 dev 且没有分叉，Git 不造新 commit，只是把 master 指针「快进」到 dev 的位置——纯指针移动。

#### `rebase`：把提交「复制」到新基点，哈希会变

变基不是移动原提交，而是**把你的一串提交，一个个「重新做一遍」放到新的基点上，生成一批内容相似但哈希全新的 commit**，原来的老提交则变成不可达（还能靠 reflog 找回）。

```
变基前:
        C1 ─▶ C2 ─▶ C3 (main)
               \
                ▶ A ─▶ B (feature)

git switch feature; git rebase main 之后:
        C1 ─▶ C2 ─▶ C3 (main)
                          \
                           ▶ A' ─▶ B' (feature)   ← A'、B' 是 A、B 的"复制品"，
                                                    内容改动一样，但 parent 变了、
                                                    哈希是全新的；A、B 变成悬空对象
```

**关键结论：rebase 会改写提交哈希。** 这就是「已经 push 到远程、别人可能基于它工作的提交，不要随便 rebase」的底层原因——你把 A、B 换成了 A'、B'，别人手里还是老的 A、B，历史对不上就会冲突/混乱。对比之下 merge 不改写老提交，只是新增一个汇合点，所以对协作更「安全」但历史线更繁杂。这正是 merge vs rebase 之争的底层依据。

---

### 3.12 分布式模型：每个克隆都是一个完整仓库

#### 大白话

Git 是**分布式（distributed）**版本控制，和老式的 SVN（集中式）根本区别在于：**你 `git clone` 下来的，不是「工作副本」，而是一整个仓库——包含从第一次提交到现在的完整历史、所有对象。** 每个人电脑上的 `.git` 都是「全量备份」，而不是「向中央服务器借来的一角」。

```
集中式(SVN)：              分布式(Git)：
                          开发者A .git(完整历史)  ┐
中央服务器(唯一完整历史)    开发者B .git(完整历史)  ├─ 每个都是完整仓库，
   ↑  ↑  ↑                开发者C .git(完整历史)  ┘   互相之间平等地 push/fetch
 工作副本(只有当前版本)     远程(如 GitHub) 只是"大家约定的同步点"，
                          地位上并不比谁更"特殊"
```

可以亲眼验证「克隆带走全部历史」：

```bash
git clone /path/to/git-lab clone-test
cd clone-test
git log --oneline        # 完整历史都在
ls .git/objects          # 所有对象都被拷过来了
git log                  # 断网也能看，因为历史就在本地
```

#### 这对协作 / 离线 / 备份意味着什么

- **离线可用**：提交、看历史、切分支、diff、blame……几乎所有操作都在本地 `.git` 完成，**不需要联网**。只有 `push`/`fetch`/`pull`（和别人同步）才需要网络。这也是 Git 快的重要原因。
- **天然多副本备份**：团队里有 N 个人，就有 N+1 份完整历史（加上远程）。中央服务器炸了，随便找一个人的克隆 `push` 上去就能恢复全部历史。不存在「服务器一挂全公司历史归零」。
- **协作灵活**：没有「唯一权威服务器」的技术限制——GitHub 上那个 `origin` 之所以「权威」，纯粹是团队**约定**的，技术上任意两个仓库都能互相同步。可以有多个远程、可以点对点交换补丁。
- **每个人可自由实验**：因为你在本地就有完整历史，可以随意建分支、变基、回退、造实验性提交，都不影响别人，满意了再 push 出去。

> 面试一句话总结：Git 的「分布式」= 每个克隆都是自带完整历史的独立仓库，远程只是约定的同步节点。它换来了离线能力、极快的本地操作、和天然的分布式备份/抗单点故障。而这一切之所以成立，底层正是 3.1~3.11 讲的——所有历史都由「内容寻址的对象 + 指针（refs）」表示，克隆时把这些对象和指针整套复制过去，历史就完整搬家了。

---

**这一板块的一条主线，请务必带走**：Git 底层其实只有两样东西——**不可变的对象**（blob/tree/commit/tag，用内容哈希寻址、天然去重、拼成一张快照 DAG）和**可变的指针**（refs/HEAD/index，只是存着哈希的小文件）。你日常敲的绝大多数命令，翻译到底层，无非是「**按内容造几个新对象**」和「**把某个指针从一个哈希挪到另一个哈希**」这两类动作的组合。抓住这条主线，Git 就从「一堆要背的命令」变成了「一个能推理的系统」。

## 四、项目协作流程与工程实践（DevOps 侧重）

> 这一板块的核心视角是：**Git 不只是一个"存代码"的工具，它是整个团队协作和自动化流水线（CI/CD）的地基**。面试里问"你们用什么分支模型""怎么做发布回滚""commit 规范怎么定"，本质上都是在问：你有没有在真实团队里参与过工程化协作。下面每个小节都先讲"这是为了解决什么问题"，再给规范和可落地的示例。

---

### 4.1 分支策略对比（面试超高频，重点中的重点）

#### 4.1.1 大白话：为什么需要"分支策略"

想象一个 10 人小组同时改一个项目。如果所有人都直接往同一条线（`main`）上提交，就会像 10 个人抢着在同一张纸上写字——互相覆盖、天天冲突、谁也不知道哪个版本是能发布的。

**分支策略（Branching Strategy / Branching Model）** 就是团队约定好的一套"规矩"：什么时候开新分支、分支叫什么、往哪合、什么分支能发布上线。它解决的核心矛盾是：**既要让很多人并行开发（隔离），又要让代码稳定可发布（集成）**。

DevOps 语境下还多一层诉求：**分支模型必须能配合自动化流水线**——哪条分支一推代码就自动测试、哪条分支一打标签就自动部署，都要清清楚楚。

#### 4.1.2 四种主流模型逐个讲

**① Git Flow（重流程、发布周期长）**

由 Vincent Driessen 在 2010 年提出，是最"经典"也最"重"的模型。它规定了 5 类分支：

| 分支 | 职责 | 生命周期 |
|---|---|---|
| `master`（或 `main`） | 只存放**已发布到生产**的稳定代码，每次合并都对应一个正式版本 | 永久 |
| `develop` | 主开发线，汇集所有已完成的功能，是"下一个版本"的集成分支 | 永久 |
| `feature/*` | 开发单个新功能，从 `develop` 切出，完成后合回 `develop` | 临时 |
| `release/*` | 准备发布，从 `develop` 切出，只做测试/改 bug/写版本号，稳定后同时合入 `master` 和 `develop` | 临时 |
| `hotfix/*` | 线上紧急修复，从 `master` 切出，修完同时合入 `master` 和 `develop` | 临时 |

- **适合**：有明确版本号、按周期发版的产品（如客户端软件、企业级私有部署、App 定期发版）。
- **优点**：职责分明，`master` 永远干净可发布，紧急修复有专门通道。
- **缺点**：分支多、合并链路长、`develop` 和 `master` 容易分叉；分支活得久 → 越晚合并冲突越大；**和"持续交付、每天上线很多次"的 DevOps 理念不太合拍**。

**② GitHub Flow（极简、面向持续部署）**

只有一条长期分支 `main`，其余全是短命的特性分支：

1. 从 `main` 切出 `feature` 分支；
2. 开发、提交、`push`；
3. 开 **Pull Request（PR）** 发起评审 + 触发 CI；
4. 评审通过、CI 绿灯 → 合回 `main`；
5. 合并后**立即部署**（`main` 永远处于可部署状态）。

- **适合**：Web 应用、SaaS、能做到"合并即上线"的团队。
- **优点**：极简，特性分支生命周期短（几小时到几天），天然贴合 CI/CD。
- **缺点**：没有专门的"预发布/多环境"概念，对"需要同时维护多个已发布版本"的场景支持弱。

**③ GitLab Flow（在 GitHub Flow 上补了"环境/发布"概念）**

核心思想：**用"环境分支"或"发布分支"来映射真实的部署环境**。常见两种玩法：

- **环境分支（environment branches）**：`main` → `staging` → `production`，代码像水流一样"从上游往下游"合并（`main` 测好合到 `staging`，`staging` 验证好合到 `production`）。每条环境分支对应一套自动部署。
- **发布分支（release branches）**：需要维护多个版本（如 `1-0-stable`、`2-0-stable`）时，为每个大版本开一条稳定分支，bug 修复先进 `main` 再 **cherry-pick** 回各发布分支（"上游优先"原则）。

- **适合**：既想要 GitHub Flow 的简洁，又需要多环境/多版本管理的团队。
- **优点**：把"部署环境"显式建模进分支，DevOps 友好。
- **缺点**：比 GitHub Flow 复杂一点，需要团队理解"上游优先"规则。

**④ Trunk-Based Development（主干开发，现代 DevOps 首选）**

所有人都围绕一条主干（trunk，即 `main`）开发，**特性分支活得极短（通常小于 1 天，甚至直接在 `main` 上小步提交）**，每天多次合并回主干。没做完的功能用 **Feature Flag（功能开关）** 藏起来，代码虽已合入主干但对用户不可见。

- **适合**：追求**持续集成/持续交付**、发布频率高、自动化测试完善的成熟团队（Google、Facebook 等大厂的主流实践）。
- **优点**：分支短命 → 冲突极小、集成风险极低；主干始终可发布；与 CI/CD 完美契合。
- **缺点**：**对自动化测试覆盖率、Feature Flag 基础设施、团队纪律要求高**；测试不到位时风险直接暴露在主干上。

#### 4.1.3 四大模型一表对比

| 维度 | Git Flow | GitHub Flow | GitLab Flow | Trunk-Based |
|---|---|---|---|---|
| 长期分支数 | 2（master+develop） | 1（main） | 1 + 环境/发布分支 | 1（trunk） |
| 特性分支寿命 | 长（数天~数周） | 短（数小时~数天） | 短~中 | **极短（<1天）** |
| 发布节奏 | 定期版本发布 | 持续部署 | 多环境/多版本 | 持续交付（高频） |
| 合并冲突风险 | 高 | 中 | 中 | **低** |
| 学习/维护成本 | 高 | 低 | 中 | 中（但要求高纪律+测试） |
| 与 CI/CD 契合度 | 一般 | 好 | 好 | **最好** |
| 典型适用 | 客户端/私有部署/按版本发布 | Web/SaaS | 需多环境多版本 | 成熟 DevOps 大团队 |

#### 4.1.4 面试要点：为什么 DevOps 语境下大家越来越倾向 Trunk-Based / 短生命周期分支？

一句话记忆：**分支活得越久，越晚集成，冲突和风险越大**（这叫"集成地狱"）。而 CI/CD 的核心信条是**持续集成（Continuous Integration）——尽早、频繁地把代码合到一起并自动验证**。所以：

- 短命分支 = 频繁小步合并 = 每次冲突都很小、问题早暴露；
- 主干始终可发布 = 随时能触发自动化流水线部署；
- 配合 Feature Flag，可以"合入但不发布"，把"部署"和"发布"解耦——这是现代 DevOps 的关键能力。

> 面试话术示例："长生命周期分支会推迟集成，导致合并冲突和回归风险累积，与持续集成理念相悖。所以在自动化测试和 Feature Flag 完备的前提下，我们倾向 Trunk-Based 或短命特性分支，保证主干始终绿色可发布。"

### 4.2 多人协作的两种仓库模式

#### 4.2.1 共享仓库模式（Shared Repository）vs Fork + PR 模式

| 对比项 | 共享仓库模式 | Fork + Pull Request 模式 |
|---|---|---|
| 权限 | 所有成员对**同一个远程仓库**有写权限 | 贡献者对主仓库**只有读权限**，把仓库 **fork（复刻）** 到自己名下再改 |
| 流程 | 直接在主仓库开特性分支 → PR/MR | 在自己 fork 的仓库改 → 向主仓库发 PR |
| 适合 | **公司内部团队**（互相信任、成员固定） | **开源项目 / 外部贡献者**（不信任外人直接写主仓库） |
| 特点 | 简单直接 | 主仓库更干净、更安全，维护者集中审核 |

#### 4.2.2 一次标准协作流程（背下来，面试常让你复述）

```bash
# 1. 拉最新主干，保证起点是最新的
git checkout main
git pull origin main

# 2. 建特性分支（命名规范：feature/xxx、fix/xxx、类型/简短描述）
git checkout -b feature/user-login

# 3. 开发 + 多次提交（提交信息遵循规范，见 4.3）
git add .
git commit -m "feat(auth): add login form validation"

# 4. 推到远程
git push -u origin feature/user-login

# 5. 在 GitHub/GitLab 上开 PR/MR（这一步会自动触发 CI 流水线）
#    → 团队成员 Code Review → CI 全绿 → 批准

# 6. 合并到 main（平台按约定的合并策略执行，见 4.5）

# 7. 删掉已合并的特性分支（保持仓库整洁）
git branch -d feature/user-login          # 删本地
git push origin --delete feature/user-login   # 删远程
```

> 记忆口诀：**拉最新 → 开分支 → 提交 → push → 开 PR → 评审 → 合并 → 删分支**。

### 4.3 Commit Message 规范

#### 4.3.1 为什么要规范提交信息

`git log` 里如果全是 `update`、`fix bug`、`改了下`、`asdf`，那这段历史几乎没有价值——出了问题没法快速定位是哪次改动、也没法自动生成发版说明。**规范的提交信息让历史可读、可检索、可被机器解析**，进而能**自动生成 CHANGELOG、自动推算版本号**，这正是 DevOps 自动化的一环。

#### 4.3.2 Conventional Commits（约定式提交）

这是目前最流行的提交规范，格式如下：

```
<类型>(<可选范围>): <简短描述>
<空行>
<可选正文：解释为什么这么改、怎么改的>
<空行>
<可选脚注：BREAKING CHANGE、关联的 issue 编号等>
```

常用**类型（type）**：

| type | 含义 |
|---|---|
| `feat` | 新功能（会触发 **MINOR** 版本号 +1） |
| `fix` | 修 bug（会触发 **PATCH** 版本号 +1） |
| `docs` | 只改文档 |
| `style` | 不影响逻辑的格式调整（空格、分号等） |
| `refactor` | 重构（既不加功能也不修 bug） |
| `perf` | 性能优化 |
| `test` | 增删测试 |
| `chore` | 杂项（构建脚本、依赖升级等） |
| `ci` | CI 配置改动 |

**示例：**

```
feat(auth): 支持手机号验证码登录

新增短信验证码通道，验证码有效期 5 分钟。
后端复用现有的 SMS 网关，不引入新依赖。

Closes #128
```

**破坏性变更（不兼容改动）** 写法——在正文脚注加 `BREAKING CHANGE:`，或在类型后加 `!`：

```
feat(api)!: 重命名 /user 接口为 /users

BREAKING CHANGE: 旧的 /user 端点已删除，调用方需改用 /users。
```

#### 4.3.3 规范如何驱动自动化（这是 DevOps 关键卖点）

因为提交信息是"结构化"的，工具可以直接解析它们：

- **自动生成 CHANGELOG**：工具（如 `standard-version`、`semantic-release`、`conventional-changelog`）扫描自上个版本以来的所有 commit，把 `feat` 归到"新功能"、`fix` 归到"问题修复"，自动生成发版日志。
- **自动推算语义化版本（SemVer，见 4.11）**：
  - 有 `BREAKING CHANGE` → 主版本 +1（`1.4.2 → 2.0.0`）
  - 有 `feat` → 次版本 +1（`1.4.2 → 1.5.0`）
  - 只有 `fix` → 修订号 +1（`1.4.2 → 1.4.3`）

> 于是"提交代码 → 自动定版本号 → 自动生成 CHANGELOG → 自动打 tag → 自动发布"就能串成一条全自动流水线。这就是规范化的价值。

### 4.4 Code Review 与 PR/MR 最佳实践

#### 4.4.1 什么是好的 PR：小而聚焦（Small & Focused）

- **一个 PR 只做一件事**。混着"加功能 + 顺手重构 + 改格式"的大 PR，评审者根本看不过来，很容易漏掉问题。经验值：**改动尽量控制在几百行以内**。
- **标题和描述清楚**：说明"为什么改、改了什么、怎么测的"，附上关联的 issue。
- **自测通过、CI 绿灯**再请人评审，别让别人帮你发现连自己都没跑过的错误。

#### 4.4.2 评审要点（reviewer 该看什么）

正确性（逻辑对不对、边界情况） → 可读性（命名、结构） → 是否有测试 → 安全性（有没有硬编码密钥、注入风险） → 是否符合团队规范。**对事不对人，评论要具体、给建设性建议**。

#### 4.4.3 Draft PR（草稿 PR）

功能还没完全做完，但想**提前让 CI 跑起来、或提前让同事看方向对不对**，可以开成 **Draft（草稿）** 状态的 PR。它能触发流水线、能被评论，但**平台会禁止在草稿状态下合并**，避免半成品误入主干。

#### 4.4.4 Review 后如何整理提交（squash）

开发过程中你可能提了一堆零碎 commit：`wip`、`fix typo`、`再改改`……合入主干前最好把它们**压缩（squash）成一个（或少数几个）干净的提交**，让主干历史整洁。大多数平台的"Squash and merge"按钮就是干这个的（见 4.5），也可以本地用交互式 rebase 整理后再推。

---

### 4.5 合并策略与保护分支

#### 4.5.1 平台上的三种合并方式

在 GitHub/GitLab 点"合并"按钮时，通常有三种模式，区别在于**主干上最终留下什么样的历史**：

| 合并方式 | 做了什么 | 主干历史长啥样 | 适合场景 |
|---|---|---|---|
| **Merge commit（普通合并）** | 保留特性分支的所有提交，再加一个"合并提交" | 完整保留分支结构，有分叉有合并点 | 想保留完整开发轨迹 |
| **Squash and merge（压缩合并）** | 把分支上所有提交**压成一个**再放进主干 | 一个特性 = 一个提交，非常干净 | **最常用**，主干整洁、每个 PR 一条记录 |
| **Rebase and merge（变基合并）** | 把分支的每个提交**逐个"搬"到主干末尾**，不产生合并提交 | 一条完美直线，无分叉 | 想要线性历史、又想保留每个提交 |

> 小白记忆：Merge = 保留全部+留疤痕；Squash = 打包成一个；Rebase = 拉成一条直线。团队里最常见的是 **Squash and merge**，因为它让主干"一个功能一行历史"，特别清爽。

#### 4.5.2 受保护分支（Protected Branch）

**大白话**：给 `main`、`production` 这种重要分支上一把锁，规定"不满足条件就不许往里合、不许强推、不许删"。这是团队防线的关键。常见的保护规则：

- **禁止直接 push**，必须走 PR/MR；
- **必须至少 N 人评审通过**才能合并；
- **必须 CI 全部通过**（status checks 绿灯）才能合并；
- **禁止 force push、禁止删除**该分支；
- 可要求提交必须签名（见 4.12）。

这套机制保证了"进入主干的每一行代码，都经过了测试和人工审核"——是 DevOps 质量门禁（Quality Gate）的核心。

#### 4.5.3 `--force` 与 `--force-with-lease` 的风险与规范

- `git push --force`：**强推，会用你本地的历史直接覆盖远程**。如果别人在这期间往同一分支推过东西，会被你**无声地覆盖丢失**，非常危险。
- `git push --force-with-lease`：**"带租约的强推"**，更安全。它会先检查"远程分支现在是否还停在我上次看到的位置"——如果别人推过新东西（远程变了），它会**拒绝推送并报错**，从而避免覆盖别人的工作。

**团队规范**：
- **永远不要对共享分支（`main` 等）强推**（受保护分支通常也直接禁止）；
- 只有在**自己的、没人协作的特性分支**上，整理完提交（rebase/squash 后）需要强推时才用，且**优先用 `--force-with-lease` 而非 `--force`**。

### 4.6 平台核心功能速览：GitHub ↔ GitLab 概念对照

两大平台功能高度相似，只是叫法不同。建立起对应关系，面试时聊哪个平台都不虚：

| 功能类别 | GitHub | GitLab | 作用 |

| 问题/需求跟踪 | Issues | Issues | 记录 bug、需求、任务 |

| 版本发布 | Releases | Releases | 关联 tag 发布正式版本、附带产物 |
| 静态站点托管 | Pages | Pages | 用仓库直接托管网站 |
| 项目文档 | Wiki | Wiki | 团队知识/文档 |
| 看板/项目管理 | Projects | Issue Boards / Milestones | 任务看板、里程碑 |
| 制品/镜像仓库 | Packages / Container Registry | Package Registry / Container Registry | 存放构建产物、Docker 镜像 |

> 一句话对照记忆：**GitHub 的 PR + Actions = GitLab 的 MR + Pipelines**。

### 4.7 CI/CD 与 Git 集成（DevOps 的心脏）

#### 4.7.1 大白话：CI/CD 是什么，Git 事件怎么触发它

- **CI（持续集成）**：每次有人提交代码，就**自动跑测试、跑构建**，尽早发现问题。
- **CD（持续交付/部署）**：测试通过后，**自动把应用打包、部署**到测试或生产环境。

它们的"触发扳机"就是 **Git 事件**。常见触发时机：

| Git 事件 | 典型用途 |
|---|---|
| `push` 到某分支 | 一提交就跑测试/构建 |
| 打 `tag`（如 `v1.2.0`） | 触发正式发布/生产部署 |
| 开/更新 PR / MR | 合并前先跑一遍检查（质量门禁） |
| 定时（schedule/cron） | 每晚跑全量回归测试、依赖安全扫描 |
| 手动触发 | 需要人工确认的生产部署 |

#### 4.7.2 GitHub Actions 最小 workflow 示例

文件放在仓库的 `.github/workflows/ci.yml`：

```yaml
name: CI                       # 流水线的名字，会显示在 Actions 页面

on:                            # 触发条件
  push:
    branches: [ main ]         # 推送到 main 分支时触发
  pull_request:                # 有 PR 时也触发（合并前先检查）

jobs:
  test:                        # 定义一个叫 test 的作业
    runs-on: ubuntu-latest     # 用一台全新的 Ubuntu 虚拟机来跑

    steps:                     # 作业里的一系列步骤，按顺序执行
      - name: 检出代码
        uses: actions/checkout@v4      # 官方动作：把仓库代码拉到虚拟机上

      - name: 安装 Python
        uses: actions/setup-python@v5  # 官方动作：装好指定版本 Python
        with:
          python-version: '3.12'

      - name: 安装依赖
        run: pip install -r requirements.txt   # run 就是执行一条 shell 命令

      - name: 跑测试
        run: pytest                    # 测试失败会让整条流水线变红
```

**逐行要点**：`on` 决定"什么时候跑"；`jobs` 下的每个作业跑在一台干净的机器上；`steps` 里 `uses` 是复用别人写好的"动作"，`run` 是执行自己的命令；**第一步几乎永远是 `checkout`**——因为虚拟机是空的，得先把 Git 仓库代码拉下来。

#### 4.7.3 GitLab CI 最小 `.gitlab-ci.yml` 示例

文件放在仓库根目录，名字固定为 `.gitlab-ci.yml`：

```yaml
stages:                # 定义阶段，按顺序执行：先 test 再 build
  - test
  - build

test-job:              # 一个作业，属于 test 阶段
  stage: test
  image: python:3.12   # 用哪个 Docker 镜像来跑（GitLab CI 默认基于容器）
  script:              # 要执行的命令（GitLab 里叫 script）
    - pip install -r requirements.txt
    - pytest

build-job:             # 另一个作业，属于 build 阶段
  stage: build
  image: python:3.12
  script:
    - python setup.py sdist       # 打包构建产物
  only:
    - main             # 只在 main 分支才跑这个作业
```

**逐行要点**：`stages` 定义阶段顺序（同阶段作业可并行，跨阶段串行）；每个作业用 `image` 指定容器环境；命令写在 `script` 里；`only: main` 表示这个作业只在 `main` 分支触发（新版语法用 `rules` 更灵活）。

#### 4.7.4 Git 在流水线里扮演的三个关键角色

1. **checkout**：流水线第一步永远是从 Git 拉取当前提交的代码——**流水线跑的就是某个 commit 的快照**。
2. **按 tag 构建/发版**：检测到打了 `v*` 的 tag，就用这个 tag 对应的代码构建正式版本、生成 Release。
3. **按分支部署到不同环境**：`develop` 分支的提交自动部署到测试环境，`main`/`production` 的提交部署到生产环境——**"哪条分支 → 哪个环境"的映射，是 DevOps 里 Git 和部署联动的核心**。

### 4.8 Git Hooks（钩子）

#### 4.8.1 大白话：钩子是什么

**Git Hook（钩子）** 就是"在 Git 某个动作发生时自动运行的一段脚本"。比如"你每次提交前，自动帮你检查一遍代码格式"——你不用记得手动跑，Git 在合适的时机替你触发。本质是放在 `.git/hooks/` 目录下、按约定命名的可执行脚本。

#### 4.8.2 客户端 hooks vs 服务端 hooks

| 类别 | 在哪运行 | 常见钩子 | 用途 |
|---|---|---|---|
| **客户端 hooks** | 每个开发者**自己电脑上** | `pre-commit`（提交前）、`commit-msg`（校验提交信息）、`pre-push`（推送前） | 本地快速自检：格式化、跑 lint、校验 commit 规范 |
| **服务端 hooks** | Git **服务器上** | `pre-receive`、`update`、`post-receive` | 服务端强制：拒绝不合规的推送、推送后触发部署/通知 |

**关键区别**：客户端 hooks **可以被绕过**（比如 `git commit --no-verify`），也**不会随仓库自动分发给别人**（默认在 `.git/hooks` 里，不进版本库）；服务端 hooks 是**强制的、绕不过去的**，因为它跑在服务器上。

#### 4.8.3 一个 pre-commit 校验小例子

在 `.git/hooks/pre-commit` 文件里写（记得 `chmod +x` 给执行权限）：

```bash
#!/bin/sh
# 提交前检查：暂存区里有没有残留的调试语句 print( 或 console.log

if git diff --cached --name-only | xargs grep -nE 'console\.log|print\(' 2>/dev/null; then
    echo "❌ 检测到疑似调试语句，请清理后再提交（如确需保留，用 --no-verify）"
    exit 1        # 非 0 退出码 = 阻止本次提交
fi
exit 0            # 0 = 放行
```

原理：Git 在你敲 `git commit` 后、真正生成提交前，会先运行这个脚本。**脚本退出码为 0 才放行，非 0 就中止提交**。

#### 4.8.4 husky / pre-commit 框架简介

原生 `.git/hooks` 有两个痛点：**不进版本库（无法团队共享）、写 shell 麻烦**。于是有了框架：

- **husky**（Node/前端生态）：把 hook 脚本纳入版本库管理，`git clone` 后一装就全队生效，常配合 `lint-staged` 只检查改动的文件。
- **pre-commit**（Python 生态的同名框架）：用一个 `.pre-commit-config.yaml` 声明要跑哪些检查（格式化、lint、密钥扫描等），一条命令装好，跨语言通用。

#### 4.8.5 hooks 与 CI 的关系：本地快检 vs 服务端强制

- **hooks（尤其客户端）= 快速的"提前拦截"**：在你本地、提交/推送前几秒钟就把低级问题挡住，反馈快、省得推上去才发现。
- **CI = 最终的"强制门禁"**：跑在服务器上，**绕不过去**，是质量的最后防线。
- 两者**互补而非替代**：本地 hook 图快（但能被 `--no-verify` 跳过），CI 图稳（谁也跳不过）。**能被绕过的检查，一定要在 CI 里再强制跑一遍**。

### 4.9 子模块与仓库组织

#### 4.9.1 git submodule（子模块）

**大白话**：你的项目里想"嵌"另一个独立的 Git 仓库（比如引用一个公共库），但又不想把它的代码直接拷进来、想保持它独立更新——`submodule` 就是在你的仓库里放一个"指针"，指向另一个仓库的**某个具体 commit**。

- **用途**：多个项目共用同一份底层库、引用第三方仓库并锁定版本。
- **常见痛点（面试爱问）**：
  - **克隆时容易漏**：普通 `git clone` 不会把子模块代码拉下来，子模块目录是空的。要用 `git clone --recursive`，或克隆后补跑 `git submodule update --init --recursive`（`--recursive` 会连"子模块里的子模块"一起拉）。
  - **更新繁琐**：子模块记录的是固定 commit，上游更新后主仓库不会自动跟进，得手动进子模块拉取、再在主仓库提交新的指针。
  - **容易踩坑**：忘记提交子模块指针的变化、在子模块里处于"游离 HEAD"状态、团队成员之间子模块版本不一致等。

#### 4.9.2 git subtree（子树，简述）

另一种把外部仓库并入本仓库的方式，思路相反：**它把外部仓库的代码真正合并进你的仓库历史**，用起来对普通协作者更透明（不需要额外记 `--recursive` 之类的命令），代价是仓库变大、拉取/回推上游操作命令更复杂。**"子模块用指针、子树用合并"** 是两者最核心的区别。

#### 4.9.3 Monorepo vs Multirepo（单仓 vs 多仓）

| 对比项 | Monorepo（单体仓库） | Multirepo（多仓库） |
|---|---|---|
| 组织方式 | 所有项目/服务放**同一个仓库** | 每个项目/服务**各自一个仓库** |
| 代码共享 | 容易，直接引用 | 需通过发包/子模块 |
| 统一改动 | 一次提交跨多个模块，方便 | 要跨多仓协调，麻烦 |
| 权限隔离 | 粒度粗（整仓） | 天然按仓库隔离 |
| 仓库体积/构建 | 容易变巨大，需专门构建工具（Bazel、Nx 等） | 每个仓小而独立 |
| 代表 | Google、Meta | 多数中小团队/微服务 |

**取舍**：追求统一管理、跨模块原子提交、共享代码方便 → Monorepo（但要投入构建/CI 工具）；追求团队/服务自治、权限清晰、独立发布 → Multirepo。

### 4.10 Git LFS（大文件存储）

- **为什么需要**：Git 天生擅长管理"文本代码的差异"，但**不擅长大的二进制文件**（图片、视频、模型权重、数据集）。这些文件每改一次，Git 就存一整份，仓库很快膨胀到几个 GB，clone 慢到崩溃。
- **原理简述**：**Git LFS（Large File Storage）** 把大文件本身存到**单独的 LFS 服务器**上，在 Git 仓库里只留一个很小的"**指针文件**"（记录该大文件的哈希和大小）。这样仓库本体保持轻量，用到大文件时才按需下载。
- **基本用法**：

```bash
git lfs install                 # 初始化（每台机器装一次）
git lfs track "*.psd"           # 声明：所有 .psd 文件走 LFS
git lfs track "*.mp4"           # 视频也走 LFS
git add .gitattributes          # track 规则会写进 .gitattributes，必须提交
git add design.psd
git commit -m "chore: 用 LFS 管理设计稿"
git push                        # 大文件传到 LFS，仓库里只留指针
```

> 记忆：**仓库里存"指针"，大文件存"别处"**。`git lfs track` 的规则记录在 `.gitattributes` 里，一定要提交，否则队友不生效。

### 4.11 发布与版本管理（DevOps 相关）

#### 4.11.1 语义化版本 SemVer

版本号格式 **`MAJOR.MINOR.PATCH`**（如 `2.4.1`），每一位的含义有严格约定：

| 位置 | 名称 | 什么时候 +1 |
|---|---|---|
| MAJOR | 主版本 | 有**不兼容**的改动（破坏了旧用法） |
| MINOR | 次版本 | **新增功能**但向下兼容 |
| PATCH | 修订号 | 只是**修 bug**、向下兼容 |

例：`1.4.2 → 1.4.3`（修了个 bug）；`1.4.3 → 1.5.0`（加了新功能）；`1.5.0 → 2.0.0`（改了不兼容的 API）。这套规则和 4.3 的 Conventional Commits 能**自动联动**，实现版本号全自动推算。

#### 4.11.2 用 tag 驱动 release / 部署

**tag（标签）** 是给某个 commit 打的"永久书签"，通常用来标记发布点：

```bash
git tag -a v1.5.0 -m "发布 1.5.0：支持验证码登录"   # 打附注标签
git push origin v1.5.0                              # 把标签推到远程
```

推送这个 tag 会**触发 CI/CD 流水线**：拉取该 tag 的代码 → 构建 → 生成 GitHub/GitLab Release → 部署到生产。**"打 tag = 发版"** 是最常见的发布触发方式。

#### 4.11.3 发布回滚思路（面试常问）

线上出问题要回退，两条主流思路：

1. **`git revert`（推荐、安全）**：生成一个"反向提交"来抵消出问题的改动。**它不删除历史、不改写已推送的提交**，特别适合已经发布到共享分支的代码。回退后重新走一遍流水线部署即可。
2. **重新部署上一个 tag**：如果发布是按 tag 驱动的，最快的回滚就是**让流水线重新部署上一个稳定 tag**（如从 `v1.5.0` 退回 `v1.4.3` 的构建产物），把用户流量切回旧版本。

> 关键原则：**共享/已发布的历史用 `revert`，不要用 `reset` + 强推去"抹掉"**——那会破坏别人的历史。

#### 4.11.4 环境 / 分支 / tag 的映射

一个典型的映射关系（把"代码位置"和"部署到哪"绑定起来）：

| 分支 / tag | 对应环境 | 触发动作 |
|---|---|---|
| `feature/*` 的 PR | 临时预览环境 | 合并前预览 |
| `develop` / `main` | 测试 / 预发环境 | push 即自动部署 |
| `v*` tag | 生产环境 | 打 tag 触发正式发布 |

这张映射表就是 DevOps 里"Git 驱动部署"的骨架——**明确了"改哪、发哪"**。

### 4.12 团队规范与安全

#### 4.12.1 `.gitignore` 与 `.gitattributes`

- **`.gitignore`**：告诉 Git**哪些文件不要纳入版本管理**（编译产物、依赖目录 `node_modules/`、日志、本地配置、密钥文件等）。放进来的东西 Git 会"装作看不见"，避免把垃圾和敏感文件提交上去。
- **`.gitattributes`**：给特定文件配置**处理规则**，DevOps 常用三类：
  - **换行符统一**：`* text=auto`，避免 Windows（CRLF）和 Linux（LF）换行差异导致的"整文件都显示改动"的假冲突；
  - **LFS 标记**：`*.mp4 filter=lfs diff=lfs merge=lfs -text`（`git lfs track` 会自动写进来）；
  - **语言检测**：`*.js linguist-vendored` 之类，控制 GitHub 语言统计、把第三方代码排除出统计。

#### 4.12.2 绝不把密钥 / 大文件提交进仓库

- **密钥（API Key、密码、私钥、token）一旦提交就等于泄露**——即使你后来删掉，它**仍留在 Git 历史里**，任何人翻历史都能拿到。所以：敏感信息一律用**环境变量 / 密钥管理服务（如 Vault、平台的 Secrets）**，并把配置文件写进 `.gitignore`。
- **大文件**别直接塞进仓库（用 LFS，见 4.10），否则拖垮整个仓库。
- **万一误提交了敏感信息怎么办（引子）**：**第一件事是立刻作废/轮换那个密钥**（因为它已经泄露，从历史里删掉也不代表没人抄走过）；然后才是用工具（`git filter-repo`、BFG Repo-Cleaner）从**整个历史**里彻底清除。
  > 具体的历史清除命令和操作步骤，见后面的"面试题板块"详解，这里只需建立"删了还不够、必须先轮换密钥"的意识。

#### 4.12.3 GPG / SSH 签名提交（Signed Commits）

- **大白话**：Git 提交里的"作者"信息是可以随便填的——我完全能把 `user.name` 改成你的名字来冒充你提交。**签名提交**就是给提交盖一个"防伪印章"，证明"这次提交**确实是我本人**做的、没被篡改"。
- **怎么做**：用 GPG 密钥或 SSH 密钥对提交签名（`git commit -S`），把公钥登记到 GitHub/GitLab，平台就会给验证通过的提交打上绿色的 **"Verified"** 标记。
- **DevOps 意义**：可以在**受保护分支**上要求"只接受签名提交"，防止有人伪造身份往主干注入代码，是供应链安全的一环。

> 一句话总结本板块：**分支模型定"怎么并行开发"，PR/评审/保护分支定"怎么保证质量"，commit 规范 + tag + CI/CD 定"怎么自动化发布"，hooks 和签名定"怎么守住安全底线"**——这四条线合起来，就是一个团队完整的 Git 工程化协作体系。

### 一、基础概念与命令区别题（高频，先把地基打牢）

#### Q：Git 和 SVN 的区别是什么？为什么说 Git 是"分布式"的？⭐

答：

先用大白话理解两个词：

- **集中式（SVN）**：只有一个"中央服务器"保存完整的项目历史。你电脑上只有"某一个版本的文件"，没有历史记录。你想看历史、提交、回滚，都必须连上中央服务器。中央服务器一挂，或者网断了，你几乎啥都干不了。
- **分布式（Git）**：**每个人电脑上都是一份完整的仓库**（包含全部提交历史）。你 `git clone` 下来的不是"一个版本"，而是"整个项目从古到今的所有版本"。所以你断网也能提交、看历史、切分支、回滚，只有最后要和别人同步时才需要联网（push/pull）。

对比表：

| 维度 | SVN（集中式） | Git（分布式） |
|---|---|---|
| 历史存在哪 | 只在中央服务器 | 每个人本地都有一份完整历史 |
| 断网能干活吗 | 基本不能提交 | 能，本地随便 commit |
| 提交速度 | 慢（要走网络） | 快（本地操作） |
| 分支成本 | 重（相当于复制一份目录） | 极轻（只是一个 41 字节的指针） |
| 单点故障 | 中央服务器挂了很麻烦 | 任何一份克隆都能恢复整个项目 |
| 典型命令 | `svn commit`（直接进中央库） | `git commit`（进本地库）+ `git push`（再同步远程） |

一句话记忆：**SVN 的 commit 是"直接上传到中央"，Git 的 commit 是"先存本地，push 才上传"**。这也是初学者最容易懵的点——Git 的"提交"和"推送"是两步。

可能的追问：
- "既然每个人都有完整历史，那 Git 有中央服务器吗？" → 有，但它只是"约定俗成的一个共享节点"（比如 GitHub、GitLab），技术上和你本地的仓库是平等的，不是必需的。

#### Q：请解释 Git 的三大区域：工作区、暂存区、版本库。⭐

答：

这是 Git 的**核心心智模型**，务必背熟。用"寄快递"打比方：

- **工作区（Working Directory）**：你正在编辑的文件夹，就是你眼睛能看到、手能改的那些文件。相当于"你桌子上摊开的东西"。
- **暂存区（Staging Area / Index）**：一个"待打包清单"。你用 `git add` 把改动放进去，表示"这些我准备提交了"。相当于"你已经装进快递箱、但还没封箱寄出的东西"。
- **版本库（Repository，即 `.git` 目录）**：真正永久保存历史的地方。`git commit` 会把暂存区的内容封装成一个提交，永久记录下来。相当于"快递已经封箱、发出、有了物流单号"。

流程和对应命令：

```
工作区  --- git add --->  暂存区  --- git commit --->  版本库
（改文件）              （待提交清单）              （永久历史）
```

为什么要多一个暂存区（很多人问"直接改完就提交不行吗"）？

因为它让你能**精挑细选**这次提交哪些改动。比如你改了 5 个文件，但只有 3 个属于"修复登录 bug"，另外 2 个是"顺手改的别的东西"。你可以只 `git add` 那 3 个，单独提交，让历史更清晰。这就是暂存区的价值——**控制提交的粒度**。

配套查看命令：

```bash
git status      # 看三大区域的差异：哪些改了没add，哪些add了没commit
git diff        # 看"工作区 vs 暂存区"的差异（还没add的改动）
git diff --staged  # 看"暂存区 vs 版本库"的差异（已add待commit的改动）
```

#### Q：`git fetch` 和 `git pull` 有什么区别？⭐

答：

一句话：**`git pull` = `git fetch` + `git merge`**。

- **`git fetch`**：只是"把远程的最新提交下载到本地"，但**不动你当前的分支**。它更新的是本地的"远程跟踪分支"（比如 `origin/main`），你自己的 `main` 还是原样。相当于"我先把快递取回来放门口，但还没拆开用"。
- **`git pull`**：先 fetch，然后**立刻把远程的改动合并进你当前分支**。相当于"取回快递并当场拆开、装到你正在用的东西上"。

为什么建议初学者多用 `fetch` 再手动 merge？

因为 `pull` 是"下载 + 合并"一步到位，如果远程有冲突或者有你没预料到的改动，它会直接在你本地触发合并（甚至产生冲突），打你个措手不及。而 `fetch` 让你能**先看一眼再决定**：

```bash
git fetch origin              # 先取回，不合并
git log HEAD..origin/main     # 看看远程比我多了哪些提交
git merge origin/main         # 确认没问题，再合并
```

可能的追问：
- "`git pull --rebase` 是什么？" → 它把默认的 merge 换成 rebase，即"把我的提交挪到远程最新提交的后面"，历史更线性、没有多余的合并提交。团队里很常用。

---

#### Q：`git merge` 和 `git rebase` 的区别？各自什么场景用？⭐⭐

答：

两者目的相同——**把一个分支的改动整合到另一个分支**，但方式和产生的历史完全不同。

假设 `main` 和 `feature` 分叉了：

- **merge（合并）**：把两个分支的内容"捏到一起"，生成一个**新的合并提交（merge commit）**，这个提交有两个父提交。历史里能看到"这里曾经分叉又合并了"的痕迹。
- **rebase（变基）**：把你 `feature` 分支上的提交，**一个个"搬到" `main` 最新提交的后面**，就好像你是从最新的 `main` 才开始开发的。历史变成一条直线，看不到分叉痕迹。

图示对比：

```
merge 后：
      A---B---C  (feature)
     /         \
D---E---F---G---M(merge)  (main)

rebase 后（feature 的 A B C 被重放成 A' B' C'）：
D---E---F---G---A'---B'---C'   一条直线
```

对比表：

| 维度 | merge | rebase |
|---|---|---|
| 历史形状 | 有分叉、有合并点 | 一条直线，干净 |
| 是否改写提交 | 不改，保留原提交 | **改写**（哈希变了，是"复制品"） |
| 保留真实过程 | 是（如实记录分叉） | 否（伪装成线性开发） |
| 适合 | 公共分支、多人协作分支 | 自己本地的、还没push的分支 |

**黄金法则（面试必答）**：**永远不要对已经 push 到公共/共享分支的提交做 rebase**。因为 rebase 改写了提交哈希，别人基于旧提交做的工作会对不上，导致团队历史混乱。rebase 只用在"自己本地、还没分享出去"的提交上，用来在 push 前把历史整理干净。

场景总结：
- 想让功能分支合进主干、并保留"这是一次功能合并"的记录 → `merge`（配合 `--no-ff`）。
- push 前想把自己乱七八糟的本地提交整理成整洁线性历史 → `rebase`。

#### Q：`git reset` 和 `git revert` 的区别？⭐⭐

答：

两者都能"撤销提交"，但本质完全不同，关键区别在**是否改写历史**。

- **`git reset`**：**把分支指针往回移**，让某些提交"从历史里消失"（其实还在，但分支不指向它们了）。这是**改写历史**，适合撤销**还没 push**的提交。
- **`git revert`**：**新建一个提交**，这个新提交的内容正好是"把某次提交的改动反向抵消"。原来的提交**仍然保留在历史里**，只是又追加了一个"反做"的提交。这是**不改写历史**，适合撤销**已经 push**的提交。

打比方：
- reset 像"用橡皮擦把写错的字擦掉"——纸面上看不出你写过错字。
- revert 像"写错了不擦，而是在后面补一句'上面那句作废'"——白纸黑字都留着。

为什么已 push 的提交必须用 revert？

因为别人已经拉走了你的历史。你要是用 reset 把提交"擦掉"再强推，别人的本地历史就和远程对不上了，会一片混乱。revert 只是"往前追加一个提交"，对所有人都安全。

```bash
# 撤销还没push的最后一次提交（reset）
git reset --hard HEAD~1        # 连改动一起丢弃

# 撤销已经push的某次提交（revert）
git revert <那次提交的哈希>    # 生成一个反向提交，再正常push
```

可能的追问见下面的"底层原理题"里对 reset 三种模式的拆解。

#### Q：HEAD 是什么？什么是 detached HEAD（分离头指针）？

答：

- **HEAD** 是一个指针，永远指向**你当前所在的位置**，通常是"当前分支的最新提交"。你可以理解为"你现在站在哪儿"的一个书签。大多数时候 `HEAD → 当前分支 → 最新提交`，是一个两层指向关系。

- **detached HEAD（分离头指针）**：当你不是"站在某个分支上"，而是**直接站在某个具体提交上**时（比如 `git checkout <某个提交哈希>` 或 `git checkout v1.0` 标签），HEAD 就直接指向那个提交，而不是指向分支。这时 Git 会警告你 "You are in detached HEAD state"。

为什么这状态危险？

因为你在这个状态下做的**新提交不属于任何分支**。一旦你切走（checkout 到别的分支），这些提交就"没人认领"了，过段时间会被 Git 垃圾回收删掉，很难找回。

正确姿势：如果你在 detached HEAD 状态下想保留新做的提交，赶紧建个分支把它"接住"：

```bash
git switch -c new-branch    # 立刻建分支，把当前提交纳入这个分支
```

什么时候会故意用 detached HEAD？临时想看看"老版本长啥样"、跑一下老代码调试，看完就切回来，不做提交，这时用它很正常。

#### Q：什么是 fast-forward（快进）合并？

答：

假设 `main` 没有任何新提交，你在 `feature` 分支上做了几个提交。现在把 `feature` 合回 `main`，Git 发现：`main` 完全落后于 `feature`，中间没有分叉。这时它不需要真正"合并"，只要**把 `main` 指针直接往前挪到 `feature` 的位置**就行了——这就叫 fast-forward（快进）。

```
合并前：
D---E  (main)
     \
      F---G  (feature)

fast-forward 合并后（main 直接挪到 G）：
D---E---F---G  (main, feature)
```

特点：**不产生新的合并提交**，历史是一条直线。

面试常问的延伸——`--no-ff`：

有时候我们**故意不要快进**，用 `git merge --no-ff`，强制生成一个合并提交。为什么？因为这样能在历史里**留下"这里合入了一个功能分支"的记录**，日后回溯"这个功能是啥时候、通过哪次合并进来的"更清晰。很多团队规定主干合并一律用 `--no-ff`。

```bash
git merge feature            # 能快进就快进（默认）
git merge --no-ff feature    # 强制生成合并提交，保留分支痕迹
```

#### Q：`git add .`、`git add -A`、`git add -u` 有什么区别？

答：

这三个都是把改动加入暂存区，区别在**范围**和**是否包含删除/新增**：

| 命令 | 新增文件 | 修改文件 | 删除文件 | 作用范围 |
|---|---|---|---|---|
| `git add .` | ✅ | ✅ | ✅（新版 Git） | 当前目录及子目录 |
| `git add -A` | ✅ | ✅ | ✅ | **整个仓库**（不管你现在在哪个子目录） |
| `git add -u` | ❌ | ✅ | ✅ | 只处理**已跟踪**的文件，不加新文件 |

关键区别讲清楚：

- `-A`（`--all`）：**整个仓库**所有变化都加进来，包括你在别的子目录里的新增文件。范围最广。
- `.`：只处理**你当前所在目录往下**的变化。如果你在 `src/` 子目录里敲 `git add .`，仓库根目录下的新文件不会被加进来。
- `-u`（`--update`）：**只更新已经被 Git 跟踪过的文件**（改了的、删了的），**不会把全新文件加进来**。适合"我只想提交对现有文件的修改，新建的临时文件先别动"的场景。

初学者小提醒：老版本 Git 里 `git add .` 不会暂存"删除操作"，需要用 `-A` 或 `-u`。新版本已经修复，`git add .` 也会处理删除了。面试答"`.` 是当前目录范围，`-A` 是整个仓库范围，`-u` 只管已跟踪文件"即可。

#### Q：`.gitignore` 为什么对已经跟踪的文件不起作用？怎么办？⭐

答：

先理解一个关键点：**`.gitignore` 只对"还没被 Git 跟踪过"的文件生效**。它的作用是"告诉 Git 忽略这些还没纳入管理的文件"。

一旦一个文件已经被 `git add` 提交过（进入了跟踪状态），你再把它写进 `.gitignore` 是**没用的**——因为 Git 已经在管它了，`.gitignore` 管不到"已经在管的东西"。这是初学者极其常见的坑：明明把 `config.log` 写进了 `.gitignore`，它还是一直被提交。

解决办法：**先把它从 Git 的跟踪里移除（但保留本地文件），再让 `.gitignore` 生效**。

```bash
# --cached 表示只从 Git 跟踪里删，本地文件保留不动
git rm --cached config.log

# 如果是一整个目录
git rm -r --cached logs/

# 然后确保 .gitignore 里有它，再提交
git commit -m "停止跟踪 config.log，改为忽略"
```

关键在 `--cached` 这个参数：**只把文件从"Git 的管辖"里拿掉，硬盘上的文件不删**。之后这个文件就变回"未跟踪"状态，`.gitignore` 就能正常忽略它了。

可能的追问：
- "我 `.gitignore` 写对了但某个新文件还是被跟踪？" → 检查是不是之前不小心 `git add -f`（force）强制加过，或者它已经在历史里了。用 `git check-ignore -v <文件名>` 可以查是哪条规则匹配（或没匹配）。

#### Q：轻量标签（lightweight tag）和附注标签（annotated tag）有什么区别？

答：

标签（tag）就是给某次提交起个"好记的名字"，通常用来标记版本（比如 `v1.0.0`）。它分两种：

- **轻量标签**：就是一个"指向某次提交的书签"，**不含任何额外信息**（没有作者、日期、说明）。它本质上只是一个名字。
- **附注标签**：是一个**完整的对象**，存了打标签的人、日期、一段说明消息，甚至可以用 GPG 签名。

对比：

| 维度 | 轻量标签 | 附注标签 |
|---|---|---|
| 存储 | 只是个指针 | 独立的 Git 对象 |
| 含作者/日期/说明 | ❌ | ✅ |
| 可签名（GPG） | ❌ | ✅ |
| 适合 | 临时、本地标记 | **正式发布版本** |

命令：

```bash
git tag v1.0                          # 轻量标签
git tag -a v1.0 -m "发布 1.0 正式版"   # 附注标签（-a = annotated）
git push origin v1.0                  # 标签默认不会自动push，要手动推
git push origin --tags                # 一次推所有标签
```

面试建议答：**正式发布一律用附注标签**，因为它记录了"谁、什么时候、为什么打的这个版本"，对追溯发布历史很重要。

### 二、实操场景题（面试最爱问"你会怎么做"）⭐

#### Q：怎么撤销"还没 push"的最后一次 commit？分"保留改动"和"不保留改动"两种情况。⭐

答：

关键工具是 `git reset`，区别在**改动去哪了**：

```bash
# 情况1：撤销提交，但代码改动保留在暂存区（还想重新提交）
git reset --soft HEAD~1

# 情况2：撤销提交，改动退回工作区（回到没add的状态，最常用）
git reset --mixed HEAD~1     # --mixed 是默认，可省略，即 git reset HEAD~1

# 情况3：撤销提交，连改动一起彻底丢弃（慎用！代码没了）
git reset --hard HEAD~1
```

`HEAD~1` 的意思是"当前提交往前数 1 个"，即"上一个提交"。三种模式的差别我在底层题里详细讲，这里先记结论：

- `--soft`：提交没了，改动还在暂存区（`git status` 显示"待提交"）。
- `--mixed`（默认）：提交没了，改动退回工作区（显示"改了没add"）。**最常用、最安全**。
- `--hard`：提交和改动**全部消失**，工作区变干净。手滑会丢代码，用前确认。

强调：这套只适用于**还没 push** 的提交。已 push 的见下一题。

---

#### Q：已经 push 出去的 commit 要撤销，怎么办？为什么不能直接 reset？⭐⭐

答：

**已 push 的提交要用 `git revert`，不能用 reset。**

原因（面试核心）：提交一旦 push，别人可能已经拉走了。如果你用 `reset` 把它"抹掉"再强推（force push），你和远程的历史就对不上了，别人再 pull 会产生一堆冲突和混乱，等于污染了整个团队的历史。

`git revert` 的做法是"**不删旧账，而是记一笔反向的账**"——它新建一个提交，内容正好抵消要撤销的那次提交，历史往前推进，对所有人都安全。

```bash
# 撤销某一次已push的提交
git revert <要撤销的提交哈希>
# Git 会生成一个"反向提交"，让你填提交信息，保存后
git push                     # 正常推送，不需要force

# 撤销一个范围的多次提交
git revert <旧哈希>..<新哈希>
```

延伸场景：
- "如果撤销的是一个合并提交（merge commit）？" → 要加 `-m 1` 指定保留哪个父分支：`git revert -m 1 <合并提交哈希>`。这是个高频坑，因为合并提交有两个父提交，Git 不知道你要"反做"到哪一边，必须显式指定主线（`-m 1` 通常指第一个父，即被合入的目标分支）。

#### Q：怎么把最近的多个 commit 合并成一个（squash）？⭐

答：

场景：你开发一个功能时提交了很多零碎的提交（"改bug"、"再改改"、"typo"），想在合并进主干前**压缩成一个干净的提交**。这叫 squash（压缩）。

方法一：交互式 rebase（最常用）

```bash
git rebase -i HEAD~3       # 整理最近 3 个提交
```

执行后会弹出一个编辑器，列出这 3 个提交：

```
pick a1b2c3 实现登录功能
pick d4e5f6 修复登录bug
pick g7h8i9 改个typo
```

把后两行的 `pick` 改成 `squash`（或简写 `s`），表示"把它们并入上面那个提交"：

```
pick a1b2c3 实现登录功能
squash d4e5f6 修复登录bug
squash g7h8i9 改个typo
```

保存退出后，Git 会再让你编辑"合并后的提交信息"，改好保存，三个提交就变成一个了。

方法二：soft reset（更简单直观，适合合并"最近连续的几个"）

```bash
git reset --soft HEAD~3    # 撤销最近3个提交，但改动全留在暂存区
git commit -m "实现登录功能"  # 重新提交成一个
```

这个思路是：用 `--soft` 把 3 个提交"退回"，代码全部保留在暂存区，然后一次性重新提交。

注意：squash 改写了历史，所以同样**只在还没 push 的提交上做**；如果已 push，压缩后需要 force push，且要通知团队。

---

#### Q：怎么修改某次历史 commit 的提交信息（message）？

答：

分两种情况：

情况一：改的是**最后一次**提交的信息（最简单）

```bash
git commit --amend -m "新的正确的提交信息"
```

`--amend` 的意思是"修补上一次提交"。注意它其实是**用一个新提交替换掉旧的**（哈希会变）。

情况二：改的是**更早的**某次提交信息 → 用交互式 rebase

```bash
git rebase -i HEAD~3        # 假设要改的提交在最近3个之内
```

在弹出的列表里，把要改的那一行的 `pick` 改成 `reword`（或 `r`）：

```
pick a1b2c3 这条不改
reword d4e5f6 这条我要改信息
pick g7h8i9 这条不改
```

保存退出后，Git 会停下来让你编辑那条提交的信息，改完保存即可。

⚠️ 提醒：两种方式都改写了历史（哈希变了）。如果这些提交已经 push 过，改完要 `git push --force-with-lease`，并且要通知协作者。没 push 的话随便改。

#### Q：不小心删了本地分支，或者被 `git reset --hard` 丢了提交，怎么找回？⭐⭐

答：

**救命神器：`git reflog`。** 面试里这是个高分点。

先理解原理：Git 把你**每一次 HEAD 的移动**（提交、切分支、reset、rebase、merge……）都偷偷记在一个叫 reflog（reference log，引用日志）的地方。哪怕你 reset --hard 把提交"删了"，那个提交对象**其实还在 Git 仓库里**，只是没有分支指向它了。reflog 记着它曾经的哈希，所以能找回。

操作步骤：

```bash
git reflog            # 查看HEAD的移动历史，会列出类似：
# a1b2c3 HEAD@{0}: reset: moving to HEAD~1
# d4e5f6 HEAD@{1}: commit: 我丢失的那个提交   ← 就是它！
```

找到丢失提交的哈希（比如 `d4e5f6`）后，把它救回来：

```bash
# 方法1：新建一个分支指向它
git branch recovered d4e5f6

# 方法2：如果只是想把当前分支拉回那个位置
git reset --hard d4e5f6

# 找回误删的分支同理：reflog找到分支最后所在的提交，再建分支
```

为什么能找回（原理，说出来加分）：Git 不会立刻物理删除"没人引用"的提交，它们会在仓库里保留一段时间（默认可达对象 30 天、不可达对象 2 周），直到 `git gc`（垃圾回收）真正清理。所以只要你**及时**用 reflog 找，通常都能救回来。

一句话记忆：**"我的提交丢了" 的标准答案就是 `git reflog`。**

#### Q：完整讲一下解决合并冲突（merge conflict）的步骤。⭐

答：

先讲什么时候会冲突：当两个分支**改了同一个文件的同一部分**，Git 无法自动判断该保留谁的，就会"停下来问你"，这就是冲突。

完整步骤：

**第 1 步**：执行合并，Git 报告冲突

```bash
git merge feature
# CONFLICT (content): Merge conflict in app.py
```

**第 2 步**：用 `git status` 看哪些文件冲突了（会列在 "Unmerged paths" 下）

**第 3 步**：打开冲突文件，你会看到 Git 插入的冲突标记：

```
<<<<<<< HEAD
这是当前分支（比如 main）的内容
=======
这是要合并进来的分支（feature）的内容
>>>>>>> feature
```

三段的含义：
- `<<<<<<< HEAD` 到 `=======` 之间：你**当前分支**的版本。
- `=======` 到 `>>>>>>> feature` 之间：**对方分支**的版本。

**第 4 步**：手动编辑，决定最终要什么——可以留一边、留另一边、或者两边融合。**改完必须把 `<<<<`、`====`、`>>>>` 这些标记全部删掉**，只留你想要的最终代码。

**第 5 步**：标记冲突已解决 + 完成合并

```bash
git add app.py             # add 就代表"这个文件我解决好了"
git commit                 # 完成合并（merge时通常直接git commit即可）
```

实用技巧（面试可以主动说，显得有经验）：
- `git merge --abort` —— 冲突太乱、想反悔，一键回到合并前的状态。
- 用带图形界面的合并工具：`git mergetool`，或直接在 VS Code 里点按钮选"接受当前/接受传入/都接受"，比手动删标记更不容易出错。

#### Q：只想把另一个分支上的**某一个**提交拿过来，怎么办（cherry-pick）？⭐

答：

场景：`feature` 分支上有 5 个提交，但你只想要其中"修复了某个bug"的那**一个**提交，不想把整个分支合过来。这时用 `git cherry-pick`（字面意思"精挑细选、摘樱桃"）。

```bash
# 先切到你想接收提交的分支
git switch main

# 把 feature 上那个提交"复制"一份过来
git cherry-pick <那个提交的哈希>

# 一次摘多个
git cherry-pick <哈希1> <哈希2>

# 摘一个连续范围（左开右闭：不含A，含B）
git cherry-pick A..B
```

原理：cherry-pick 会把指定提交的**改动内容**在你当前分支上"重新应用一遍"，生成一个**新的提交**（哈希和原来不同，因为父提交变了）。所以它是"复制改动"，不是"移动"。

如果 cherry-pick 过程中冲突了，处理方式和合并冲突一样：改文件 → `git add` → `git cherry-pick --continue`（或 `--abort` 放弃）。

典型用途见下一题（把 hotfix 从某分支摘出来）。

---

#### Q：线上出了紧急 bug，某个修复提交在 develop 分支上，怎么单独摘到 hotfix / 主干上线？

答：

这是 cherry-pick 最经典的实战场景。假设：
- `develop` 是日常开发分支，里面掺杂了很多**还没测试完、不能上线**的功能。
- 其中有一个提交 `abc123` 是"修复了线上紧急 bug"，你**只想上线这一个修复**，不想把 develop 里其它半成品也带上线。

做法：

```bash
# 1. 从当前线上版本（比如main或某个tag）拉一个hotfix分支
git switch main
git switch -c hotfix/urgent-bug

# 2. 把 develop 上那个修复提交摘过来
git cherry-pick abc123

# 3. 测试通过后，合并进 main 并打tag发布
git switch main
git merge --no-ff hotfix/urgent-bug
git tag -a v1.2.1 -m "紧急修复线上bug"
git push origin main --tags

# 4. 别忘了把 main 的修复也合回 develop，避免下次发布又冒出来
```

为什么不用 merge 整个 develop？因为那会把 develop 里所有未完成的功能一起带上线，风险极大。cherry-pick 让你**精准地只上线需要的那一个改动**，这是它的核心价值。

#### Q：`git stash` 是干什么的？什么场景用？⭐

答：

大白话：stash 就是一个"**临时抽屉**"。你手头改了一半的代码还不想提交，但突然需要切到别的分支干点急事——直接切分支 Git 会拦你（怕丢改动）。这时把当前改动"塞进抽屉"，工作区瞬间变干净，你就能自由切分支了；忙完再"从抽屉里拿回来"继续。

典型场景：
1. 正在开发功能，突然要紧急切到别的分支修 bug。
2. 想 `git pull` 拉取更新，但本地有未提交改动挡着。
3. 想临时切个干净环境跑一下测试。

常用命令：

```bash
git stash              # 把当前改动存进抽屉，工作区变干净
git stash push -m "登录功能改了一半"   # 存的时候加个备注，方便识别

git stash list         # 看抽屉里存了哪些（stash@{0}、stash@{1}...）

git stash pop          # 取出最近一次存的，并从抽屉里删除
git stash apply        # 取出但不删除（抽屉里还留着，可反复应用）

git stash drop stash@{0}   # 删掉某一条
git stash clear            # 清空抽屉
```

`pop` 和 `apply` 的区别是**取出后要不要从抽屉删掉**——`pop` 用完即删，`apply` 用完还留着。初学者常用 `pop`。

小坑：`git stash` 默认**不会**保存"新建但还没 add 的文件"（未跟踪文件）。要一起存需加 `-u`（`git stash -u`）。

#### Q：不小心把密码/密钥等敏感信息提交并 push 上去了，怎么彻底清除？⭐⭐⭐

答：

这是 DevOps 岗**极高频**且体现安全意识的题。先说最重要的一句：**只从最新提交里删掉是没用的，因为它还留在历史记录里，任何人 clone 都能翻出来。必须改写历史，把它从所有相关提交里彻底抹除。**

完整应对流程（顺序很重要）：

**第 1 步（最紧急）：立刻轮换密钥。**
既然密钥已经 push（甚至可能被别人、被爬虫抓到），**它就该被视为已泄露**。第一时间去对应平台**作废旧密钥、生成新密钥**。这比清理 Git 历史更优先——因为清理需要时间，而泄露的密钥每一秒都在暴露。

**第 2 步：用工具把敏感信息从整个历史里抹掉。**
推荐 `git filter-repo`（官方推荐，比老旧的 `git filter-branch` 快且安全）或 `BFG Repo-Cleaner`。

```bash
# 方法A：git filter-repo，删除某个文件的所有历史痕迹
git filter-repo --path config/secrets.yml --invert-paths

# 方法B：BFG，替换掉所有历史里的某个字符串/密钥
bfg --replace-text passwords.txt   # passwords.txt里写要清除的敏感串
```

`--invert-paths` 的意思是"反选"，即"保留除了这个文件之外的所有东西"，等于把这个文件从全部历史里删干净。

**第 3 步：强制推送改写后的历史到远程。**

```bash
git push --force --all
git push --force --tags
```

因为你改写了历史，必须 force push 覆盖远程。

**第 4 步：通知团队所有人。**
历史被改写后，别人本地的旧历史全部失效。要通知他们**重新 clone**（或按流程 rebase），否则他们一 push 又会把敏感信息带回来。

**第 5 步：善后。**
- 把敏感文件加进 `.gitignore`，防止再次提交。
- 检查有没有 fork、缓存、CI 日志里也残留（GitHub 的缓存可能需要联系官方清理）。

一句话总结面试答法：**"轮换密钥 → filter-repo/BFG 改写历史 → force push → 通知团队重新clone → 加 .gitignore 防复发"，核心认知是"删最新提交没用，敏感信息一旦push就默认已泄露，必须轮换 + 改写全历史"。**

#### Q：不小心提交了一个很大的文件（比如几百 MB 的日志/二进制），怎么处理？

答：

分两种情况：

情况一：**还没 push，就在最近的提交里**

```bash
# 如果就是最后一次提交，撤销提交、移除大文件、重新提交
git reset --soft HEAD~1        # 退回提交，改动留暂存区
git rm --cached huge_file.zip  # 把大文件移出暂存区（本地保留）
echo "huge_file.zip" >> .gitignore
git commit -m "移除误提交的大文件"
```

情况二：**已经 push，或者大文件深埋在历史里**

大文件即使从最新提交删掉，仍然留在历史里、仓库依旧臃肿。必须像清理敏感信息一样**改写历史**：

```bash
git filter-repo --path huge_file.zip --invert-paths
git push --force --all
# 同样要通知团队重新clone
```

预防和根本解法：
- 大的二进制文件（图片、视频、模型、数据集）**本就不该直接放进 Git**。Git 擅长管文本（能算差异），对大二进制文件只能整份整份存，会让仓库迅速膨胀。
- 正确做法是用 **Git LFS**（Large File Storage）来管这类文件（见 DevOps 部分的题）。
- 把大文件类型写进 `.gitignore` 从源头拦住。

### 三、底层原理题（能答好这些，直接和别人拉开差距）

#### Q：Git 保存的是"快照"还是"差异"？⭐⭐

答：

**Git 存的是快照（snapshot），不是差异（diff）。** 这是 Git 和很多老版本控制系统（如 SVN、CVS）最本质的区别之一。

- **差异模型（SVN 那套）**：只记录"每个版本相比上一版，改了哪几行"。想还原某个版本，得从头把一串差异累加起来。
- **快照模型（Git）**：每次 commit，Git 都给**当时项目的全部文件拍一张完整的"照片"**存起来。

有人立刻会问："那不会很占空间吗？每次都存全量？" —— 这是理解 Git 的关键点：**如果一个文件在两次提交之间没有变化，Git 不会重复存它，而是让新快照直接指向之前那份一模一样的文件对象**（Git 用文件内容算出的哈希来去重，内容相同就是同一个对象）。所以只有**变化了的文件**才会存新的一份，没变的复用旧的，空间并不会爆炸。

（补充：Git 后台还有个叫 packfile 的机制，会把对象打包压缩、对相似对象做 delta 压缩来省空间，但那是存储层的优化，**逻辑模型上 Git 就是快照**。）

为什么快照模型好？因为**切分支、看任意版本、对比都非常快**——直接拿那张"照片"即可，不用把一堆差异重新累加计算。这也是 Git 分支和切换如此快的底层原因。

---

#### Q：Git 的四种对象是什么？commit 对象里到底存了什么？⭐⭐

答：

Git 底层就是一个"按内容寻址的数据库"，一切都由四种对象构成，每个对象用它内容的 SHA-1 哈希当"身份证号"：

| 对象类型 | 存什么 | 打比方 |
|---|---|---|
| **blob**（数据对象） | 一个**文件的内容**（不含文件名） | 一张纸上的文字 |
| **tree**（树对象） | 一个**目录**：记录该目录下有哪些文件名、对应哪个 blob，以及子目录（子 tree） | 目录的文件清单 |
| **commit**（提交对象） | 一次提交的元信息 | 一次存档的封面 |
| **tag**（标签对象） | 附注标签的信息（指向某提交 + 说明 + 签名） | 贴的版本标签 |

**commit 对象里具体存了什么**（面试重点，能背出来加分）：

1. 一个指向 **tree** 的指针 —— 代表"这次提交时，整个项目的目录结构快照"。
2. **父提交（parent）的哈希** —— 指向上一次提交，这样一串 commit 就连成了历史链条（合并提交有两个 parent）。
3. **作者（author）**信息 + 时间。
4. **提交者（committer）**信息 + 时间。
5. **提交说明（commit message）**。

注意：**commit 对象里并不直接存文件内容**，它只存了一个指向 tree 的指针，tree 再指向各个 blob。层层指向，最终定位到所有文件内容。

它们的关系（层层指向）：

```
commit ──指向──> tree（根目录）
                  ├──> blob（README.md 的内容）
                  ├──> blob（app.py 的内容）
                  └──> tree（src 子目录）
                        └──> blob（src/main.py 的内容）
commit ──指向──> parent commit（上一次提交）
```

你可以亲手验证：

```bash
git cat-file -t <哈希>    # -t 看对象类型（blob/tree/commit/tag）
git cat-file -p <哈希>    # -p 看对象内容，能看到commit里的tree/parent/author
```

#### Q：为什么 rebase、amend 会改变 commit 的哈希？⭐

答：

回到上一题的知识点：**一个 commit 的哈希，是对它全部内容算出来的 SHA-1**。而"它的内容"包括：指向的 tree（文件快照）、**父提交哈希**、作者、提交者、时间、提交信息……

所以，**只要这里面任何一项变了，算出来的哈希就必然变**——哈希本质上是内容的"指纹"，内容一动指纹就变。

- **`git commit --amend`**：你改了提交信息（或补了文件），提交内容变了 → 哈希变。它不是"修改原提交"，而是**生成一个全新提交把旧的替换掉**。
- **`git rebase`**：它把你的提交"搬到"另一个基点后面，也就是**每个被搬动提交的 parent 变了**。parent 变了 → 内容变了 → 哈希必然变。所以 rebase 后的提交都是"内容一样但哈希全新"的复制品，原来的旧提交则被"抛弃"（还能在 reflog 里找到）。

这也解释了那条黄金法则**为什么成立**：因为 rebase/amend 会**换掉提交的哈希**，如果这些提交已经 push、别人已经基于旧哈希工作，哈希一换，大家的历史就对不上号了。所以"改写历史的操作只在没分享出去的提交上做"。

#### Q：执行一次 `git commit`，底层到底发生了什么？

答：

把上面几题串起来，一次 commit 的底层动作是：

1. **为暂存区里每个（新的/改过的）文件内容创建 blob 对象**，各自算出哈希。没变的文件不新建，复用已有 blob。
2. **创建 tree 对象**，记录当前这个快照里各目录下"文件名 → blob 哈希"的对应关系（子目录再对应子 tree）。
3. **创建 commit 对象**，里面写上：指向刚才根 tree 的指针、指向上一次提交的 parent 指针、作者/提交者/时间、你写的提交信息。算出这个 commit 的哈希。
4. **移动分支指针**：让当前分支（比如 `main`）指向这个新 commit；`HEAD` 跟着指向新位置。
5. **记一笔 reflog**：把这次 HEAD 的移动记录下来（这就是日后能用 reflog 找回的原因）。

一句话：**commit = 把暂存区打包成 blob+tree 快照 → 封装成一个带 parent 的 commit 对象 → 把分支指针挪过去。**

#### Q：分支（branch）的本质是什么？为什么说 Git 切分支这么快？⭐

答：

**一个分支的本质，就是一个"指向某个 commit 的、可移动的指针"**——物理上它只是 `.git/refs/heads/` 目录下一个小文件，里面就存了一行：那个 commit 的 40 位哈希。仅 41 字节左右。

这解释了为什么 Git 分支操作快得惊人：

- **创建分支** = 新建一个小文件、写进当前 commit 的哈希。**几乎零成本**，不复制任何文件。（对比 SVN，建分支相当于服务器上复制一整份目录。）
- **切换分支** = 把 `HEAD` 指向另一个分支指针，然后把工作区文件更新成那个 commit 的快照。因为快照复用了大量相同对象，也很快。
- **提交时分支指针自动前移**：你在某分支上 commit，这个分支指针就自动指向新的 commit。

而 `HEAD` 是"指向当前分支的指针"（指针的指针）。所以完整链条是：

```
HEAD ──> main（分支指针）──> commit（某次提交）──> tree ──> blobs
```

一句话记忆：**分支就是一个 41 字节的、指向提交的可移动指针，所以又轻又快。**

#### Q：reflog 为什么能找回"丢失"的提交？Git 的垃圾回收（GC）什么时候才真删对象？⭐

答：

分两层理解：

**为什么能找回**：当你 reset --hard、删分支、rebase 时，你只是**移动或删掉了"指针"**（分支、HEAD 的指向），而那些 commit **对象本身并没有从 Git 的对象数据库里删掉**。它们变成了"没有任何分支/标签指向"的**不可达对象（unreachable objects）**，像"断线的风筝"飘在仓库里。而 `reflog` 忠实记录了 HEAD 曾经指过的每一个位置的哈希，所以你能顺着 reflog 找到那根"断线风筝"的哈希，重新拴上一个分支就救回来了。

**GC 什么时候真删**：Git 会在合适时机（比如仓库里松散对象太多，或你手动 `git gc`）运行垃圾回收，把"不可达且已过保护期"的对象真正物理删除。保护期由配置决定，默认大致是：

- **不可达对象**：默认保留约 **2 周**（`gc.pruneExpire` 默认 `2.weeks.ago`）。
- 被 reflog 引用的对象：reflog 条目本身也有过期时间（可达的默认 90 天、不可达的默认 30 天），过期后对应对象才可能被清。

所以结论是：**丢了提交要尽快用 reflog 找回**，拖太久（几周后）一旦 GC 清理，就真的没了。平时你不用担心 reset 会立刻毁掉代码——有这段"缓冲保护期"兜底。

```bash
git gc                # 手动触发垃圾回收（一般不用手动，Git会自动）
git fsck --unreachable  # 查看当前有哪些不可达对象（也是一种找回途径）
```

#### Q：`git reset` 的 `--soft`、`--mixed`、`--hard` 底层分别动了什么？⭐⭐

答：

这题把"三大区域"和"reset"结合起来考，答好很加分。先记住 reset 干的核心事是"**移动当前分支指针到指定提交**"，三种模式的区别在于**移动指针后，暂存区和工作区要不要跟着一起变**。

| 模式 | 移动分支指针 | 暂存区（Index） | 工作区（文件） | 效果 |
|---|---|---|---|---|
| `--soft` | ✅ | 不动 | 不动 | 提交没了，改动全留在暂存区（待提交状态） |
| `--mixed`（默认） | ✅ | 重置 | 不动 | 提交没了，改动退回工作区（改了没add状态） |
| `--hard` | ✅ | 重置 | **重置** | 提交、暂存、工作区全部回到目标提交，**改动彻底消失** |

一层层理解（从改动最小到最大）：

- **`--soft`**：**只**把分支指针往回挪，暂存区和工作区**原封不动**。所以被"撤销"的那些提交的改动，还乖乖躺在暂存区里，你可以立刻重新 commit。→ 常用于"合并多个提交"（reset --soft 后重新提交一次）。
- **`--mixed`（默认）**：挪指针 + **重置暂存区**（把暂存区变回目标提交的样子），但**工作区文件不动**。所以改动从"暂存"退回到"工作区未add"状态。→ 最常用，"我想撤销提交，重新挑要add的东西"。
- **`--hard`**：挪指针 + 重置暂存区 + **连工作区文件也重置**成目标提交的样子。→ 三个区域全部对齐，工作区里的未提交改动**会被清掉、无法通过普通手段找回**（提交本身还能靠reflog找，但工作区那些没提交过的改动是真没了）。所以 `--hard` 用前一定要确认。

一句话记忆：**soft 只动指针，mixed 动指针+暂存区，hard 动指针+暂存区+工作区（最狠，会丢工作区改动）。**

### 四、DevOps / 工程实践题（贴合岗位方向，重点中的重点）⭐

#### Q：常见的分支策略有哪些（Git Flow / GitHub Flow / Trunk-Based）？怎么选型？⭐⭐

答：

分支策略就是"团队约定怎么用分支来协作和发布"。三种主流：

**1. Git Flow（重型、规范）**
固定好几种长期/临时分支：
- `main`（发布的稳定版）、`develop`（日常开发主线）
- `feature/*`（功能分支，从 develop 切）、`release/*`（发布准备）、`hotfix/*`（线上紧急修复）

优点：分工清晰、适合**有明确版本发布节奏**的产品（如客户端 App、需要维护多个版本）。
缺点：分支多、流程重、合并频繁，对持续交付不友好。

**2. GitHub Flow（轻量）**
只有一个长期分支 `main`，任何改动都从 main 切一个短命的功能分支 → 提 Pull Request → review + CI 通过 → 合回 main → 立即部署。

优点：简单，天然适合**持续部署的 Web 服务**。
缺点：没有专门的发布/预发布分支概念，靠 tag 和环境来管发布。

**3. Trunk-Based Development（主干开发，现代 CI/CD 首选）**
所有人都尽量往**同一个主干（trunk/main）** 上频繁提交，功能分支存在时间极短（几小时到一两天就合并），用 **feature flag（功能开关）** 来隐藏没做完的功能，而不是靠长期分支。

优点：集成极频繁 → 冲突小、最适合 CI/CD 和 DevOps 文化；避免"大分支长期不合、最后合并地狱"。
缺点：要求高（强 CI、feature flag、良好测试），团队纪律要好。

选型对比：

| 策略 | 复杂度 | 适合场景 |
|---|---|---|
| Git Flow | 高 | 有版本号、需维护多版本、发布周期长（如桌面/移动客户端） |
| GitHub Flow | 低 | 持续部署的 Web 应用、开源项目 |
| Trunk-Based | 中（配套要求高） | 追求持续交付、成熟 DevOps 的团队 |

面试答法：**没有绝对最好，看发布节奏和团队成熟度**。追求持续交付、CI/CD 强的现代团队普遍倾向 **Trunk-Based 或 GitHub Flow**；需要维护多个正式版本的产品更适合 Git Flow。

#### Q：Git 是怎么和 CI/CD 集成的？流水线是怎么被触发的？⭐⭐

答：

先解释 CI/CD：
- **CI（持续集成）**：每次代码提交后，自动**拉代码、编译、跑测试、做代码检查**，尽早发现问题。
- **CD（持续交付/部署）**：CI 通过后，自动把产物**部署**到测试/预发/生产环境。

Git 是整个流程的"**触发源和事实来源**"。集成的核心机制是"**Git 事件触发流水线**"：

CI/CD 平台（GitHub Actions、GitLab CI、Jenkins 等）会**监听 Git 仓库的事件**，常见触发方式：

1. **push 到某分支** → 触发（比如 push 到 `main` 就跑构建+部署）。
2. **提 Pull Request / Merge Request** → 触发（跑测试和检查，通过才允许合并）。
3. **打 tag（如 `v1.2.0`）** → 触发**正式发布**流水线（构建发布产物、部署生产、发版本）。
4. **定时（cron）** 或 **手动** 触发。

底层是怎么"感知"到 Git 事件的？

- 云平台（GitHub/GitLab）通过 **webhook**：你一 push，平台就调用 CI 系统的一个回调 URL，把"谁、哪个分支、哪个提交"告诉它，CI 就开始跑。
- 流水线里通常按 **commit 哈希 / 分支名 / tag 名** 来决定做什么（比如"是 tag 就部署生产，是普通分支就只跑测试"）。

一个 GitHub Actions 的触发配置直观感受一下：

```yaml
on:
  push:
    branches: [main]        # push到main时触发
    tags: ['v*']            # 打v开头的tag时触发
  pull_request:
    branches: [main]        # 向main提PR时触发
```

一句话：**Git 的 push/PR/tag 等事件通过 webhook 通知 CI 平台，平台据此拉取对应提交并执行构建、测试、部署流水线。**

#### Q：Git Hooks 有哪些？客户端 hook（如 pre-commit）和服务端 hook 有什么区别？它们和 CI 怎么分工？⭐⭐

答：

**Git Hooks（钩子）**：Git 在**特定动作发生时自动执行的脚本**，放在 `.git/hooks/` 目录下。可以理解为"在某个时机自动帮你跑一段检查/操作"。

分两大类：

**客户端 hook（在开发者本地电脑上跑）**：
- `pre-commit`：**提交前**触发。最常用——跑代码格式化、lint、快速测试，不合格就拦下不让提交。
- `commit-msg`：检查**提交信息格式**（比如强制符合 Conventional Commits 规范）。
- `pre-push`：**push 前**触发，可跑更全的测试。

**服务端 hook（在远程仓库服务器上跑）**：
- `pre-receive` / `update`：服务器**收到 push、真正写入前**触发。可拒绝不符合规范的 push（比如禁止直接推 main、拒绝没过检查的提交）。
- `post-receive`：push 被接受**之后**触发，常用来触发部署、发通知。

核心区别（面试要点）：

| | 客户端 hook | 服务端 hook |
|---|---|---|
| 在哪跑 | 每个开发者自己电脑 | 远程仓库服务器 |
| 能否被绕过 | **能**（`git commit --no-verify` 就跳过了，且不会自动分发给别人） | **不能**，对所有人强制生效 |
| 适合 | 本地快速反馈（省得等CI） | 强制性的准入门禁 |

**和 CI 的分工**（关键认知）：

- 客户端 hook（pre-commit）：**快速、本地、给开发者早反馈**，但**不可信**（能被 `--no-verify` 跳过，也可能没人装）。所以它是"第一道方便的提醒"，不能作为唯一保障。
- 服务端 hook / **CI 流水线**：是**真正强制、不可绕过的关卡**。团队真正的质量门禁应该放在 **CI**（PR 必须通过 CI 才能合并）和服务端上。

一句话总结：**pre-commit 在本地给快速反馈但能被绕过，服务端 hook 和 CI 才是强制门禁；本地 hook 求快，CI 求稳、求不可绕过，两者互补。**

补充：`.git/hooks` 不会被 clone 分发，所以团队统一 hook 一般用 **pre-commit 框架** 或 **husky** 之类工具，把 hook 配置纳入版本管理、让每个人自动装上。

#### Q：Conventional Commits（约定式提交）/ 提交规范有什么价值？⭐

答：

**Conventional Commits** 是一套**提交信息的书写规范**，格式长这样：

```
<类型>(<可选范围>): <简短描述>

feat(login): 新增手机号登录
fix(api): 修复订单金额计算错误
docs: 更新 README 安装说明
```

常见类型：
- `feat`：新功能　`fix`：修 bug　`docs`：文档　`style`：格式（不影响逻辑）
- `refactor`：重构　`test`：测试　`chore`：杂务/构建　`perf`：性能优化

价值（面试要点，讲"能自动化"是加分项）：

1. **历史可读**：一眼看出每个提交是"加功能还是修 bug"，`git log` 清晰。
2. **能自动生成 CHANGELOG（变更日志）**：工具（如 semantic-release）可以扫描提交类型，自动生成版本更新说明。
3. **能自动决定版本号（语义化版本 SemVer）**：`fix` → 补丁号 +1（1.2.3→1.2.4）；`feat` → 次版本号 +1（1.2.3→1.3.0）；带 `BREAKING CHANGE` → 主版本号 +1（1.2.3→2.0.0）。**发版本可以全自动化**。
4. **方便筛选和协作**：按类型过滤提交、review 时快速定位。

配套：用 `commit-msg` hook 或 commitlint 工具**强制校验**格式，不符合就拒绝提交，保证全团队统一。

一句话：**约定式提交让提交信息结构化，从而能自动生成日志、自动定版本号、让历史更可读——是把"提交"接入自动化发布流水线的基础。**

#### Q：受保护分支（protected branch）是什么？合并策略里的 squash / rebase / merge 怎么选？⭐

答：

**受保护分支**：给 `main`、`master` 这类重要分支加上"保护规则"，防止有人误操作或绕过流程。常见规则：
- **禁止直接 push**，必须通过 Pull Request 合并。
- **PR 必须通过 CI**（测试、检查全绿）才能合并。
- **必须至少 N 人 code review 批准**。
- **禁止 force push**、禁止删除该分支。

这是团队质量和安全的"制度保障"，DevOps 岗常要配置这些。

**合并 PR 时的三种策略**（GitHub/GitLab 让你选）：

| 策略 | 做法 | 主干历史效果 | 适合 |
|---|---|---|---|
| **Merge commit**（普通合并） | 保留分支所有提交 + 生成一个合并提交 | 有分叉、完整保留过程 | 想保留真实开发过程 |
| **Squash and merge**（压缩合并） | 把 PR 里所有提交**压成一个**再合入 | 每个 PR = 主干上一个干净提交 | **最常用**，主干整洁，一个功能一个提交 |
| **Rebase and merge**（变基合并） | 把 PR 的提交逐个 rebase 到主干末尾 | 线性、无合并提交，保留每个提交 | 想要线性历史又想保留细粒度提交 |

怎么选（面试答法）：
- 想让主干**每个功能就是一个干净提交、便于回滚** → **Squash**（团队最流行）。
- 想要**线性历史**但保留每个小提交 → **Rebase**。
- 想**如实保留分支的开发过程和合并点** → **Merge commit**。

大多数追求整洁主干的团队默认用 **Squash and merge**。

#### Q：Git submodule（子模块）是什么？有什么优缺点和坑？

答：

**submodule** 让你在一个 Git 仓库里**嵌入另一个独立的 Git 仓库**。父仓库只记录"子仓库应该停在哪个 commit"，不把子仓库的代码直接混进来。常用于"我的项目依赖一个我也在维护/需要跟踪源码的库"。

```bash
git submodule add <子仓库URL> libs/some-lib   # 添加子模块
git clone --recurse-submodules <父仓库URL>     # clone时连子模块一起拉
git submodule update --init --recursive        # 已clone的仓库补拉子模块
```

优点：
- 主仓库和子仓库**历史独立、各自管理**，能精确锁定依赖到某个 commit。
- 适合"多个项目共享同一份代码库"且需要跟踪其源码时。

缺点/坑（面试爱问，能说出坑显得有实操经验）：
1. **容易忘记初始化**：别人 clone 后不加 `--recurse-submodules`，子模块目录是空的，一脸懵。
2. **两步提交**：改了子模块要先在子模块里提交+push，再回父仓库提交"指向的新commit"，很容易漏。
3. **子模块默认处于 detached HEAD**：新手在里面改代码不建分支，容易丢。
4. 团队协作时状态容易不同步，"子模块没更新"是常见事故。

替代方案：如果只是想固定依赖版本，用包管理器（npm/pip/go modules 等）通常更省心；如果想要真正的一体化，考虑 **monorepo** 或 `git subtree`。

#### Q：Monorepo 和 Multirepo 有什么区别？各自优缺点？⭐

答：

- **Monorepo（单体仓库）**：把**很多个项目/服务/库都放在同一个 Git 仓库**里（谷歌、Meta 都这么干）。
- **Multirepo / Polyrepo（多仓库）**：**每个项目/服务各自一个独立仓库**。

对比：

| 维度 | Monorepo（单仓） | Multirepo（多仓） |
|---|---|---|
| 代码共享/复用 | 容易，直接引用 | 要发包、跨仓依赖 |
| 一次改动跨多项目 | 一个提交/PR 搞定，原子性好 | 要改多个仓库、协调版本 |
| 统一规范/工具 | 容易统一 | 各仓各管，易分裂 |
| 权限控制 | 粗（一个仓） | 细（按仓授权） |
| 仓库体积/性能 | 会很大，需要专门工具 | 每个都小巧 |
| 构建/CI | 需要"只构建改动部分"的工具（Bazel、Nx、Turborepo） | 天然按仓独立 |

选型：
- 团队内高度协作、大量代码共享、想统一规范 → **Monorepo**（但要投入构建/CI 工具解决体积和"按需构建"问题）。
- 各项目独立性强、团队分散、想细粒度权限 → **Multirepo**。

一句话：**Monorepo 便于共享和原子化跨项目改动，但对工具链要求高；Multirepo 独立灵活、权限清晰，但跨仓协作和依赖管理更麻烦。**

#### Q：Git LFS 解决什么问题？⭐

答：

**问题背景**：Git 天生擅长管**文本**（能算逐行差异、压缩好），但对**大的二进制文件**（图片、视频、音频、数据集、编译产物、模型权重）很不友好——每改一次就得整份存一遍，仓库体积迅速膨胀，clone 变得又慢又大，而且历史里的大文件永远甩不掉。

**Git LFS（Large File Storage，大文件存储）** 的解决思路：

- 真正的大文件**不直接存进 Git 仓库**，而是存到一个**单独的 LFS 服务器/存储**上。
- Git 仓库里只留一个**小小的"指针文件"**（几十字节，记录这个大文件的哈希和大小）。
- 你 checkout 时，LFS 会根据指针**按需下载**真正的大文件。

```bash
git lfs install
git lfs track "*.psd"        # 声明.psd这类大文件交给LFS管
git lfs track "*.mp4"
git add .gitattributes       # track规则记在.gitattributes里，要提交
git add design.psd
git commit -m "添加设计稿"    # 仓库里存的是指针，实体走LFS
```

好处：主仓库保持轻量、clone 快；大文件也能纳入版本管理。

适用场景：游戏资源、设计稿、机器学习数据集/模型、音视频素材等需要版本化的大二进制文件。

一句话：**Git LFS 把大二进制文件挪到专门存储、仓库里只留指针，从而避免仓库因大文件而臃肿。**

#### Q：怎么用 tag 做版本发布和回滚？⭐

答：

**tag（标签）** 是版本发布的核心工具——它给某个"经过测试、准备上线"的提交起一个不变的版本名（如 `v1.4.0`），作为发布的**锚点**。

**用 tag 发布**：

```bash
# 1. 在确定要发布的提交上打附注标签（用语义化版本号）
git tag -a v1.4.0 -m "发布 1.4.0：新增支付功能"

# 2. 推到远程，通常这一步会触发CI/CD的发布流水线
git push origin v1.4.0
```

如前面讲的，CI/CD 常配置成"**检测到新 tag（如 v* ）就自动构建发布产物、部署生产**"。tag 成了"发布"这个动作的触发器和记录。

**用 tag 回滚**：因为每个发布版本都有 tag 标记，回滚就是"**把线上部署切回上一个稳定 tag**"：

```bash
git checkout v1.3.0          # 定位到上一个稳定版本
# 通常做法：从这个稳定tag重新部署，或基于它建hotfix分支
git switch -c hotfix/rollback v1.3.0
```

实践中回滚上线常见两种思路：
1. **重新部署旧 tag 的产物**（最快，很多 CD 平台一键"redeploy 某个 tag"）。
2. **用 revert 把出问题的提交反做掉**，再打新 tag（如 `v1.4.1`）重新发布——保留历史、更规范。

一句话：**tag 给每个发布版本一个不可变锚点，发布靠 push tag 触发流水线，回滚靠切回/重新部署上一个稳定 tag（或 revert 后发新版本）。**

#### Q：在团队里怎么保证提交质量？⭐⭐

答：

这题考的是"体系化的质量保障思路"，要答出**多层防线**：

**第 1 层：本地即时反馈（pre-commit hook）**
- 用 pre-commit 框架 / husky，在提交前自动跑：代码格式化（prettier/black）、静态检查（eslint/flake8）、快速单测。
- 好处：开发者第一时间发现问题，不用等 CI。但能被绕过，只是"辅助"。

**第 2 层：提交规范（commit-msg hook + commitlint）**
- 强制 Conventional Commits，保证提交信息规范、可自动生成日志。

**第 3 层：受保护分支 + Pull Request 流程**
- 主干设为受保护分支：**禁止直接 push**，一切改动走 PR。
- PR 必须满足：**CI 全绿 + 至少 N 人 review 批准**才能合并。

**第 4 层：CI 流水线（强制、不可绕过的核心门禁）**
- 在服务器上跑完整的：编译、全套测试、覆盖率检查、静态扫描、安全扫描（如密钥泄露检测、依赖漏洞扫描）。
- 这是真正可信的关卡（本地 hook 能被跳过，CI 不能）。

**第 5 层：Code Review（人的把关）**
- 机器查不出的设计问题、逻辑漏洞、可维护性，靠人 review 补上。

一句话总结：**"pre-commit 本地快检 + commit 规范 + 受保护分支强制走 PR + CI 强制门禁 + 人工 review"，多层防线互补——本地求快、CI 求稳不可绕过、review 补机器查不到的，共同保证质量。**

#### Q：`--force` 和 `--force-with-lease` 有什么区别？为什么推荐后者？⭐⭐

答：

背景：当你改写了本地历史（rebase、amend、reset 后），本地和远程"对不上"，普通 push 会被拒绝，需要**强推**覆盖远程。

- **`git push --force`**：**无条件**用你本地的版本覆盖远程，**不管远程现在是什么状态**。危险在于：如果在你 rebase 期间，**别人往同一分支 push 了新提交**，你这一 `--force` 会把**别人的提交直接冲掉**，造成同事的工作丢失。
- **`git push --force-with-lease`**：**有条件**的强推。它会先检查"**远程现在的状态，是否还是我上次看到的样子**"。如果是（说明这期间没别人动过）→ 允许覆盖；如果远程被别人更新过（和我印象里的不一样）→ **拒绝推送并报错**，提醒你"有人动过，先拉下来看看"。

打比方：
- `--force` 是"闭着眼睛硬盖，不管底下压没压着别人的东西"。
- `--force-with-lease` 是"盖之前先确认底下还是我上次看到的那样，被人动过就不盖了"。

对比：

| | `--force` | `--force-with-lease` |
|---|---|---|
| 是否检查远程被别人改过 | ❌ 不检查 | ✅ 检查 |
| 会不会冲掉同事的新提交 | **会** | 不会（会先拒绝） |
| 安全性 | 危险 | 相对安全 |

规范建议（面试标准答法）：**需要强推时，一律用 `--force-with-lease` 而不是 `--force`**，它能防止误删别人在你不知情时推的提交。当然，最根本的还是尽量不对共享分支强推。

#### Q：怎么做"代码回滚上线"？线上出问题了，你的处理流程是什么？⭐

答：

这题考应急处理思路，要答得**冷静、分场景、强调安全**：

**核心原则**：线上分支（main）通常是受保护的、已被大家共享的，所以**回滚要用不改写历史的方式（revert 或重新部署旧版本），不要用 reset 强推**。

分两种常见思路：

**思路一：Git revert（撤销问题提交，保留历史，最规范）**

```bash
# 1. 定位是哪个提交/哪次合并引入了问题
git log --oneline

# 2. 反做掉它，生成一个"修复用"的新提交
git revert <问题提交哈希>
# 若是合并提交： git revert -m 1 <合并提交哈希>

# 3. 走正常流程：push → CI → 部署上线
git push
```

优点：历史完整、可追溯、对团队安全；缺点：要重新走一遍构建部署，稍慢。

**思路二：重新部署上一个稳定版本（最快止血）**

如果 CD 平台支持，直接"**redeploy 上一个稳定 tag / 上一个成功的构建**"，几分钟内让线上回到好的版本。先止血，再从容排查根因。

```bash
# 定位上一个稳定发布
git tag                       # 找到上一个好版本，比如 v1.3.0
# 用CD平台把 v1.3.0 重新部署上线
```

**完整应急流程（面试可以这样组织）**：
1. **先止血**：用最快方式让线上恢复（重新部署上一个稳定版本 / 或 revert 后紧急发布），优先恢复服务，别急着查根因。
2. **建 hotfix 分支**排查和修复根因。
3. 修复经过测试后，正常走 PR + CI 合入主干，打新 tag（如 `v1.4.1`）发布。
4. **复盘**：写事故复盘，补测试/监控/门禁，避免再犯。

一句话：**回滚上线优先用"重新部署上一个稳定 tag"快速止血，或用 revert 规范撤销；坚决避免对共享主干 reset+强推。先恢复服务，再修根因，最后复盘补防线。**

### 五、高频"必背"速查清单（考前突击，争取脱口而出）

> 这一节把最容易被追问、最该秒答的核心区别浓缩成一句话，考前扫一遍。

**核心命令区别：**

| 对比项 | 一句话答案 |
|---|---|
| **fetch vs pull** | fetch 只下载不合并；pull = fetch + merge（自动合并进当前分支） |
| **merge vs rebase** | merge 保留分叉、生成合并提交；rebase 把提交搬到目标末尾、历史变直线但改写了哈希。**共享分支别 rebase** |
| **reset vs revert** | reset 改写历史、移动指针（撤销**未 push**）；revert 新建反向提交、不改历史（撤销**已 push**） |
| **fast-forward** | 目标分支没新提交时，合并就是把指针直接前移，不产生合并提交；`--no-ff` 可强制生成合并提交 |
| **add . / -A / -u** | `.` 当前目录范围；`-A` 整个仓库；`-u` 只管已跟踪文件（不加新文件） |
| **force vs force-with-lease** | force 无条件覆盖（可能冲掉同事提交）；force-with-lease 先检查远程没被别人动过才覆盖，更安全 |
| **轻量 vs 附注标签** | 轻量标签只是指针；附注标签是完整对象（含作者/日期/说明/可签名），**发布用附注** |
| **submodule** | 父仓库里嵌独立子仓库，只记子仓库的 commit 指针；坑是容易忘 `--recurse-submodules` |

**reset 三模式（背下来）：**

| 模式 | 分支指针 | 暂存区 | 工作区 |
|---|---|---|---|
| `--soft` | 移动 | 不变 | 不变（改动留暂存区） |
| `--mixed`（默认） | 移动 | 重置 | 不变（改动退回工作区） |
| `--hard` | 移动 | 重置 | 重置（**改动全丢**） |

**底层原理速记：**

- **快照 vs 差异**：Git 存**快照**（每次提交拍全量照片，没变的文件复用旧对象去重），不是存差异。
- **四种对象**：**blob**（文件内容）、**tree**（目录结构）、**commit**（提交元信息：指向 tree + parent + 作者 + 信息）、**tag**（附注标签对象）。
- **commit 里存了啥**：指向根 tree 的指针 + parent 提交哈希 + 作者/提交者 + 时间 + 提交信息（**不直接存文件内容**）。
- **为什么 rebase/amend 改哈希**：哈希是对提交全部内容算的指纹，parent 或信息一变，指纹必变。
- **分支的本质**：一个指向某 commit 的、41 字节的可移动指针，所以建/切分支极快。
- **HEAD**：指向"你当前所在位置"（通常是当前分支）；detached HEAD = 直接指向某个提交而非分支，此时新提交易丢。
- **reflog 能找回丢失提交**：因为 reset/删分支只是动指针，提交对象还在，reflog 记着它的哈希；GC 默认约 2 周后才真删不可达对象——**丢了提交先 `git reflog`**。

**应急处理口诀：**

- 撤销**未 push** 最后一次提交：`git reset --soft/--mixed/--hard HEAD~1`（要不要留改动看模式）。
- 撤销**已 push** 的提交：`git revert <哈希>`（不改历史、安全）。
- 合并多个提交：`git rebase -i` 用 squash，或 `git reset --soft` 后重新提交。
- 找回丢失提交/误删分支：`git reflog` 找哈希 → 建分支或 reset 回去。
- 只要别人某个提交：`git cherry-pick <哈希>`。
- 临时存改动切分支：`git stash` → 忙完 `git stash pop`。
- 提交了密钥：**先轮换密钥** → `git filter-repo`/BFG 改写历史 → force push → 通知团队重新 clone → 加 `.gitignore`。
- 强推必须用 `--force-with-lease`，不用 `--force`。
