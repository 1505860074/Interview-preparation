## Part 1 RAG 是什么 + 为什么需要（🔴 一句话定义 + 三个推荐理由）

**一句话**：**RAG（Retrieval-Augmented Generation，检索增强生成）** = 生成前先从外部知识库**检索**相关片段，拼进上下文后再让 LLM 生成 → **让模型用"最新/私有/庞大"的信息回答，而不是只靠训练时学到的东西。**

**为什么需要（🔴 必答三个理由）**：
1. **知识新鲜度**：模型训练有截止点，私有/实时信息（你的故障码、新配置、现场结论）模型根本不知道 → RAG 把"知识"放到外部，随时更。
2. **幻觉控制**：不检索就用记忆瞎编概率高；检索给了"答案证据"，模型照材料说，**可引用可溯源**。
3. **成本与私有**：全量训进模型很贵且还要重新部署（微调改权重），RAG 零训练、改文档即改知识、数据不出本地。

> **一句话记忆**："RAG = **把 '记住' 外包给数据库，让 LLM 专注 '会想'**。"

## Part 2 RAG 完整链路（🔴 全链路图，能画）

```
文档/消息/代码 ……
   │ ① 加载 & 解析（去噪、结构化）
   ▼
 Chunking 切分（含 overlap）
   │ ②
   ▼
 Embedding 编码（每 chunk → 一个稠密向量）
   │ ③
   ▼
 向量库索引（HNSW/IVF）+ 元数据（来源/时间/类型）
   │ ④ 查询：query → 同样 Embedding
   ▼
 检索 TopK（向量召回；可加关键词/多路召回）
   │ ⑤
   ▼
 Rerank 重排（Cross-Encoder 精排）→ 取最终 K 条
   │ ⑥
   ▼
 拼上下文 + 引用来源 → LLM 生成 → 输出（可溯源）
```

**六步必须能讲**：加载解析 → 切分 → 向量化 → 索引 → 检索（+重排）→ 生成。**面试官让你"讲一遍 RAG 怎么做"，你画这张图 + 每步一句话就是满分开场。**

## Part 3 Chunking 切分（🟡 基础但常问）

- **为什么切**：① Embedding 模型有最大长度限制；② 太长的 chunk 语义被稀释（一个向量存太多信息）；③ 检索粒度要"够小才能精确命中"。
- **切分策略（按好到坏的工程排序）**：
  - **按语义边界切**（标题/段落/代码函数）→ 最符合"一段话一个语义"。
  - **固定字符数 + overlap**：设定 max length + 前后 **overlap（重叠）**，避免语义被切断在边界丢失。
  - **按结构切**（MD/HTML/代码 AST）：你处理 Markdown/代码时天然按结构切。
- **overlap 的意义**：切分边界处若把完整语义切两半，检索会丢信息 → 重叠一段让"跨边界的语义"完整保存在某一块。
- **常见问题**：中文按字符切会切碎词；表格/代码要特殊处理；切太细 → 召回碎片错乱；切太粗 → 语义混杂。
- **评估**：切分好坏直接影响检索（**chunking 与检索效果强相关**，RAG 调优第一步常是调 chunking）。

## Part 4 Embedding（🟡 理解 + 会选型）

- **是什么**：把文本映射成**稠密向量**（如 1024/1536 维），**语义相近的文本向量距离近**。
- **嵌入空间的代价**：名称含义（"堵转"≈"卡住不动"在向量空间近；"0xff3f" 这种精确码在向量空间**没有区分度**→ 精确词用关键词检索）。**（这条 Part 6/9 会反复用，是你最值钱的洞察。）**
- **选型维度**：模型大小/维度、是否中文优化（你的场景要中文）、**MRL/M2V 多任务**（语义/检索双优）等；**工程上：距离度量 vs 维度 vs 精度**。
- **查询侧 vs 文档侧**：文档入库和查询到库都要过**同一个 Embedding 模型**，才能在同一空间比较。
- **归一化**：余弦相似度用归一化向量（内积=余弦）；向量字段均方归一化有助于 BM25/纯向量 A/B。

## Part 5 向量库与索引（🟡 理解 ANN）

- **向量库**：Milvus / Qdrant / pgvector / Chroma；装得下百万/亿级向量 + 元数据过滤。
- **关键是 ANN（近似最近邻）**：精确 KNN 太慢，用**近似**索引换速度：
  - **HNSW**（分层可导航小图）：精度高、快、**索引常驻内存大**（百万级 OK）。
  - **IVF**（倒排分桶，聚类中心分流）：省内存、召回略糙。
- **过滤与元数据**：按来源/时间过滤（你的"90 天滚动清理"就是元数据+过滤思想的落地）。
- **和传统索引的关系（串讲）**："向量索引和 B+ 树索引是同一类问题的两端：**B+树精确有序，能范围/精确；向量索引放弃精确换'亿级向量毫秒级 top-K'。推导出：关键词检索是精确家族、向量是近似家族，所以我混合用。**"（已在数据库册 Part 9.3 详述，可直接复用。）

## Part 6 检索：语义 vs 关键词 / 混合 / 多路召回

### 6.1 向量检索 vs 关键词检索（🔴 必背对比，你的四库每天都在用）
| | 向量检索 | 关键词检索（BM25/倒排） |
|---|---|---|
| 查找逻辑 | 语义相似 | **词面匹配** |
| 擅长 | 同义、换词、语义扩展（"卡死"→"堵转"）| 精确词、编号、专有名词（"0xff3f"、"E42"、"450/620/770"）|
| 弱点 | 精确码/罕见词失真 | 同义/换词召回不了 |
| 你的实现 | 向量召呼吁（CRG 知识库/语义） | ★SQLite FTS5 倒排（故障码/型号/人名）|

### 6.2 混合检索（Hybrid Search）+ 多路召回（🔴 加分点）
- **为什么混合**：单一向量召回在精确词、专有名词上有天然短板；单一关键词召回不了语义。两条路**并召回（multi-recall）再融合**，取长补短。
- **融合算法**：**RRF（Reciprocal Rank Fusion）**——按排名倒数和分加权（`1/(k+rank)` 求和），合并两路排名；或 **加权分数融合**。
- **面试一句话**："我因一个真实问题做了混合检索：**搜故障码 '0xff3f' 向量召回不可靠，搜 '卡住不动' 关键词召回不了——两个单一方案都有硬伤，所以两路召回 + RRF 融合。**"

### 6.3 查询改写（Query Rewriting，🟡 进阶加分）
- **为什么**：用户/模型 query 可能短、口语、含指代（"它上次说的问题"）→ 直接拿去检索不精准。
- **做法**：让 LLM 重写/展开 query（补全指代、加关键词、拆多意图）。
- **Agent 场景**：Agent 每步检索前先重写"当前需求"为精准检索词再查。

## Part 7 Rerank（粗排+精排 / Cross-Encoder，🔴 高频）

### 7.1 为什么要 Rerank（两阶段检索）
- **第一阶段（召回=粗排）**：向量/关键词召回 → Top 50–100，**快，但只讲"像不像"**。
- **第二阶段（重排=精排）**：对 top 内的候选，用**更精确的模型重新打分排序** → 取 Top 5–10 进上下文。
- **为什么不能直接用精排模型做全部检索**：精排模型（Cross-Encoder，query+doc 一起算）质量高但**慢**，全库跑不现实 → **粗召回 + 精重排，成本和质量的折中。**

### 7.2 粗排 vs 精排
| | 召回/粗排 | 重排/精排 |
|---|---|---|
| 模型/方法 | Bi-Encoder（query 和 doc **分别编码**，余弦/内积）| Cross-Encoder（query+doc **拼接一起编码**，打分）|
| 速度 | 快（可离线建索引）| 慢（每对都要算）|
| 精度 | 中 | 高 |
| 用于 | 全库召回取粗 Top | 粗 Top 里挑最优 Top-K |

### 7.3 ★ 你的四库怎么对应 Rerank（面试讲"我做过两阶段"）
> "我的跨源检索器**召回面比较粗**（FTS5 关键词 + 向量各召回一批），如果全塞给模型上下文会爆炸。所以我做了**过滤/排序两步**：先按来源/时间过滤 + 按相关度精简，再按优先级/可信度整理进上下文——**这就是'粗召回→精重排→限量进上下文'的降级版 RAG 重排**。我当时没叫它 Rerank，但做的是同一件事：**召回可以粗，进上下文的必须精。**"

## Part 8 GraphRAG 与高级变体

### 8.1 GraphRAG（🟡 概念）
- **痛点**：普通 RAG 擅长"点对点"检索（One-hop 事实），**回答跨多文档/依赖关系的问题时抽不干净**（如"哪些客户项目互相影响"）。
- **解法**：把文档/实体/关系**建图**（实体=节点、关系=边），检索时**沿图多跳扩展**再召回汇总。
- **工程代价**：建图成本高（LLM 抽实体关系）、图更新难、存储结构复杂。
- **★ 你的钩子（CRG 就是 Graph 检索）**：code-review-graph 用 **Tree-sitter 把代码建成结构图**（函数/调用/继承），检索时按图"最小相关上下文"取子图——**这就是面向代码的图检索**，和 GraphRAG"沿关系扩展"思路一致。**能讲出来就说明你真的理解图检索和文本向量检索的区别。**

### 8.2 其他变体（🟢 面到提一嘴加分，别细讲）
- **多查询检索**（multi-query）：一个 query 拆多个变体分别检索合并。
- **上下文压缩 / RAG-fusion**、**迭代 RAG（Agentic RAG）**：把检索本身当 agent 的一个工具（**RAG 和 Agent 的关系见 Part 10**）。

### 9.2 逐环节对应表（🔴 熟记，可展开）
| RAG 环节 | 你的实现（对应） | 你在里面加的工程细节 |
|---|---|---|
| ① 加载/解析 | 四源：飞书消息快照 / Claude 对话归档(.jsonl) / 飞书文档 / Confluence | **去噪**（剥离 thinking、超长工具输出）；转结构化 Markdown + INDEX.md |

| ④ 索引 | 全文索引 + 元数据字段 | 按源/人/时间过滤（字段过滤）|
| ⑤ 检索 | **统一跨源检索器** | **混合检索**：FTS5 精确（故障码/型号）+ 语义召回 + **RRF/排序融合**；查询改写（把需求转成检索词）|

### 9.3 完整话术（背下来）

> "我在公司建了四套本地知识库并做了一个跨源检索器，用 RAG 的话说就是：
> - **语料**：飞书消息、Claude 对话归档、飞书云文档、Confluence，每天增量拉取，属于**私有/实时/千量级中小语料**；
> - **索引**：用 SQLite（B-tree 底子）+ **FTS5 倒排**做主索引，元数据（人/群/时间/类型）可过滤；
> - **选择混合检索的原因（这是我踩过的最关键决策）**：我的数据里有大量**精确词需求**——故障码 `0xff3f`、型号 `450/620/770`、客户名/人名/配置项名。**这类 token 向量化后没有区分度，用向量检索反而不靠谱**，所以 FTS5 关键词检索是刚需；但要搜'电机卡住不动'这种语义（原文是'堵转'）关键词又召回不了，得靠向量/语义召回。**两条路各有不可替代，所以 hybrid search + 排序融合**；
> - **重排**：召回面粗，进上下文的要精——过滤+排序后只喂**最小相关上下文**给模型（省 token、防污染，这和 CRG'只喂最小相关子图'一个思路）；
> - **评估**：检索结果以'能不能正确回溯到原始消息/文档'为标准（RAG 的可溯源价值），每周被动检验（周报引用可追溯）。

> 因为四库量级是**本地中小语料**，我没上重型向量库/GraphRAG，选了**够用 + 零运维**的方案——**先想清楚检索需求是'精确还是语义'，再选索引，而不是一上来就上 RAG 全家桶。**"

**（这段话 = RAG 术语全套 + 真实决策 + 选型克制，是你所有面试素材里最完整的一段"项目级 RAG"，务必反复练。**）

## Part 10 RAG vs 微调 / RAG vs Agent（经典辨析题）

### 10.1 RAG vs 微调（🔴 高频）
| | RAG | Fine-tuning |
|---|---|---|
| 改什么 | 不改模型，改输入（喂检索到的知识）| 改权重 |
| 更新速度 | **秒级**（改文档就生效）| 重新训练/部署，贵慢 |
| 确定性 | 可引用可溯源，答案证有出处 | 记忆式，可能幻觉 |
| 适合 | 知识类/事实类/动态/**私有**数据 | **稳定行为/风格/格式/领域语言** |
| 成本 | 每次调用检索+token | 一次训练+长期部署 |
| 一句话 | **"知识放 RAG，行为才微调"** | |

### 10.2 RAG vs Agent；RAG 是 Agent 的一个工具吗？（🔴 必考开放题）

**结论：RAG 是一种"检索+生成"模式；Agent 是"循环使用工具完成任务"的系统。两者正交但高度协同。**

- **RAG 不必然是 Agent**：单次检索+生成就叫 RAG（一次问答）。
- **RAG 可以是 Agent 的工具**：Agent 在循环里**把"检索"当成一个工具来调**（`search_knowledge_base(query)`），想搜就搜 → 这是 **Agentic RAG**（检索变成 Agent 循环里的动作，而不是固定前置于 prompt）。
- **分辨**：普通 RAG：检索发生在**生成前一次**；Agentic RAG：检索发生在**循环中多次、按需、可追问**。

> **★ 你的项目经理对照（讲这个最清楚）**：
> "我的'每日问题总结'是**先检索后生成**（标准 RAG）；但我的跨源检索器被 Claude Code 当**工具按需调用**，它会自己决定'什么时候搜、搜什么、搜完要不要再搜'——这说明 RAG 是不是 Agent 取决于**检索发生的位置**：固定前置=pipeline RAG；循环中按需=Agent 化 RAG（它就是 Agent 循环里的一个 tool）。"

## Part 11 RAG 的评估（🟡 你有测试背景，讲起来加分）

- **分段评估（不只看最终答案）**：
  - **召回质量**：检索到的片段**相关性与完整性**（Recall@K / 命中 gold 片段比例）。
  - **重排质量**：前 K 是否包含真相关项。
  - **生成质量**：**忠实性（Faithfulness，答案是否基于提供的片段，不编造）** 与 **答案相关性**。
- **可测工具**：RAGAS 类框架给三连指标（忠实度/相关度/上下文正确性）。
- **★ 你的做法（测试思维）**："我评估 RAG 和测试一个道理：**看'检索准不准'（召回=取全）和'回答有没有忠于引用'（忠实=不编）两个环节分测**，再加引用可回验。因为检索和生成是两个故障点，合着测会把错归错位。"

## Part 12 面试题库

### 高频必答
1. RAG 是什么？为什么需要？→ 检索增强生成；新鲜/私有/可控幻觉/省微调成本。
2. 完整链路画一遍？→ Part 2 六步图。
3. 向量检索 vs 关键词检索？→ 语义 vs 精确词；各有一段（你的故障码例子）。
4. 什么是混合检索？怎么融合？→ 两路召回 + RRF/加权。
5. 为什么要 Rerank？粗排/精排区别？→ 召回快但粗、精排慢但准；两阶段折中；Cross vs Bi-Encoder。
6. Chunking 怎么切？overlap 为什么？→ 语义边界/长度+overlap/结构切；避免边界切断语义。
7. RAG vs 微调 vs Agent？→ 知识放 RAG、行为才微调；RAG 可前置（pipeline）也可作 Agent 工具（agentic）。
8. GraphRAG 是什么？→ 建图沿关系多跳检索；代价是建图/更新成本。
9. 怎么评估 RAG？→ 召回/重排/生成双侧：忠实性+相关性+引用可溯源。

### 深挖
- "检索不准最可能浪费在哪？"→ 切分粒度 + embedding 与语料匹配 + query 改写 → 调优顺序：chunk→检索→重排→prompt。
- "什么时候不该用 RAG？"→ 模型已提供足够知识、答案不要求精确/可引用、检索本身成本超收益（小型已知范围）。
- "多查询/迭代检索会放大什么风险？"→ 成本上升、上下文爆炸 → 要预算+熔断（回到系统设计的平衡）。

### ★ 结合项目
- "讲一个你做过带检索的系统。"→ Part 9.3 完整话术（这是最完整的回答素材）。
- "你搜故障码和搜'卡住不动'为什么用不同检索？"→ 精确码向量化失真（Part 6.1/9.3），这句观点独特且真实。
- "你的检索怎么保证不喂脏上下文？"→ 去噪 + 过滤 + 防空（Part 4.3 Agent 册 + 本册 9.2）。

> **本册一句话**：RAG 的高分不是背链路图，而是**"在什么场景选什么索引、为什么"的决策**——你手里有四库这个真实案例，还有"故障码该用关键词、语义该用向量"这个一般人没有的洞察。**把 Part 9.3 那段话说到能自然讲出，RAG 这道题你就赢了。**
