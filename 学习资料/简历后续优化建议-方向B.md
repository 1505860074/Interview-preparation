# 简历后续优化建议 · 方向 B（补内容 / 升级证据）

> 记录时间：2026-08-17
> 适用简历：`姚金盟-简历-CodingAgent-v13-一页.html`（当前最终版）
> 说明：这是「方向 A（改措辞和结构，已完成 v10–v13）」之后，**收益最大的下一步**。
> A 已把现有材料的**呈现**打磨到极致；B 的目标是**补充/升级证据本身**，突破 A 的天花板。

---

## 一、B 要解决的核心矛盾

简历目前最大的短板：

> **定位是「Coding Agent 研发工程师」，但证据几乎全是「Agent 重度使用者 + 研读/复刻者」，缺少「构建者 / 改进者」的证据。**

关键认知：**招聘方买的是「你能造 / 改进 Agent」的能力，而不是「你很懂用 Agent」。**
重度用户全网几十万，不稀缺；能从 Agent 侧动手造东西、并把它做稳、做得可评测的人，才稀缺。

### 证据强度分层

| 层级 | 内容 | 目前情况 |
|---|---|---|
| L1　用现成 Agent 编排 | headless 调 Claude Code 做飞书群每日总结 | ✅ 已有（本质是「用」）|
| L2　研读 / 复刻开源 Agent | letta 三层记忆复刻、nanoGPT、code-review-graph | ✅ 已有（本质是「临摹」）|
| **L3　从 0 手写 agent loop** | 自己设计 tool-use 循环、定义 tools、管理 context | ❓ **分水岭，尚缺** |
| **L4　改进 / 评测 Agent** | 写 eval harness 测 Agent 行为、做失败恢复 / 上下文压缩策略 | ❓ **最贴目标，尚缺** |

- **方向 A 的天花板就在 L2**——再怎么改措辞，也变不出 L3 / L4 的证据。
- **方向 B 的目标：把简历顶到 L3 / L4。**

---

## 二、为什么 B 对「测试出身」的我尤其值 —— 独特差异化角度

自我定位里最值钱的一句话：

> 「从 Agent 侧提升其**稳定性与可评测性**」

问题：**它目前是空口号**，下面没有任何项目兑现它。
但这里恰恰藏着**杀手锏**：

> **「Agent 的 evaluation / 稳定性 / 失败恢复」是一个「测试思维 × LLM」的交叉领域。**
> 绝大多数投 Agent 研发的人不懂测试；而我恰好是测试工程师出身。

**结论：**
- 一直以为「测试出身」是投研发岗的**包袱**；
- 但只要 B 做的是「**Agent 评测 / 稳定性**」方向，测试背景立刻从**减分项 → 差异化优势**：
  「一个懂得如何系统性地测东西的人，来做 Coding Agent 的可评测性」。
- 这正是大厂 Coding Agent 团队真实缺人的地方（agent eval / benchmark / 稳定性都在建设期）。
- **性价比最高的一跃**：不需要转行去补一堆 LLM 训练知识，而是把**已有的测试硬实力**平移到 Agent 评测上。

---

## 三、B 的候选项目（从小到大，按推荐度排序）

> 原则：优先选**既贴目标句（可评测 / 稳定性）、又吃测试功底**的项目。

1. **⭐ Agent 行为评测小框架（eval harness）** ——**最推荐**
   - 给一个 coding agent 设计一组任务用例 + 自动打分：跑通率 / token 消耗 / 步数 / 失败类型分布。
   - 跑几个模型或几款工具做横向对比，产出评测报告。
   - 直接兑现「可评测性」这句话，且最大化利用测试功底。

2. **失败恢复 / 稳定性实验**
   - 故意注入失败（工具报错、超时、幻觉路径），观察不同 agent 的恢复行为并量化对比。
   - 兑现「稳定性」这句话。

3. **自研极简 coding agent（补 L3）**
   - 从 0 手写 agent loop + 几个真实 tool（读文件 / 跑测试 / 改代码）+ context 管理，玩具级也行。
   - 证明理解 Agent 内部机理，而非只会调 API。

4. **自研 MCP server（顺带补 TypeScript 短板）**
   - 把现有「四套本地知识库检索」封装成一个真正的 MCP server，用 TS 写。
   - 一举两得：既是 Agent 生态产出，又补上简历缺的 TS 实战。

---

## 四、B 的铁律：绝不编造

- 简历上写的每个项目，**面试都会被追着问实现细节**，编造的一戳就穿，风险极高。
- 所以 B 的产出必须基于**真实做过 / 真实愿意投入时间做**的东西。
- 宁可项目小、但每一句都能经得起追问，也不要写一个华丽但答不上细节的项目。

## 五、落地前需要先想清楚的问题（自检清单）

在动手前，先如实回答自己这几点，用来决定「挖现有材料」还是「新做一个小项目」：

1. **是否从 0 写过 agent loop？**（不是复刻 letta，而是完全自己设计：模型 → 调工具 → 观察结果 → 再决策 的循环 + 自定义 tools）到什么程度？没有的话愿不愿意做？
2. **实测对比 Claude Code / Cursor / opencode / Aider 时，有没有留下产出物？**（对比笔记、评测记录、发现的失败案例 / bug、整理的用例）—— 这些是能直接长成 eval 项目的**种子**。
3. **XYZ 的「每日自动问题总结」里，有多少是自己写的逻辑？**（prompt 设计、工具封装、失败重试、结果校验）还是基本只是 headless 调一下？
4. **针对「Agent 行为好不好、稳不稳」，有没有过任何评测 / 打分的想法或雏形？**（哪怕只是「我觉得应该这么测」）
5. **现实约束**：距离面试还有多久？能投入多少时间做 B（几天 / 1–2 周 / 完全没空只能重新包装现有材料）？
6. **目标岗 JD**：Moonshot 的 Coding Agent 岗具体强调什么（eval / infra / agent framework）？拿到 JD 能让 B 的方向更精准命中。

## 六、两条落地路径（回答完上面再二选一）

- **路径一：挖现有材料**
  从「多工具实测记录 / XYZ 自动化脚本 / 知识库检索」里，找出一个能升级到 L3 / L4 的点，补充实现 + 整理成项目 + 写教学文档，替换或补强简历上的一个条目。

- **路径二：新做一个 1–2 周小项目**
  按第三节候选（首选「Agent 评测小框架」），规划一个能做完、能开源、能写进简历、且面试扛得住追问的项目。
